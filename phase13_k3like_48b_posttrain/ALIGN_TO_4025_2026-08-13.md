# Aligning to the upstream K3 PR: structural comparison and migration plan

Fetched `JavaZeroo/torchtitan agent/add-kimi-k3-reference-model` at `1da44c16a`
("Add Kimi K3 numerical validation"), based on upstream `5de7d1150` -- inside the window
we just merged, so it is current.

The decision this document supports: **pre-rebase onto their structure now** rather than
finish migrating ours. If their PR lands while our 2,300-line hand-built model is
mid-migration, we inherit a conflict on every file at once.

## The headline

| | theirs | ours |
|---|---|---|
| `model.py` | 805 lines | 2,300+ |
| `parallelize.py` | **100 lines** | 1,400+ |
| `parallelize_module` / `use_local_output` | **0 / 0** | 3 / 28 |
| nested `Config` classes | **9** | 0 |
| module base classes | `Module`, `FeedForward`, `BaseAttention`, `GroupedExperts`, `Decoder` | `nn.Module` |

Their `parallelize.py` calls `apply_fsdp_to_decoder` and `apply_fsdp_to_vision_encoder`
and nothing else. Everything TP is declared on the Config tree. This is the shape the whole
migration I have been attempting was converging on -- **they already wrote it**.

## AttnRes: they have it, and their data structure is the one that works

I first read their class list and concluded they had no AttnRes. Wrong: it is a function
plus a field on the block, not a class.

```python
def _apply_attention_residual(hidden_TD, block_residual_TND, proj, norm)
class KimiK3TransformerBlock(Module):   # "Hybrid KDA/MLA decoder block with Kimi attention residuals"
    def forward(self, x_BLD, block_residual_TND, ...) -> tuple[Tensor, Tensor]
```

The difference that matters is the CARRIER:

| | theirs | ours |
|---|---|---|
| block history | `block_residual_TND`, one `[T, N, D]` tensor threaded through every block's signature | a Python `list` of block tensors |
| running sum | `prefix_sum_BLD`, a local returned in the tuple | `partial_block`, a second accumulator |
| gate stream | -- | `plain_stream`, a third accumulator |
| block commit | `torch.cat` at `layer_id % attn_res_block_size == 0` | `blocks.append(...)` |
| aggregation | `torch.cat` + prefix sum, FP32 | `torch.stack(blocks + [partial_block])` |

**Three Python-level accumulators versus two tensors in the forward signature.** That is
exactly the wall this migration hit today: `ffn_out` became a DTensor while
`partial_block` and `plain_stream` stayed plain, because no `sharding_config` can reach a
value the model code carries in a list. A tensor that crosses the module boundary can be
declared; a list element cannot.

Their block also carries a measured note we should not lose:

> returning None here instead reassociates the residual's gradient accumulation and
> perturbs `tok_embeddings.weight.grad` by ~2e-3 relative

They route `block_residual_TND` back out of the module even when unchanged, so the FSDP
unit's backward hooks see it. That is an FSDP-correctness constraint on the carrier design.

## What this means for our four PRs

**PR-C (PP + AttnRes): the adapter STAYS.** An earlier draft of this file said the
threaded carrier might make it unnecessary. That is wrong, and the arithmetic says so:

    block_residual_TND = h_BLD.new_zeros(B * L, 0, D)          # N = 0
    block_residual_TND = torch.cat((block_residual_TND, ...), dim=1)   # +1 per block

`N` grows monotonically with depth, so shipping the carrier through the stage boundary
costs `[T, N, D]` per hop and `N` is the number of blocks committed so far. At 2.8T dims
(8 blocks, seq 8192, hidden 7168) one block is 0.109 GiB, so the last hop carries ~0.88 GiB
per microbatch, multiplied by the microbatches in flight under `pp x vp`. The adapter's
rank-local cache plus a `recv_delta` is what makes that per-hop cost CONSTANT -- which is
the whole reason it exists.

Their `parallelize.py` has no PP at all, so they have not met this. What changes is not
whether we need the adapter but WHAT it caches: columns of `block_residual_TND` instead of
elements of a Python list.

**PR-A (TP + KDA)** shrinks to whatever their declarations do not cover. Their KDA is
`KimiDeltaAttention(Module)` with a `KimiKDAKernel(Module)` inside it and no
`use_local_output` anywhere, so the fla boundary is handled differently from ours -- read
their kernel module before assuming our shims are still needed.

**PR-B (EP + grouped MoE)** -- they have `KimiGroupedExperts(GroupedExperts)` and
`KimiLatentMoE(Module)`. Our EP work already goes through upstream's
`set_moe_sharding_config`, so this is the closest to theirs.

**PR-D (CP)** -- theirs has no CP, so this stays our increment. The LOGIC does not change;
the attachment points do -- Ulysses for MLA and fla's merged KCP for KDA hang off attention
modules that will now be `KimiMLAAttention` / `KimiDeltaAttention` from their tree.

Summary of how much each axis moves:

| axis | theirs | what happens to ours |
|---|---|---|
| TP | declarative, complete | mostly replaced; what remains is the LoRA / packed-MXFP4 段 they have no equivalent for |
| EP | `KimiGroupedExperts`, `KimiLatentMoE` | smallest change -- ours already goes through upstream's `set_moe_sharding_config` |
| CP | **none** | logic kept, re-attached to their attention modules |
| PP | **none** | adapter kept, its cache re-targeted at the new carrier |

## Rules for the migration itself

These exist because a half-finished migration already left an unrunnable tree once today,
and only a branch kept it off the main line.

1. **The imperative implementation is the reference and nothing is deleted before its
   replacement passes the matrix.** Every increment goes new-alongside-old, verify, then
   remove -- never remove-then-rebuild.
2. **One axis per branch.** No flipping two of them in the same tree.
3. **The criterion is the three-arm matrix, not "it runs".**
4. **`attention_residual_dev` stays at the last all-green state**; every migration step
   lives on a branch until its matrix is green.

## What is genuinely ours after alignment

Nothing about the base model. The increments are:

* Block AttnRes **under PP** (the cross-stage story, whatever survives of the adapter)
* CP: Ulysses for MLA, KCP for KDA, dynamic CP for the vision tower
* LoRA / QLoRA, including LoRA x TP and packed MXFP4 -- their model has no LoRA
* DEP (report sec 5.2.3), which their vision encoder does not have
* MTP, the 2.8T flavor, and the veRL / SGLang integrations

## Migration plan

Ordered so each step is verifiable and nothing is discarded before its replacement runs.

### 0. Freeze what is verified (no code)
`attention_residual_dev` at `108e55f4b` is the reference: multimodal full 16/18, LoRA
16/18, text 10/18 with all failures attributed. Every step below is judged against
`verify_post_merge/` by `compare_to_dev_baseline.py`.

### 1. Vendor their model on a branch, unmodified
Take their `model.py`, `parallelize.py`, `config_registry.py`, `state_dict_adapter.py`,
`vision_encoder.py` as-is into a branch. Run the text arm. This measures the gap in one
step: whatever fails is what our flavors need that theirs does not provide.

### 2. Port our flavors onto their config registry
Their registry is Config-tree based. Our flavors (debugmodel_report_arch, mini, 2p8t,
LoRA/QLoRA variants) become Config trees. Gate: the text arm's cells train.

### 3. Re-attach the increments, in dependency order
CP first (attaches to attention modules, no interaction with AttnRes's carrier), then
LoRA/MXFP4 (attaches to Linear leaves), then DEP, then PP.

### 4. PP last, and re-derive rather than port
Check first whether threading `block_residual_TND` through the stage boundary removes the
need for the cache adapter. If it does, PR-C becomes a small change to
`module_fqns_per_model_part` plus the DEP vision-stage wiring. If it does not, port the
adapter -- but only the parts the new carrier still needs.

### 5. Verification at every step
Three arms, `compare_to_dev_baseline.py`, criterion "no BROKE". Expect numbers to move:
their model is a different implementation, so byte-identity is not available and is not the
target. What must hold is that every cell that trains today still trains.

## Two things to confirm before step 1

* **Is their AttnRes numerically ours?** They validate against the release
  ("Add Kimi K3 numerical validation"); we validate a graft against Kimi-Linear-48B at
  alpha=0. Compare `_apply_attention_residual` against our `block_attn_res` on the same
  inputs before assuming the semantics match.
* **Does their block interface survive PP splitting?** A block that takes and returns a
  tuple has to be splittable by `pipeline_module_split`. Read how their model iterates
  `self.layers.values()` and whether the tuple threading is compatible.


## CORRECTION 2026-08-14: upstream has NO parallelism but FSDP

The per-axis table above says TP is "declarative, complete" and EP is present via
`KimiGroupedExperts` / `KimiLatentMoE`. **Both are wrong**, and the migration plan built on
them is wrong in the same place.

Checked on their tree at the head we vendored:

* `parallelize.py` raises `NotImplementedError` for tensor, pipeline, context AND expert
  parallel. It calls `apply_fsdp_to_decoder` and `apply_fsdp_to_vision_encoder`, nothing else.
* `sharding_config` / `ShardingConfig` appear **zero times** in their `__init__.py` and
  `model.py`. There are no declarations.
* They never call `model.parallelize()`.

The error was reading inheritance as capability: their modules subclass `Module`,
`GroupedExperts`, `BaseAttention`, which are the classes that CAN carry declarative
sharding. Carrying the mechanism is not the same as declaring a layout, and with no
`sharding_config` anywhere, `parallelize()` would be a no-op even if it were called.

So upstream K3 has **FSDP2 and nothing else**. Every one of the four parallelisms is built
from zero on this tree, not ported onto an existing one:

| axis | what the plan assumed | what is true |
|---|---|---|
| TP | declarative and complete; ours mostly deleted | absent; ours is the only implementation |
| EP | present; smallest change of the four | absent |
| CP | absent | absent -- correct, and now done (`MIGRATION_STEP3_CP_2026-08-14.md`) |
| PP | absent | absent -- correct; carrier fix done, adapter remains |

This makes the migration larger than planned on two axes and does not change the other two.
It also means our TP and EP work is not redundant with anything upstream, which is the
opposite of what the plan concluded.
