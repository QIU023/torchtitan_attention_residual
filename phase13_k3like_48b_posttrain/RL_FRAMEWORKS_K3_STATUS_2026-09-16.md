# Kimi K3 post-training in the other RL stacks: verl upstream, Miles, slime, Megatron-Bridge (2026-09-16)

Checked on 2026-09-16 through the GitHub API, the repos' trees and the linked pages. The verl repository moved from `volcengine/verl` to `verl-project/verl` (searches against the old name return HTTP 422).

## verl upstream (`verl-project/verl`)

- No Kimi K3 in the tree: the only Kimi files are `verl/models/transformers/kimi_vl.py`, `verl/checkpoint_engine/kimi_checkpoint_engine.py` and a K2.6 / GLM-5.1 Megatron script. The upstream torchtitan engine (`verl/workers/engine/torchtitan/transformer_impl.py`, 884 lines) has no K3 mention; the fork's engine (`kimi_k3_integration_rebased` = `a3661ae3`, 46 commits on upstream `00cd5b44`) is the only torchtitan-engine K3 path.
- One open PR: verl-project/verl#7866, "[fsdp, megatron, rollout, model] feat: support Kimi K3 training on Ascend NPUs" (wangdongleix, opened 2026-09-15, awaiting seven code owners, CLA pending). Ascend only: FSDP-Turbo (checkpoint streaming into local shards, packed expert weight export), Megatron / MindSpeed-Bridge (multimodal forward registration, routing replay, gradient and optimizer offload, distributed checkpointing), vLLM-Ascend rollout, NPU IPC weight reconstruction; full-parameter, multimodal, no parallelism claims, "Ascend end-to-end validation is pending", launch scripts reference files not in the PR. Nothing in it runs on GPU.

## Miles (`radixark/miles`, LMSYS / RadixArk, forked from slime)

- Day-0 K3 RL on 2026-07-27 (LMSYS blog "SGLang and Miles Add Day-0 Support for Kimi K3"): radixark/miles#1825 "Kimi-K3 lora RL day-0 support" (yueming-yuan, opened 2026-07-27, last commits 2026-09-10, still open awaiting seven code owners; depends on sglang#37704 and Miles#3194). Docs: `docs/models/kimi/kimi-k3.md`; image `radixark/miles:kimi-k3` with the `sglang-miles-k3` SGLang branch.
- Model: Miles's own K3 layers on Megatron-LM ("Megatron is untouched"), with three custom operators from a Megatron-LM fork PR ("Add the Kimi K3 backend primitives Megatron-LM#94": `gated_activation_func`, `moe_latent_use_norm`, `sum_gradients_across_tp_domain`). Covers KDA, no-RoPE MLA, the attention-residual snapshot bank and the latent MoE. Text only; MoonViT not mentioned.
- Parallelism: TP / SP / PP / CP / EP. Pipeline: "K3's attention-residual snapshot bank has to cross stage boundaries, but Megatron's point-to-point carries one hidden-states tensor, so the stage boundary packs `[prefix_sum, bank]` into it and unpacks on entry" (the whole bank rides every hop; no delta, no rank store). Context parallel: "The bank shards for free, since every attention-residual operation is per-token"; "The relayout runs only around KDA".
- Training mode: LoRA only. "Full-parameter K3 RL currently disabled", pending SGLang reloading MXFP4 in place. Rank 16 default, 32 / alpha 64 in the validated run, lr 1e-5; adapters on `o_proj`, `q_a_proj`, `kv_a_proj_with_mqa`, the dense MLP and both expert projections; the 896 experts share one A factor and carry per-expert B factors. Base weights: the MXFP4 checkpoint upcast to BF16 once offline (`tools/convert_mxfp4_to_bf16.py`), then an offline `torch_dist` conversion on 32 ranks; training takes the MXFP4 directory as `--hf-checkpoint` and the converted `torch_dist` as `--ref-load`; `lora_base_cpu_backup` keeps a host copy of the frozen base so the GPU copy is reclaimed during rollout.
- Rollout: colocated with native packed-MXFP4 SGLang engines on the same GPUs; each step transfers only BF16 LoRA adapters over CUDA IPC as HF-named chunks (278 buckets), "the engine applies the delta as a separate BF16 `B(Ax)` term on top of the quantized base GEMM"; no full-weight resync, no requantization.
- Scale and numbers: 16 nodes x 4 GB300 (64 GPUs, 277 GiB cards); validated knobs PP 8, CP 2, EP 8 (resolved), rollout TP 16, `max_tokens_per_gpu` 8192 (the blog quotes TP8 / PP8 / EP8 for the trainer); rollout peaks near 225 GiB per GPU, the BF16 trainer near 155 at initialization; train / rollout KL flat at the ~2e-3 MXFP4 floor; AIME-2024 greedy 43.3% to 76.7% over 60 steps under a 12 h limit (DAPO), the PR's 236-step run 0.467 to a 0.867 peak at step 170; the four-layer smoke (4 nodes, TP16) reads train_rollout_logprob_abs_diff 0.0611 / train_rollout_kl 0.0057.
- Hopper: `SGLANG_K3_ATTN_RES_MODE=jit`; validation was on Blackwell.

## slime (`THUDM/slime`)

No K3: the tree has Kimi K2 / K2-Thinking scripts only; the K2.5 work (INT4 RL, HF weight conversion, Kimi-VL PP and multimodal input fixes) sits in open or closed PRs; no issue or PR mentions K3, Kimi Linear, KDA or attention residuals. The K3 work of that family is Miles's.

## Megatron-Bridge (`NVIDIA-NeMo/Megatron-Bridge`)

Tracking issue #4910 ("PoR: [model] tracking: Kimi K3 support"). Nightly docs carry `bridge.models.kimi.kimi_k3_layers` (`KimiK3ShortConvolution`, TP-sharded KDA short convolution with FP32 state; `KimiK3Attention`, KDA or no-RoPE MLA by global layer number; `KimiK3MoELayer`, MCore latent MoE with the post-combine RMS norm; `KimiK3TransformerLayer`, "implementing Kimi K3's AttnRes residual bank"), `kimi_k3_bridge`, `kimi_k3_provider`, `kimi_k3_ops`. The parameter mapping is "adapted from the Apache-2.0 Miles implementation". Status page: the language backbone only; HF to Megatron import and Megatron greedy inference verified (BF16, TP2 / PP3 / EP8 / ETP2 on 12 nodes x 4 GB200, 2026-07-28); not verified or not done: CPU import / export, GPU export to HF, exact round-trip parity, pretraining, SFT, long context, LoRA / PEFT ("Training was intentionally excluded from this model-only verification pass"), vision.

## What this changes for the K3 line here

- The RFC's post-training question (torchtitan RL #4680 or the veRL engine) now has a third reference point: the only K3 RL that has run at production scale is Miles's LoRA-only colocated recipe on Megatron. The veRL torchtitan engine here is the only stack with a full-parameter path and the only one on torchtitan's parallelisms; full-parameter on Miles waits for SGLang's in-place MXFP4 reload, which the engine here sidesteps by syncing bf16 weights (and fake-quantized expert stacks for QAT models).
- Miles's pipeline transport is the whole-bank pack into the single P2P tensor; PR 4312's stage class carries the committed block's delta and keeps the rest in a rank store. That is a concrete design difference to name in 4312's thread when the reviewer asks about alternatives, and the PP offload / balance drafts have no counterpart there.
- Miles's CP note ("the bank shards for free") is the same observation as 4639's block-stack-on-cp adaptation on the tree.
- Megatron-Bridge now has K3 layers with the AttnRes bank (from Miles's mapping) but no training recipe; the "AttnRes port to Megatron" item is therefore not a port of the block math any more, it is the training-side pieces (pipeline transport, recompute, offload) if it is pursued at all, and the hold until PR 4312 merges stands.
- Numbers that are not comparable: Miles's KL floor (2e-3, MXFP4 rollout against a BF16 trainer at 2.8T) against the engine's log-prob diff mean (0.15, a bf16 debug model against vLLM on the 5060); a real-weight cell is what makes the engine's number meaningful (the 48B graft or the released checkpoint).
