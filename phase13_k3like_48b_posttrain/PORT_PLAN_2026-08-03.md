# Porting plan: gate first, then four parallelism PRs

## Step 0 (gate): alpha math parity -- RESOLVED against the release itself

No fixtures were needed. The official modeling code is downloadable like the
tokenizer was: `modeling_kimi_linear.py` (50 KB) carries `_apply_attn_res`, and
`modeling_kimi_k3.py` turns out to be entirely MoonViT3d -- which also settles
the naming question PR #4025 raised.

The official operator, verbatim:

    def _apply_attn_res(prefix_sum, block_residual, proj, norm):
        v = torch.cat((block_residual, prefix_sum.unsqueeze(1)), dim=1)
        v_float = v.float()
        variance = v_float.pow(2).mean(-1, keepdim=True)
        k = v_float * torch.rsqrt(variance + norm.variance_epsilon)
        score_weight = norm.weight.float() * proj.weight.squeeze(0).float()
        scores = (k * score_weight).sum(-1)
        probs = scores.softmax(-1).unsqueeze(1)
        hidden_states = torch.matmul(probs, v_float).squeeze(1)
        return hidden_states.to(v.dtype)

Three of the four suspected differences are NOT differences:

**Concatenation.** `prefix_sum` is assigned `hidden_states` at layer entry and
appended to `block_residual` at block boundaries -- the same semantics as our
`partial_block` and `blocks`, under different names. Not a prefix-sum in the
cumulative-sum sense.

**Scoring.** The official code folds `norm.weight` into the query
(`norm.weight * proj.weight`) and dots it with an UNWEIGHTED `k`. We apply
`nn.RMSNorm` (which includes its affine weight) and dot with `proj.weight`
alone. These are the same operator: `(w*k) . p == k . (w*p)` elementwise.

**Normalisation.** Ours is `nn.RMSNorm`, theirs is the same formula written out
with `variance_epsilon`. Same eps source.

**The one real difference is precision.** The official operator computes the
whole of alpha in FP32 -- `v.float()`, an FP32 `score_weight`, FP32 softmax and
matmul -- and casts back only at the end. Ours deliberately casts DOWN to the
stream dtype at two points (`K = K.to(V.dtype)`, `query = query.to(K.dtype)`)
to match FSDP mixed precision.

That matters more here than it usually would: alpha starts with a
zero-initialised projection, so the softmax starts uniform and the pseudo-query
gradient is a difference of nearly equal terms. This session measured the
cancellation at 6x to 15x. Doing that in bf16 rather than FP32 is exactly where
it costs.

Action: switch the alpha operator to FP32 and re-take the AttnRes-sensitive
numbers. The adapter is untouched -- transport and gradient topology do not
depend on the operator's dtype.

## Correction on the CP gap

The plan says "parallelize.py has no apply_cp, so MLA sequence sharding looks
unwired". Half right, and the half that is wrong matters for how PR-D is worded.

There is no `apply_cp` function, but CP IS wired, inline in the main entry
(parallelize.py:140-205). Both `KimiMLAAttention` and `KimiDeltaAttention` get
`_cp_group` set and each has a `._forward_cp`. The MLA branch even validates
`num_heads % (tp * cp) == 0`, so it is designed for TP x CP composition.

What it is: **Ulysses** -- head-dimension sharding with one fused differentiable
all-to-all on the cp sub-mesh, each rank running conv/scan/SDPA on its head
subset over the FULL sequence.

What it is not: ring/zigzag SEQUENCE sharding. The code says why -- KDA cannot
ring because fla-core's scan is sequential, and the custom MLA inner_attention is
not the torchtitan SDPA type `apply_cp_to_forward` dispatches on.

So "CP support" is real and measured (cp2 passes across the matrix; KCP conv halo
is bit-exact at cp2/4/8), but PR-D must say Ulysses head-parallelism, not
sequence parallelism. Claiming the latter would be the overclaim the plan is
right to guard against.
