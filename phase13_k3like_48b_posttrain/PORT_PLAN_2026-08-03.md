# Porting plan: gate first, then four parallelism PRs

## Step 0 (gate): alpha math parity. NOT PASSED -- and there is nothing to pass it with

Our `block_attn_res` was written before 2026-07-27 from the report, not from the
release. Its formula:

    V = stack(blocks + [partial_block])        # [N+1, B, T, D]
    K = RMSNorm(V)
    logits = einsum("d,nbtd->nbt", proj.weight, K)
    weights = softmax(logits, dim=0)           # over the block axis
    h = einsum("nbt,nbtd->btd", weights, V)

Three properties of the official `_apply_attention_residual` are absent here:

1. **FP32 compute.** Ours runs in the stream dtype -- `K = K.to(V.dtype)` and
   `query = query.to(K.dtype)` explicitly cast DOWN to bf16 to match FSDP mixed
   precision. If the release computes alpha in FP32, ours is not just less
   precise, it is a different operator.
2. **kimi_eps normalisation.** Ours uses `nn.RMSNorm`'s default eps from the
   model config. A release-specific epsilon would change the keys.
3. **residual entries concatenated with a prefix_sum.** Ours stacks
   `blocks + [partial_block]` -- the completed block representations plus the
   current partial. A prefix-sum formulation is a different quantity, not a
   different spelling of the same one.

**There is no parity test in the folder.** `ls tests/ | grep -iE
"parity|fixture|ref"` returns nothing, so this has never been checked against
anything. That is the honest state: the alpha operator is unverified against the
release, and every parallelism result we have is a result about OUR operator.

What this does not invalidate: the adapter's transport and gradient topology --
which stage owns which block, how blocks cross a boundary, how gradients route
back -- is independent of what alpha computes. That is why the plan's ordering is
right, and why swapping the operator later does not redo the PP work.

Action: obtain the frozen fixtures, diff the two formulas, and if they differ the
official one wins. Only the alpha operator changes; the adapter does not.

## Correction on the CP gap

The plan says "parallelize.py has no apply_cp, so MLA sequence sharding looks
unwired". Half right, and the half that is wrong matters for how PR-D is worded.

There is no `apply_cp` function, but CP IS wired, inline in the main entry
(parallelize.py:140-205). Both `KimiMLAAttention` and `KimiDeltaAttention` get
`_cp_group` set and each has a `._forward_cp`. The MLA branch even validates
`num_heads % (tp * cp) == 0`, so it is designed for TP x CP composition.

What it is: **Ulysses** -- head-dimension sharding with one fused differentiable
all-to-all on the cp sub-mesh, each rank running conv/scan/SDPA on its head
subset over the FULL sequence.

What it is not: ring/zigzag SEQUENCE sharding. The code says why -- KDA cannot
ring because fla-core's scan is sequential, and the custom MLA inner_attention is
not the torchtitan SDPA type `apply_cp_to_forward` dispatches on.

So "CP support" is real and measured (cp2 passes across the matrix; KCP conv halo
is bit-exact at cp2/4/8), but PR-D must say Ulysses head-parallelism, not
sequence parallelism. Claiming the latter would be the overclaim the plan is
right to guard against.
