## MTP on the new tree (`fa5117ac2`, 2026-09-06)

Ported from `k3_mtp` (`mtp.py` and its build tests verbatim; `__init__.py`, `model.py`,
`config_registry.py`, `sharding.py` re-seated). Adapted to this tree: the mirror layer joins the
tensor-parallel sharding walk (spmd_types consumes every declaration, so it is declared at tp=1
too; `eh_proj` and the mirror `ffn_res_proj` read the TP-invariant stream and take the stream-param
placement, `I`, where the old tree's `R` would sum identical gradients under TP); the mirror KDA's
flops are counted; the MTP layers register after the vision encoder so a model without MTP draws
the same init stream. Guards raise on chunked loss, on a pipeline stage without both embedding and
head, on sequence parallel and on context parallel (the depth-shifted slice indexes tokens on a
stream those shard by position). No HF mapping for the MTP weights (the released config ships none).

Bar: `kimi_k3_debugmodel_mtp --loss.mtp_weight 0.0`, dp1, step 1 = **12.41967**, bitwise the
`kimi_k3_debugmodel` dp1 row of the mm18 protocol (same data, seed 42; plain CE and chunked CE agree
at the printed precision): the MTP layer leaves the backbone's forward and init untouched.

mm18 protocol (4096 tokens per step, 256 per micro-batch, seed 42, 3 measured steps), composite loss
= main CE + 0.3 x depth-1 CE (`matrix_scripts/mtp_smoke.sh`):

## verl engine, reconciled with upstream's LoRA sync (2026-09-06, `5a6ce58a`)

- Upstream `#7327` / `#7376` resolve `.base_layer` on the vLLM receiver (`resolve_weight_name`,
  per name, against the live namespace, on released and newer vLLM alike). Our trainer-side
  `_insert_base_layer_suffix` was the pre-`#7327` answer to the same KeyError; it is dropped and
  the base half ships plain HF names. Kept: the warning that names a wrapped projection whose
  base key is absent (PP rank, graft-only target).

  the adapter-only mode (`model.lora.merge=False`), which has no delta protocol. One
  `_lora_mode()` decides adapter vs merged for both paths.
