## 4. The migration plan, in full

Quoted from `ALIGN_TO_4025_2026-08-13.md`, which is the document to read first.

### Why realign at all

Fetched `JavaZeroo/torchtitan agent/add-kimi-k3-reference-model` at `1da44c16a`, based on
upstream `5de7d1150` -- inside the window we just merged, so it is current.

| | theirs | ours |
|---|---|---|
| `model.py` | 805 lines | 2,300+ |
| `parallelize.py` | **100 lines** | 1,400+ |
| `parallelize_module` / `use_local_output` | **0 / 0** | 3 / 28 |
| nested `Config` classes | **9** | 0 |
| base classes | `Module`, `FeedForward`, `BaseAttention`, `GroupedExperts`, `Decoder` | `nn.Module` |

Their `parallelize.py` calls `apply_fsdp_to_decoder` and `apply_fsdp_to_vision_encoder` and
nothing else; all TP is declared on the Config tree. **They already wrote the shape the
declarative migration was converging on.** If their PR lands while our hand-built model is
mid-migration, we inherit a conflict on every file at once.

### AttnRes: the carrier is the difference

| | theirs | ours |
|---|---|---|
| block history | `block_residual_TND`, one `[T, N, D]` tensor threaded through every block's signature | a Python `list` |
| running sum | `prefix_sum_BLD`, returned in the tuple | `partial_block` |
| gate stream | -- | `plain_stream` |
| commit | `torch.cat` at `layer_id % attn_res_block_size == 0` | `blocks.append(...)` |

Three Python-level accumulators versus two tensors in the forward signature. That is
exactly the wall the declarative migration hit: `ffn_out` became a DTensor while
`partial_block` and `plain_stream` stayed plain, and **no `sharding_config` can reach a
value the model code holds in a list.**

Their block also carries a measured note worth keeping: returning `None` instead of routing
the residual back out "reassociates the residual's gradient accumulation and perturbs
`tok_embeddings.weight.grad` by ~2e-3 relative".

### Per-axis impact

| axis | theirs | what happens to ours |
|---|---|---|
| TP | declarative, complete | mostly replaced; what remains is the LoRA / packed-MXFP4 section they have no equivalent for |
| EP | `KimiGroupedExperts`, `KimiLatentMoE` | smallest change -- ours already goes through upstream's `set_moe_sharding_config` |
| CP | **none** | logic kept, re-attached to their attention modules |
| PP | **none** | **adapter kept**, its cache re-targeted at the new carrier |

**The PP adapter is not redundant.** `N` grows monotonically with depth, so shipping the
carrier through each stage boundary costs `[T, N, D]` per hop -- about 0.88 GiB per
microbatch on the last hop at 2.8T dims, times the microbatches in flight under `pp x vp`.
The rank-local cache plus a `recv_delta` is what makes the per-hop cost constant. An
earlier draft said the threaded carrier might remove the need for it; that was wrong.

### Rules for the migration

1. **Nothing is deleted before its replacement passes the matrix.** New alongside old,
   verify, then remove.
2. **One axis per branch.**
3. **The criterion is the three-arm matrix, not "it runs".**
4. **`attention_residual_dev` stays at the last all-green state.**

### Steps

0. **Freeze** -- done, `108e55f4b` plus the baseline tables.
1. **Vendor their model unmodified** -- DONE. `torchtitan/models/kimi_k3_up/`, registered as
   a parallel module, trains on 2 GPUs: `12.40271 -> 12.15932 -> 11.10994`. The gap on the
   base model is zero: their code needs nothing from us.
2. **Port our flavors onto their Config registry.** They ship one `debugmodel`; we need
   `debugmodel_report_arch`, `mini`, `2p8t`, and the LoRA/QLoRA variants. Gate: the text
   arm's cells train.
3. **Re-attach the increments in dependency order**: CP (attaches to attention modules,
   no interaction with the AttnRes carrier), then LoRA/MXFP4 (attaches to Linear leaves),
   then DEP, then PP.
4. **PP last.** Keep the adapter; re-target its cache at columns of `block_residual_TND`
   instead of elements of a Python list.
5. **Verification at every step**: three arms, `compare_to_dev_baseline.py`, criterion
   no BROKE. Byte-identity is NOT available -- their model is a different implementation.

## 5. Open items, with the next concrete action

## 6. PR hygiene, learned the hard way today

A maintainer replied to the grad-norm PR: *"sorry I couldn't really understand the PR
summary which seems to be written by AI. Before vs. after this change, what ops that are
used to performed in bf16 are not performed in fp32?"*

He is right, and the question he had to ask has a two-line answer the body never gave:
the per-tensor norms (`torch._foreach_norm`) and the norm-of-norms (the `vector_norm` over
the stacked result). `Raising_PRs/PR_WRITING_RULES.md` now holds the rules -- a body answers
what changes, why it is wrong today, the evidence, and what does not change, then stops --
with that PR as the worked bad example and a ten-line rewrite.

**Commit messages must not contain PR numbers of any kind.** Use a description or the
commit hash.

## 7. Method notes that paid for themselves

* **Instrument instead of guessing.** `probe_declaration_conflicts.py` listed all 79
  declaration conflicts with module names in one run; each preceding guess advanced one
  layer. Same for `--debug.detect-anomaly`, which located the vision-CP backward failure
  immediately.
* **Prove the tree under test contains the change.** Results described the wrong tree three
  times today: `run_maxdeg.sh` hard-coded `TITAN`, edits landed in one worktree while
  `PYTHONPATH` pointed at another, and five cells "matched byte-identically" because they
  were the same tree.
* **Extract a cell's parameters from the matrix script, never hand-write them.** Six 8-GPU
  runs were spent on a "deadlock" that was `--training.local-batch-size 2`, a flag the
  matrix passes only to PP cells.
* **One GPU job at a time.** `pgrep` before launching; note that `pgrep -f torchtitan.train`
  matches the launching shell itself.
