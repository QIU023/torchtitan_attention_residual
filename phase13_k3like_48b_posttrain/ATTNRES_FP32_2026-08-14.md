# The AttnRes precision defect: found, fixed, and what the fix cannot explain

## What was wrong

`block_attn_res` normalized the stacked block values in the stream dtype and cast to fp32
afterwards:

```python
K = norm(V)      # variance, rsqrt and the norm weight multiply, all in bf16
K = K.float()
```

The release's `_apply_attn_res` floats the values FIRST, so the whole of alpha -- variance
included -- is fp32. Our own comment in the file said so and the code did not do it.

This is not a rounding nicety. `proj` is zero-initialized, so the block softmax starts
uniform and the pseudo-query gradient is a difference of nearly equal terms; 6x to 15x
cancellation was measured on this model. bf16 is exactly where that costs.

The half of this that was already fixed on 2026-08-03 removed a cast DOWN after the norm.
It left the norm itself in the stream dtype, which is the remaining half.

## The fix

```python
K = norm(V.float())
```

One token. The `norm(...)` call is preserved as a module call because that is what
all-gathers `proj.weight` under FSDP2 -- `proj.weight` is read directly, never through
`proj.forward`, and the two share an FSDP param group.

## Evidence

Both implementations are in the tree, so this is a direct comparison on identical inputs
(`matrix_scripts/attnres_parity.py`). Relative error against the vendored reference:

| dtype | before | after |
|---|---|---|
| float32 | 1.3e-07 | 1.3e-07 |
| bfloat16 | **1.9e-03** | **0.0** |

The probe had to be strengthened first: it used a unit norm weight, which makes the
query-folding difference between the two forms vacuous, so that arm was untested and the
"before" number was measured against nothing. It now uses a random weight and keeps the
pre-fix form inline so the regression cannot return silently.

## The text arm: I attributed this wrongly, and the control caught it

The text arm drifts ~1e-2 against `verify_post_merge/`. I attributed that to migration
step A rather than to this change, on this reasoning:

* `kimi_k3_mini_block_attn_res` sets `training.dtype = float32`, where `V.float()` is the
  identity;
* run old and new through forward and backward on fp32 inputs and every gradient is
  bitwise identical;
* so the change cannot move a float32 arm.

The attribution control settles it the other way. Dev head -- step A present, this fix
absent -- is **byte-identical to the baseline**:

    baseline (merge tree):     7.70979 7.66901 7.57535 7.42618 7.18265 6.79439 6.01403 5.35497 5.21788 4.81907
    dev head (step A, no fix): 7.70979 7.66901 7.57535 7.42618 7.18265 6.79439 6.01403 5.35497 5.21788 4.81907
    with this fix:             7.70979 7.66831 7.57164 7.42718 7.18487 6.79681 6.02037 5.35490 5.21851 4.81946

Step A moves nothing. The drift is this change.

### Why the fp32 reasoning was wrong

`training.dtype` is not the dtype the residual stream runs in.
`ParallelismConfig.mixed_precision_param` defaults to **`bfloat16`** independently, so FSDP2
casts parameters to bf16 whatever `training.dtype` says, every linear emits bf16, and the
tensors reaching `block_attn_res` are bf16 -- in the "float32" arm.

The unit test was correct and irrelevant: it measured the dtype the config names, not the
dtype the path runs. That is the same error as using a control arm without checking what it
shares, one level down -- here the two things assumed identical were a config field and a
runtime dtype.

The gradient table stands on its own terms, and now reads as a prediction of the text arm
rather than an exclusion of it:

| dtype | proj.weight.grad | norm.weight.grad | block grads |
|---|---|---|---|
| float32 | identical | identical | identical |
| bfloat16 | 2.5e-01 | 3.9e-03 | 2.9e-03 |

So all four arms are bf16 in the place that matters, all four move, and the fix is doing
in the text arm exactly what it does in the multimodal ones.

## Text arm, for the record
