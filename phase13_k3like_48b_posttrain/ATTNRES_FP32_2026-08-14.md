# The AttnRes precision defect: found, fixed, and what the fix cannot explain

## What was wrong

`block_attn_res` normalized the stacked block values in the stream dtype and cast to fp32
afterwards:

```python
K = norm(V)      # variance, rsqrt and the norm weight multiply, all in bf16
K = K.float()
```

The release's `_apply_attn_res` floats the values FIRST, so the whole of alpha -- variance
included -- is fp32. Our own comment in the file said so and the code did not do it.

This is not a rounding nicety. `proj` is zero-initialized, so the block softmax starts
uniform and the pseudo-query gradient is a difference of nearly equal terms; 6x to 15x
cancellation was measured on this model. bf16 is exactly where that costs.

The half of this that was already fixed on 2026-08-03 removed a cast DOWN after the norm.
It left the norm itself in the stream dtype, which is the remaining half.

## The fix

```python
K = norm(V.float())
```

One token. The `norm(...)` call is preserved as a module call because that is what
all-gathers `proj.weight` under FSDP2 -- `proj.weight` is read directly, never through
`proj.forward`, and the two share an FSDP param group.

## Evidence

Both implementations are in the tree, so this is a direct comparison on identical inputs
(`matrix_scripts/attnres_parity.py`). Relative error against the vendored reference:

| dtype | before | after |
|---|---|---|
| float32 | 1.3e-07 | 1.3e-07 |
| bfloat16 | **1.9e-03** | **0.0** |

The probe had to be strengthened first: it used a unit norm weight, which makes the
query-folding difference between the two forms vacuous, so that arm was untested and the
"before" number was measured against nothing. It now uses a random weight and keeps the
pre-fix form inline so the regression cannot return silently.

## What the fix does NOT explain, and how that was settled

The text arm drifts ~1e-2 against `verify_post_merge/` after this change, which the
mechanical comparator reports as BROKE. It is not this change:

* `kimi_k3_mini_block_attn_res` trains in **float32**, where `V.float()` is the identity;
* step 1 is **bit-identical in every text cell**, so the forward did not move;
* run old and new through forward AND backward on fp32 inputs and every gradient --
  `proj.weight`, `norm.weight`, all four block inputs -- is **bitwise identical**.

| dtype | proj.weight.grad | norm.weight.grad | block grads |
|---|---|---|---|
| float32 | identical | identical | identical |
| bfloat16 | 2.5e-01 | 3.9e-03 | 2.9e-03 |

The bf16 row is the point of the fix: the pseudo-query gradient is the quantity with the
cancellation, and it is the one that moves most.

What is left between the baseline tree (`tt_merge` at the merge commit) and the tested tree
is **migration step A**, whose byte-identity was verified on the multimodal arm only --
`tp2`, `fsdp2_tp2_cp2` and `ep2_fsdp2_tp2_cp2`, none of them a text cell. The attribution
control runs the same three text cells on dev head (step A present, this fix absent) and on
the merge tree (neither), which separates the two.

Recorded because the shape recurs: a mechanical comparator says BROKE, and the first
instinct is to look at the change under test. The cheaper question was which of the two
trees actually differ, and by what.

## Multimodal arm: the fix takes effect, and step 1 proves the mechanism

`kimi_k3_debugmodel_report_arch` trains in bfloat16, so this is the arm where the change
is supposed to do something.

| | baseline | after |
|---|---|---|
| cells training 10/10 | 13 / 13 | **13 / 13** |
| step 1 | -- | **bit-identical in every cell** |
| steps 2-10 | -- | drift up to 4.0e-02 |

The step-1 result is not a null result, it is the mechanism. `proj` is zero-initialized, so
at step 1 the block softmax is exactly uniform whatever precision computes it -- there is
nothing for bf16 to lose. Precision only starts to matter once `proj` has taken a gradient
step, which is precisely the claim the fix rests on: the defect is in the pseudo-query's
GRADIENT, not in the forward.

### On the comparator's verdict

`compare_to_dev_baseline.py` reports FAIL, because its criterion is a 1e-4 drift
threshold. That is the criterion for a REFACTOR, where numbers must not move. This is a
deliberate computation change, so the criterion is the one the migration doc gives for
that case:

* every cell that trained still trains -- 13/13, unchanged;
* the drift is bounded and mechanistically explained -- 4e-2 at step 10 on a loss of ~9.9,
  i.e. 0.4%, entering at step 2 exactly where the theory says it should;
* the set of passing cells is identical.

Read as a refactor gate it fails; read as what it is, it passes. Both readings are worth
writing down, because a mechanical FAIL is easy to either ignore or over-trust.

## Text arm, for the record

3 cells fail on fla's SM120 shared-memory ceiling (`dp1`, `pp2`, `tp2`) -- the same three
as in the baseline, unrelated to any of this. The other 10 train 10/10.
