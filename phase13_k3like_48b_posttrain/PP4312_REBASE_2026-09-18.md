# PR 4312's head rebased onto torchtitan main a3a819c67 (2026-09-18)

## What was rebased, and the correction that got there

The first attempt rebased `pp_review5`, on the understanding that it was the PP PR's head. It is not. `de6f29514` is the head of PR 4312, confirmed by fetching `refs/pull/4312/head` fresh and getting the same object; it is also the tip of `origin/k3_pp_text` and `origin/pp_review4`. `pp_review5` branched off the 2026-09-04 main three days earlier and is 101 commits behind that head, and every identifier its 23 commits carry is already on the head at equal or greater spread (`PPRankLocalCache`, `layer_to_stage_from_split`, `self.first_layer_in_block`, `first_stage_modules`, the config exclusivity message, `AttnResPipelineStage`). `pp_review6` sits on the PR's own line, twelve commits behind it. So the first replay was done on a superseded sibling and is discarded.

The real job replays 37 commits from merge base `d9ca9e55a` onto `a3a819c67`, with 62 upstream commits in between. `git merge-tree` predicted five conflicting files, exactly the set the 4312 follow-up note recorded. Result: `ab8ea5f61`, 37 commits, 16 files, +1525/-34.

## How each conflict was decided

Every resolution was taken from the commit's own diff rather than from the shape of the conflict, because the conflicts are mostly diff alignment: git pairs a line the commit deletes against an unrelated neighbour. Five conflicts turned out to carry old-base text that upstream has since dropped, and taking "our" side wholesale would have reinstated it:

    ("tensor parallel", tp_enabled)      upstream supports K3 TP now; the commit only deletes the pipeline entry
    TODO: Add TP Support                 zero occurrences on upstream/main and on the integration tree
    from .moe import KimiFeedForward...  upstream narrowed that import to KimiLatentMoE
    spmd_backend validation              the field is gone from ParallelismConfig; it appeared three times
    from torchtitan.tools.logging        the module moved to torchtitan.observability.logging

Each was checked against upstream, against the integration tree, and against the commit's own added lines before being dropped. Two resolutions needed a positive fix rather than a choice: `parallelize.py` gets `import logging` plus `logger = logging.getLogger(__name__)` in place of the moved module, and the `__all__` in `pipeline_parallel.py` keeps upstream's logger assignment while taking the commit's widening.

## The gate that made this checkable

Every replayed commit was compared against the original commit's own per-file numstat. Thirty-three files matched exactly. Four differed and each was traced line by line before being accepted:

    commit 6   model.py +34/-21 against +32/-20   upstream's one-line docstring reopens as multi-line
    commit 13  model.py +0/-4 against +0/-5       a blank line inside the docstring, see below
    commit 19  pipeline_parallel.py +35/-2        an import line upstream already had, merged away
    commit 32  parallelize.py +92/-11             one blank line between import groups

A harness refuses to stage anything unless the resolver exits zero, no file keeps a real conflict marker, and every modified file parses. That gate exists because an earlier run committed three conflict-marker lines into five commits: the resolver raised, the shell carried on, and `git add` staged the unresolved file. The audit also resolves every `from torchtitan...` import against the commit's own tree, which `ast.parse` cannot do; a package directory with no `__init__.py` counts as resolvable, since `torchtitan.tools` is a namespace package.
