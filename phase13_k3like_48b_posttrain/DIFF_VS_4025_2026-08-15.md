# What still differs from the upstream K3 tree, enumerated

Written so that aligning after their PR merges is a checklist rather than a
rediscovery. Measured by diffing `Config` field names class by class between
`torchtitan/models/kimi_k3/` (ours) and the pristine vendored
`torchtitan/models/kimi_k3_up/` (theirs, byte identical to what upstream shipped).

**We are deliberately not aligning the names yet.** Their PR is under review with
many maintainer comments, and everything in the "rename" bucket below is exactly
what review comments move: field names, and which class owns which field. Doing
it now risks doing it two or three times. What we did instead -- making our
construction config-driven -- is independent of their final naming, and is the
part that unlocks a per-model `sharding.py`.

## Bucket 1: pure renames (mechanical, do after merge)

| theirs | ours |
| --- | --- |
| `dim` | `hidden_size` |
| `wq_a` / `wq_b` | `q_a_proj` / `q_b_proj` |
| `wkv_a` / `wkv_b` | `kv_a_proj_with_mqa` / `kv_b_proj` |
| `wo` | `o_proj` (MLA) |
| `q_norm` / `kv_norm` | `q_a_layernorm` / `kv_a_layernorm` |
| `gate` (MLA) | `attn_gate_proj` |
| `head_dim` / `num_heads` (KDA) | `kda_head_dim` / `kda_num_heads` |
| `conv_kernel_size` | `kda_short_conv_kernel_size` |
| `forget_a` / `forget_b` | `f_a_proj` / `f_b_proj` |
| `beta` (KDA) | `b_proj` |
| `output_gate` / `output_proj` | `g_proj` / `o_proj` |
| `beta` / `linear_beta` (SiTU) | `situ_beta` / `situ_linear_beta` |
| `attention_norm` / `ffn_norm` | `input_layernorm` / `post_attention_layernorm` |
| `layer_id` | `layer_idx` |

Ours follow the released checkpoint's spelling; theirs follow titan's internal
convention. Theirs is the more idiomatic one, which is why the three attribute
renames we already did (AttnRes projections, `attention`/`delta_attention`,
`moe`/`feed_forward`) were worth doing before this decision -- those were
attribute names on the module tree, which the state-dict adapters map, not config
field names still under review.

## Bucket 2: class boundaries (real work, decide after merge)

* They put the four AttnRes modules (`attention_res_norm`/`proj`,
  `ffn_res_norm`/`proj`) and `attn_res_block_size` on the transformer block
  itself; we put them on a `KimiAttnResDecoderLayer` subclass. Aligning means
  folding the subclass back into the block.
* They put `vision_encoder`, `output_res_norm`/`output_res_proj` and
  `spatial_merge_size` on the model trunk; ours live on
  `KimiK3MultimodalModel` and `KimiK3AttnResModel`.
* Our trunk config still carries `kimi_config`, the flat config, because
  `register_topology(model.config)` and `init_weights`' `initializer_range` read
  it after construction. Theirs has no flat config at all.

## Bucket 3: kept on purpose, with evidence (not to be aligned)

* **KDA's convolutions and gated norm.** They use core's `Conv1d` and their own
  plain-PyTorch `KimiRMSNormGated`; we use fla's `ShortConvolution` and
  `FusedRMSNormGated`. Theirs are declarable and need no shim, which is a real
  advantage on their side, but swapping a fused Triton kernel for eager code on
  every KDA layer's critical path is a performance regression.
* **The MoE's internals.** Theirs is flat (`router`, `routed_experts`,
  `token_dispatcher`, `routed_down`/`up`/`norm`); ours composes core's `MoE` as
  `_moe`. That composition IS our expert-parallel support: `apply_ep` is 16 lines
  calling `_moe.parallelize(parallel_dims)`. Their class has no EP path and their
  parallelize refuses EP, and core's declarative EP needs the
  `routed_experts.inner_experts` / `routed_experts.token_dispatcher` nesting that
  their config flattens -- so their shape cannot reach core's EP machinery at all.
* **The grouped experts' GEMM seam.** Ours calls `self._grouped_mm`; theirs calls
  `torch._grouped_mm` directly, which bypasses the seam the MXFP8 converter
  overrides.

## Not a 4025 difference, but a report difference

The tech report's sec 5.2.3 schedules the ViT's forward and backward passes into
1F1B pipeline bubbles; we place the tower on dedicated stages instead. That is a
fidelity gap against the report rather than a difference from their tree, and it is
written up separately in `VIT_BUBBLE_SCHEDULING_GAP_2026-08-15.md`, together with
the measurement that makes it matter: the tower is 0.12% of a pipeline stage's
parameters, so spending a stage on it buys a 15% text-side imbalance.

## What is worth doing before any merge

Becoming an idiomatic torchtitan model, which is independent of their review:
every other model (llama3 74 lines, qwen3 111, gpt_oss 127, kimi_k2_7 145,
deepseek_v3 192, qwen3_5 343) carries a per-model `sharding.py` and has zero
imperative `ColwiseParallel`/`RowwiseParallel` entries, while ours has 1598 lines
of `parallelize.py` with ten. The config-driven conversion just done is the
precondition: `KimiK3Model.Config` now carries `tok_embeddings`, `norm` and
`lm_head`, the three fields core's `set_decoder_sharding_config` writes to, and
`layers` for the model's own loop.
