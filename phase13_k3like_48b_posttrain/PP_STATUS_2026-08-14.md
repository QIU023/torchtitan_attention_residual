| piece | evidence |

The 6 missing cells were fla's shared-memory ceiling, not this work -- see the dtype fix

## Memory side: not started

`N` grows monotonically with depth, so shipping the carrier through each stage boundary
costs `[T, N, D]` per hop: about 0.88 GiB per microbatch on the last hop at 2.8T dims,
times the microbatches in flight under `pp x vp`. The rank-local cache plus a `recv_delta`
is what makes the per-hop cost constant. That is the remaining PP work and it sits ON TOP
of the correctness above, not instead of it.

## The text flavor's six dead cells, fixed

`training.dtype` was `float32`. It reaches the model itself, while `mixed_precision_param`
only reaches parameters through FSDP -- so every layout WITHOUT FSDP or CP ran KDA on fp32
operands, and this GPU allows 101376 bytes of dynamic shared memory per block where that
kernel asks for 108160. `dp1`, `pp2`, `tp2` and maxdeg `pp4`, `pp8`, `tp4` died where
`fsdp2` and `cp2` passed.

The multimodal twin fixed this the same way when it was written. The text flavor was left
on the default, and the six FAILs were then carried in every report as "pre-existing,
unrelated". Both true, and also: they made 54/54 unreachable by construction and trained
every reader to skip six FAILs. Set to `bfloat16`.

## What I got wrong on this step, since it shaped the work

* **Predicted the risk surface as the PP cells and the adapter's column semantics.** It was
  neither -- the smoke died before any cell and the adapter needed no rethink.
* **Read one kind-mixing error three times from the source**, each reading self-consistent
  and wrong, before running the probe that answers it in one go: input plain, weight
  `DTensor(S(0))`, the model loop bypassing `nn.Module.__call__` so FSDP never unsharded.
  Recorded in `HOW_I_GET_THIS_WRONG`.
* **Called option (2) the largest of three without measuring it.** Twelve mechanical lines;
  1571 was the file's length, not its exposure. That nearly steered the choice to option
  (3), which would have had to be redone.
* **Set a self-contradictory gate.** "Pure container change, no licence to move a digit" --
  but the container IS the memory layout, so bitwise and "adopt the upstream layout" cannot
  both hold. The single-GPU equivalence probe proved arithmetic equivalence at one shape,
  which I read as distributed bitwise.
* **Repeated "the matrix takes 2.5 hours"** with no document behind it. Measured: 40
  minutes. That figure changes whether a change is worth a full gate, and I had been
  reasoning with the wrong one.

## CORRECTION: the adapter is implemented but OFF in every matrix arm

I wrote "memory side: not started". Wrong. `CrossStageCacheAdapter` is 1571 lines and
complete -- `RankLocalCache`, delta mode, `_LocalCacheCapture`, the producer-side grad
hooks. What is true is that `attn_res_cache=False` in all three matrix flavors, so
`adapter_enabled()` returns False and the adapter runs as a naive passthrough.

So the carrier does travel whole through every hop in the runs we have been grading, and
memory does grow with depth **in that configuration** -- but not because the fix is missing.

The serious part is not the wording. **The twelve lines I changed are all inside the
delta path**, which is the branch `adapter_enabled()` gates:

* `_return_only_new_blocks` and the new-blocks return
* `recv_delta_tensor` and its unstacking
* per-block column indexing in `RankLocalCache`

**No matrix cell executes any of it.** The 8 PP cells passing proves the naive path is
correct under the new carrier and says nothing about the delta path. I was about to
write "54/54, PP migration verified" on that basis.

`attn_res_cache`'s comment says "opt-in until we trust it", and the trust has been
accumulating from a matrix that never enters it. Same shape as the six SM120 cells: a
criterion that looks like it covers something and does not.

**Rule: before crediting a matrix for a change, check that some cell actually executes the
changed branch.** A config gate is enough to make a green table meaningless, and it will
not announce itself.

Queued: the four PP cells with `TORCHTITAN_ATTNRES_CACHE=1` -- `pp2`, `fsdp2_tp2_pp2`,
`tp2_pp2_cp2`, `ep2_fsdp2_tp2_pp2`. That is the run that tests what was changed, and the
risk surface I originally predicted (the adapter's column semantics) has simply not been
tested yet rather than having been cleared.

## Coverage, stated as combinations rather than as a cell count

54/54 is a count, and a count hides which BRANCHES ran. Written out:

| combination | status |
|---|---|
| naive carrier x DEP x dynamic CP (both multimodal arms) | **54/54** |
| delta path, no DEP | **4/4 bitwise equal to naive** |
| delta path x DEP x dynamic CP | **4/4 bitwise equal** |
| delta path x DEP x dynamic CP x LoRA | **4/4 bitwise equal** |

Every delta-path cell is bitwise identical to the naive path on the same harness -- twelve
of twelve, none of them merely close. The densest is
`ep2_fsdp2_tp2_pp2` on the LoRA flavor: LoRA x EP x TP x PP x DEP x dynamic CP with the
cache on, equal to the same cell with the cache off.

So the twelve changed lines are clean and the cache is what it claims to be, a memory
optimisation with no arithmetic of its own. That could not be concluded from 54/54, which
never entered the branch.

The gap exists because `run_cells.sh` did not export the arm knobs the gate exports, so
the four delta-path cells ran with DEP and dynamic CP OFF while every 54-cell multimodal
row had them ON. The adapter has DEP-specific wiring (`_install_vision_stage_wiring`,
`_dep_vision_share_index`), so that intersection is real code, not a formality.

The same harness mismatch is what briefly made the delta path look defective: the same tree
gave 12.04691 under `run_cells` and 12.07827 under the gate. Fixed there; the coverage hole
it created is separate and is what this section tracks.

**A cell count is not a coverage statement.** 54/54 was true and simultaneously left two
combinations untested, one of them because a config gate (`attn_res_cache`) defaults off
and one because a harness dropped two environment variables.
