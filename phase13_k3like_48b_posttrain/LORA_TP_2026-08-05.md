# LoRA under TP: what the constrained measurement says, and one hypothesis refuted

Previous sessions produced two "findings" here that were the same measurement
error twice: comparing values that are SUPPOSED to differ per rank. So this round
is built as a constraint rather than as a search --
`lora_tp_replicate_probe.py` refuses to compare anything whose TP-axis placement
is not `Replicate`, and now also records WHY each parameter was excluded, because
absence from a disagreement list otherwise reads as "clean" when it can mean
"never compared".

Run on the dense diagnostic flavor (`kimi_k3_mini_diag_4l_mla_lora`) at tp2:
MoE top-k is a discrete choice, so on a MoE model a cross-rank comparison
measures route divergence instead of correctness.

## The control, which decides whether LoRA is involved at all

| run | Replicate-on-TP grads checked | disagreeing |
|---|---|---|
| LoRA **off** (`kimi_k3_mini_diag_4l_mla`) | 40 | **0** |
| LoRA **on** (`..._lora`) | 26 | 11 |

Same probe, same code path, same seed. **LoRA is the trigger**, and the AttnRes
projections are not independently broken -- which matters beyond LoRA, because it
means the TP legs of the published parallelism matrices are not implicated.

## The previous framing was an artifact of what got compared

Recorded before: "`q_a_proj.lora_b`'s gradient is identical across ranks on layer
0 and differs on layers 1, 2, 3", read as a defect localized to layers 1-3.

With the exclusion reasons dumped, layer 0 shows only

    layers.0.self_attn.q_a_proj.base.weight    no_grad

and no `lora_a` / `lora_b` entry at all. Layer 0 has **no `q_a_proj` adapter**, so
it was never compared. It is not clean; it is absent. (Nor does
`q_a_proj.lora_a` exist in *any* layer, unlike every other target, which have
both -- worth its own look.)

The accurate statement is stronger and simpler. Of the 68 LoRA parameters in this
model, exactly **three are Replicate on the TP axis -- the three
`q_a_proj.lora_b` -- and all three disagree.** 64 are Shard or Partial and are
correctly outside this test's scope. So the failure rate among LoRA gradients this
test can judge is 3 of 3, not "3 of many".

The other 8 disagreements are the AttnRes projections (`attn_res_proj`,
`mlp_res_proj`, `final_attn_res_proj`), which stay full-param trainable under
base-freeze by the alpha-fullparam exception, are Replicate, and sit downstream.
Note `layers.0.mlp_res_proj` disagrees at 5.16e-02 against a reference magnitude
of 4.58e-02 -- over 100% relative, and the earliest disagreement in the network.

## Hypothesis tested and refuted: a Partial intermediate

`parallelize.py` distributes a Rowwise-styled adapter as `lora_a = Shard(1)`,
`lora_b = Replicate()`. In `KimiLoRALinear.forward` the adapter is then

    lora_out = F.linear(F.linear(x, la), lb)

With `x` sharded on the contracted axis and `la` sharded on dim 1, the inner
result is **Partial**. Matmul is linear in it, so DTensor may legally carry the
Partial through the second matmul and reduce once at the end -- the forward is
right either way. The proposed defect: `lora_b`'s gradient is
`grad_out^T @ inter`, so each rank builds its own term of the sum and the result
comes out labelled `Replicate` while holding a partial value, with nothing
downstream reducing it because the label says there is nothing to reduce.

Tested by forcing the intermediate to `Replicate` before the second matmul.
**Refuted:** the three `q_a_proj.lora_b` deltas came back bit-identical
(4.262e-04, 1.951e-04, 1.627e-04), so that branch never fires for `q_a_proj` --
its intermediate is not Partial. The change also relabelled other adapters'
gradients from excluded to `Replicate`, exposing `o_proj.lora_b` and
`down_proj.lora_b` as disagreeing too, taking the count from 11 to 19. So it made
the measurement broader and the model no better. Reverted; not committed.

What that rules out: the Rowwise `lora_a`/`lora_b` composition inside `forward`
is not where `q_a_proj`'s gradient goes wrong.

## Next measurement, again as a constraint

`q_a_proj`'s adapter has no `lora_a`, which means it is not the ordinary
two-matrix adapter the forward assumes. Establish what it actually is before
theorising about its gradient: dump the module type, the parameter set, and every
placement for `layers.1.self_attn.q_a_proj`, and find out why layer 0's differs
from layers 1-3's at all when the four layers are structurally identical.

Compare only `Replicate`-on-TP values. Never compare plain per-rank or
Shard-placed locals.
