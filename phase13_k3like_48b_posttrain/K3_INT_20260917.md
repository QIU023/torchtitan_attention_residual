### `allgather_kv`: the cause, and a correction of my own reading

The 09-17 line closed with the cause open after the thread hypothesis was withdrawn. It is not open any more, and nothing new had to be run: both probe logs were already on disk.

`torch._dynamo` prints the sentence in the failure only under one condition. `eval_frame.py` branches on whether the `fullgraph=True` call collected any skip reasons: with reasons it lists them, and with none it appends "Compilation was not attempted and no cached compiled code was found". That second form is what the failure carries, so dynamo had nothing to report as skipped, which rules out the reading that some earlier call had poisoned the frame.

The second probe log says what happened instead. At 15:38:01 it prints `torch._dynamo hit config.recompile_limit (8)` for frame `[0/8]`, and that run dies as `FailOnRecompileLimitHit` at `_attention.py:1304`, the same `compiled_create_block_mask(...)` call the first probe failed on. The defaults here are `recompile_limit` 8 and `accumulated_recompile_limit` 256. Three wrappers compile the same `create_block_mask` code object with different settings: `torchtitan/models/common/attention.py:604` and `models/common/vision_encoder.py:35` wrap it as a plain `torch.compile`, and torch's context-parallel path wraps it with `dynamic=False, fullgraph=True`. Once the code object exhausts its recompile budget dynamo stops compiling that frame and the `fullgraph=True` call reports exactly what it finds. The two probe runs are the cause and the consequence of one thing.

It also explains the runs that did not fail, which the thread story never did: the seven `allgather_kv` cells under plain torchrun and the fresh wrapper the probe builds both reach that code object after far fewer distinct shapes.

The cached-wrapper reading from 09-17 is retired. `_compiled_create_block_mask` has exactly one writer in the entire environment, `_create_cp_block_mask` itself, so no foreign call can fill it first and it was never the asymmetry that was measured.

One correction of my own, recorded because it nearly became a second false lead. Reading the first probe's stack through `cut -c1-165` truncated the frame numbers, turning 1167 into 116 and 1304 into 130, and those numbers point at unrelated code in the installed file. #### Why the limit did not hold, from torch's source

`torch/utils/_config_module.py` backs every config value with a `ContextVar`. `__setattr__` calls `config.user_override.set(value)` and `__getattr__` calls `.get()`, and the comment above those declarations says it plainly: config values are per-thread via `ContextVar`. So a write does not leave the context that made it.

Measured in one interpreter, with no GPU: setting `recompile_limit` to 64 on a worker thread reads 64 on that thread and 8 on the main thread, and the same is true from an asyncio thread. A second measurement on one event loop makes it sharper, and the sharpening matters: a `ContextVar` is per context and each asyncio task runs in a copy of its creator's, so 64 set inside task A reads 64 there, 8 in task B and 8 on the loop thread, while 32 set on the loop thread is inherited by a task created after it. Picking the right thread is therefore not sufficient by itself; the write has to happen before the task exists, which is what makes interpreter startup the only comfortable place for it. The engine hook runs on Ray's asyncio actor thread, which the older `DYNAMO-PROBE` lines already recorded as `thread=AsyncIO Thread: default main=False`. It raised the limit in a context dynamo's check never reads, which is exactly what the log shows: a truthful banner and a check that still sees 8.

Two things follow. The `allgather_kv` account is untouched and keeps its standing, the best explanation of the measurements with no direct test behind it. And the first approach was right in principle after all: a `sitecustomize` runs at interpreter startup on the main thread, before any thread or task split, so its value would be the one dynamo reads. What it never did was load inside the WorkerDict actors, and Ray's `worker_process_setup_hook` is the supported way to make that happen.

Worth naming, since it is the shape of three failures in a row tonight: each time the mechanism was reachable in principle and the delivery was wrong, and each time the run looked like it had taken effect. The banner was the worst of the three, because it was true.


#### What the delivery route has to satisfy, read out of Ray and OmegaConf

Two obstacles were checked rather than assumed, and only one of them is real.

Ray 2.58.0 takes `worker_process_setup_hook` in the runtime env and runs it in `default_worker.py` at process startup, on the main thread and before any actor task, which is the only point whose value a later compile check can inherit. A hook given as a string goes through `load_and_execute_setup_hook_module`, which calls `load_class` inside the worker, so the module has to be importable there; Ray's own error text says as much. A hook given as a callable is exported through the function manager instead and needs no import path, but a Hydra command line cannot express a callable, so the string form is the one worth testing.

The struct worry was unfounded. verl's comment at `main_ppo.py:67` warns that `ray_init.runtime_env` is a struct DictConfig and that adding an `env_vars` key to it raises, which reads like any new key would. Loading `ppo_trainer.yaml` and checking directly, `OmegaConf.is_struct` on that node is None and assigning `worker_process_setup_hook` succeeds, so the command line can carry it. The warning applies to the merged object in that one code path, not to the node a CLI override lands on.

So the open question narrowed to one thing that costs seconds rather than a cell: whether a module on `PYTHONPATH` is importable inside a Ray actor on this box, given that a `sitecustomize` on the same path never loaded in the WorkerDict actors.

#### The setup-hook route is dead, and it took seconds to find out

    SYNC-ACTOR:  {'thread': 'MainThread', 'limit': 64}
    ASYNC-ACTOR: {'thread': 'AsyncIO Thread: default', 'main_thread': False,
                  'limit_in_async_method': 8, 'limit_in_nested_task': 8}

The hook sets 64 on the worker's main thread. A synchronous actor method, which runs on that same thread, reads 64. An async actor method runs on a separate thread Ray names `AsyncIO Thread: default` and reads 8, and so does a task created inside it.

That thread name is the one the older `DYNAMO-PROBE` lines already carried, `thread=AsyncIO Thread: default main=False`, so this is exactly the shape verl's colocated worker runs in. A `ContextVar` starts empty in a new thread, so a value set on the main thread cannot reach it. The route is closed, and closing it cost one script rather than another cell.

One thing is still unaccounted for, and it is worth stating rather than smoothing over: the engine hook ran on that same asyncio thread and set 64 there, and the check still read 8. Per-thread isolation does not explain that on its own. The remaining candidate is that the recompile check does not run on the thread executing the frame. Whether it does is a matter of reading where `exceeds_recompile_limit` is called from, not of running anything.

Until that is answered, item 5 stands where it has stood all evening: the behavioural sentence is the only thing the PR body carries, and the recompile-budget account remains the best explanation of every measurement with no direct test behind it. Three cells and four injection attempts have not moved that, and the next step is reading, not launching.


#### The last candidate is dead, and what is left is my own diagnostic

`exceeds_recompile_limit` in `torch/_dynamo/cache_size.py` reads `config.recompile_limit` inline, inside `_compile`, which the eval-frame callback drives on the thread executing the frame. Inductor's `compile_threads` is 32 with `worker_start_method` set to subprocess, so those are processes doing backend codegen and not the thread taking this decision, and these cells ran with `TORCHINDUCTOR_COMPILE_THREADS=1` regardless. So the check does run where the frame runs, and the idea that it reads the config from some other thread is finished.

That leaves one explanation standing, and it is a defect in the probe rather than anything in torch. `_raise_recompile_limit_once` carries a module-level `_RECOMPILE_LIMIT_RAISED` flag and sets the value once per process. Ray's async actor runs each method invocation as its own task, and a `ContextVar` write inside a task is invisible to the next one. So the first call into `prepare_model_inputs` wrote 64 into that task's context and flipped the flag, and every later call skipped the write and read the default 8. The banner was printed by the one call that did set it, which is why it was both truthful and useless.

The fix is one line, dropping the once guard so the value is set on every call, in the context that is about to use it. It is not worth a cell tonight: item 5 blocks nothing, the PR body sentence has been settled since the start of the evening, and the account of the `allgather_kv` failure itself is unchanged either way. Recorded so the next session starts from a one-line edit rather than from four injection attempts.
