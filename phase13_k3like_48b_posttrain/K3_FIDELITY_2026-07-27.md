# K3 fidelity pass, part 2 (2026-07-27, after the release artifacts)

Continues `K3_RECONCILIATION_2026-07-27.md`. That document reconciled the
*architecture* against the report and config. This one records what happened
when the reconciled architecture was actually exercised: three features turned
out to be inert, and one recorded result turned out to be measuring nothing.

Every claim below has a test or a probe behind it, named inline.

## 1. Three features that existed, passed their unit tests, and did nothing

The same shape recurred three times, which is why it gets its own section.

| feature | why it was inert | how it failed silently |
| --- | --- | --- |
| routed-expert init | `init_weights` dispatched on `type(m).__name__ == "GroupedExperts"` and initialized `("w1","w2","w3")`; upstream renamed the params to `w1_EFD`/`w2_EDF`/`w3_EFD` and K3's experts became a subclass | model trains on the dense + shared + latent path; loss curve looks fine |
| Per-Head Muon | driven by a `_muon_heads` attribute that only two *test files* ever set | falls back to full-matrix Newton-Schulz, a valid optimizer |
| MXFP4 QAT scope | targeted MLA and dense/shared-FFN Linears -- nearly the *complement* of K3's routed-experts-only scope | quantizes real layers, so it looks like it is working |

The lesson is narrower than "add tests": all three HAD passing unit tests. What
was missing in each case was a test that the feature affects the *model*, not
that the function computes the right thing in isolation. The three checks that
would have caught them, and are now in place:

* zero the routed experts and assert the loss moves
  (`test_expert_init.py::test_routed_experts_affect_the_output`)
* assert a per-head update differs from a full-matrix one, and that a
  `per_head=True` group with nothing tagged *warns*
  (`test_muon.py::TestPerHeadMuonTagging`)
* assert no `nn.Linear` is in the quantization scope and that MXFP4 changes the
  expert output (`test_quant_scope.py`)

The routed-expert case invalidated recorded numbers; see
`EVIDENCE_INVALIDATION_2026-07-27.md`.

## 2. A result that read as a pass and was not

The first MXFP4-QAT A/B showed base and QAT losses *bit-identical* (7.71445),
which is the vacuous-A/B signature already recorded for FlashKDA. Chasing it
found the expert-init bug. But an earlier offline comparison had shown QAT
changing the loss while the base did not, which looked like confirmation that
QAT worked. It was not: MX-quantizing an all-zero tensor yields garbage rather
than zeros, because the block scale derives from `amax = 0`. The fake-quant was
accidentally *supplying* the weights init had skipped.

With live experts the A/B is genuine, k3mini dp2 seed 42:

    base 7.75113 / 7.68023 / 7.59077      QAT 7.72159 / 7.65503 / 7.55739

Both directions of a vacuous A/B are now on record: "no difference" (FlashKDA,
the verifier had silently rejected the fast path) and "a difference" (this one).
Neither is informative without a control proving the harness can separate the
arms.

## 3. Fidelity gaps closed against the release

**Routed experts were SwiGLU.** `hidden_act: "situ"` is global in the released
config, and `situ_and_mul` was wired into `KimiMLP` (dense FFN, shared experts)
but not into the routed experts, which inherit core `GroupedExperts` and its
hardcoded `F.silu`. Those experts are the overwhelming majority of the model.
`KimiSiTUGroupedExperts` subclasses `GroupedExperts` the way
`GptOssGroupedExperts` does for its clamped SwiGLU -- same `w1_EFD`/`w2_EDF`/
`w3_EFD` parameters, so the state-dict adapter, the expert TP/EP layout and the
torchao MX/Float8 expert converters keep working untouched.

A detail that first made the test vacuous: **SiTU is a soft-clipped SiLU**.
`beta*tanh(g/beta)*sigmoid(g) -> g*sigmoid(g)` as `g/beta -> 0`, and the two
agree to under 3% for `|g| <= 1`. So a SwiGLU-vs-SiTU control needs
pre-activations past `beta = 4` or it proves nothing. That is also the reason
SiTU can replace SiLU without retuning the init scale.

**Quantization scope was inverted.** The released `quantization_config` targets
`["Linear"]` but ignores `self_attn`, `shared_experts`, the dense FFN,
`lm_head`, `vision_tower` and `mm_projector`; report sec 4.1.4 states the intent
directly. The scope is the routed experts only -- which are not `nn.Linear` at
all. `quant_scope.py` is now the single definition, holding the official
regexes verbatim so a diff against a future checkpoint is mechanical, and the
predicate is positive rather than "not ignored" so an unclassified module
defaults to high precision.

**LoRA missed most of the K3 module set.** `DEFAULT_LORA_TARGETS` predated the
release: on the K3 structure it adapted 75 of 139 eligible Linears, skipping the
entire compressed-Q path (`q_a_proj`/`q_b_proj`), the Gated MLA output gate and
the latent MoE projections.

**MoonViT-V2 was a placeholder.** Now implemented against `vision_config`. Two
inferences worth flagging as such:

* `qkv_hidden_size` (1536) is *wider* than `vt_hidden_size` (1024), so
  head_dim = 128 and the output projection contracts 1536 -> 1024.
* The report's "roughly 0.4B parameters" and "attention is factorized into
  intra-frame spatial and inter-frame temporal passes" reconcile only if the two
  passes **share** one qkv/out projection set: measured **401.2M** shared vs
  **571.1M** unshared. Asserted with the counterfactual in
  `test_moonvit.py::test_parameter_count_matches_the_reported_0p4b`.

## 4. Quantile Balancing: connected, and three things the equation does not say

QB was implemented and unit-tested but never wired to a run. It now goes on via
`post_optimizer_build_fn`; the cutoff `alpha` is recomputed in a router forward
hook from the raw `scores_BLE` the router already returns, so no core change is
needed. Histogram counts are additive, so one all-reduce over the loss mesh
pools the whole global batch.

Measured on a deliberately skewed n=16 / k=2 / m=4096 router, iterating to the
fixed point and reading the load coefficient of variation from 0.607:

| estimator | plateau |
| --- | --- |
| exact quantile | 0.053 after 60 updates, still descending |
| histogram, 256 bins | 0.160 |
| histogram, 512 bins | 0.147 |
| histogram, 2048 bins | 0.104 |
| histogram, 8192 bins | 0.092 |

1. **Interpolating inside the crossing bin is essential, not a refinement.**
   Snapping to the bin's left edge restricts the bias to a lattice, making the
   update map piecewise constant: the iteration locks at cv 0.232 and never
   moves again.
2. **A single update does not land on balance.** "Solves for the bias" describes
   the per-step subproblem; the trajectory is a fixed-point iteration, because
   applying the bias moves every token's cutoff.
3. **The margin distribution has an atom at exactly 0.** `alpha_i` is itself one
   of the scores, so `s_ij - alpha_i` is exactly 0 whenever expert j is token
   i's (k+1)-th -- 419 of 4096 tokens for the most over-subscribed expert. That
   is why Eq. 14's count identity holds only up to ties. Handling the atom
   explicitly made the plateau *worse* (0.154 vs 0.147) and is not carried;
   dropping those boundary tokens entirely did help (0.118), but that is a
   departure from the published rule, so it is recorded rather than adopted.

## 5. Verified, not assumed

Two things that looked like problems and were checked rather than waved through.

**MLA is exactly latent-space MQA.** Because `mla_use_nope` skips RoPE, `W_UK`
transposes onto the query, so the attention can run over the 512-dim latent plus
the 64 head-shared rot channels -- 576 values per token per layer instead of 96
x 320 decompressed, a 53x cache difference. Measured rel < 1e-10 in float64
against our own forward, gated and ungated, with and without q-compression
(`test_mla_latent_absorption.py`). We keep training in the decompressed form
(fewer FLOPs at long T); the test exists so a change that silently breaks
absorbability fails here instead of in a serving stack.

**FSDP2's "did not run forward before backward" warning on
`final_attn_res_proj` is benign.** `block_attn_res` reads `proj.weight` directly
instead of calling `proj(...)`, so no pre-forward hook fires. Pairing proj with
`final_attn_res_norm` in ONE param group is what makes it correct: norm IS
called one line earlier and triggers the shared group's all-gather. Verified on
both ranks at dp2 under the real `apply_fsdp` -- full `[1, D]` plain tensor,
gradient finite (`attnres_fsdp_tail_probe.py`). This makes the statement order
inside `block_attn_res` load-bearing, now noted at the hazard site.

One caveat from that probe worth keeping: a *hand-rolled* `fully_shard` of the
same module groups produced a nan gradient under bf16 compute while fp32 stayed
finite. The real `apply_fsdp` path is clean, so it is an artifact of the
approximation -- but it means such a probe must call `apply_fsdp`, because an
ad-hoc wrapping does not reproduce the trainer here.

## 6. Still open

* KCP: the short-conv halo gate (`causal_conv1d_cp`) and then integration
  (varlen vs fixed-length batches, `output_final_state` unsupported under CP),
  keeping Ulysses as the A/B.
* Migrate `init_weights` to upstream's declarative per-parameter init map
  (`deepseek_v3/__init__.py::_depth_experts_init`), which would also supply the
  depth-scaled std our pass lacks. A hand-maintained exhaustive walk is what
  broke in sec 1.
* MXFP8 activations for the QLoRA path (QAT has them; the packing path is
  weights-only, matching the released checkpoint's `input_activations: null`).
* Wire the vision tower into `multimodal_model.py`, whose projector is still the
  generic 2-layer MLP rather than `PatchMergerV2`.
