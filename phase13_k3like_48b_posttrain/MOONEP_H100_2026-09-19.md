# MoonEP on the 4 x H100 box, 2026-09-19

Box `115.124.123.240:16923`, replacing every earlier address. 4 x H100 80GB HBM3, SM90, 192 cores, 2.2 TB RAM, 307 GB free.

## The gate the earlier H100 box failed

`nvidia-smi topo -m` reads NV18 between every pair and `nvidia-smi -q` reports Fabric State Completed, Status Success, so this is an NVSwitch fabric. All four devices report `CU_DEVICE_ATTRIBUTE_MULTICAST_SUPPORTED = 1`, read from the driver through `libcuda` after torch 2.11's `_SymmetricMemory.has_multicast_support` refused both argument forms tried.

That is the condition the 2026-09-15 box at `103.60.105.169` failed: four H100s on NV6 direct links, Fabric State N/A, multicast 0, and MoonEP asserts multicast in its buffers. So MoonEP can run here and could not run there.

## Toolchain, and why it is cu126 rather than the box's own 12.8

nvcc is 12.8, driver 560.35.03, and `/venv/main` carries torch 2.15 era wheels at cu128. That pairing cannot be used: the nightly index has no 2.15 build for cu128 (its newest cu128 is 2.12.0.dev20260408), and building `moonep._C` needs an nvcc matching torch's CUDA, which is what stopped the 09-15 box. cu126 has 2.15.0.dev20260905 through 20260907, and `cuda-toolkit-12-6` installs from the NVIDIA apt source already configured here, so the H200 recipe's pairing is reproduced exactly: toolkit 12.6 plus `torch==2.15.0.dev20260907+cu126`. The driver admits CUDA 12.8, so 12.6 needs no forward compatibility. Only `cuda-toolkit-12-6` is installed, never the `cuda` metapackage, which would pull `cuda-drivers` over the host driver.

The test's `parallel_dims` double returned `None` for every query, so it had been exercising the copied formula and nothing else; it now returns an axis sized the way core sizes it.

## The comment budget, measured against #4577 with one ruler

The audit asked for a trim pass on the grounds that comment plus docstring was 15.3 percent of the added lines against #4577's 4.3. Both numbers turned out to be measured differently from each other, so neither could settle anything.

Measured with a single classifier over production files only, excluding the BSD headers every new file carries and counting docstring delimiter lines the same way on both sides: this branch is 569 code, 20 comment, 34 docstring, which is 8.7 percent, and #4577 at `01dd6ddb8` is 224 code, 3 comment, 9 docstring, which is 5.1 percent. So the gap is real but smaller than either published figure suggested, and the 4.3 in the repo guide is not reproducible against that commit with this ruler.

What did not happen is cutting to the number. Read against the rule, which allows a comment for a non-obvious invariant and forbids one that narrates the next line, the comments here are almost all of the first kind: the shape-suffix legend, the `[in, out]` rows against the grouped-mm seam's `[row, out, in]`, `launch_grad_reduce` addressing rows by global expert id, the kernel fencing peers after its reads so the writes still need a fence of their own. Deleting those to reach 5.1 percent would remove what a reviewer of a foreign transport most needs. One comment did narrate its next line and is gone.

The docstrings are already one-liners except two module headers and one class, which the same rule permits.

## The box cannot run MoonEP's kernels as installed

Cell 1, MoonEP's own suites, fails on every test with `cudaErrorInsufficientDriver`, error code 35, raised inside cutlass DSL's own CUDA runtime check at `cudaGetDeviceCount`. torch sees all four GPUs from the same interpreter, so the driver is fine for torch's cu126 runtime; something in the cutlass path asks for more than the 560.35.03 driver admits, which tops out at CUDA 12.8. Every CUDA runtime package in the venv is cu12 at 12.6, with one exception that stands out, `nvidia-cuda-nvdisasm` at 13.4.92, so a CUDA 13 component came in as a dependency of something.

It is `cuda-python`. cutlass-dsl 4.6.0 pulls `cuda-python 13.4.1` with `cuda-bindings 13.4.2`, and those bindings report a runtime of 13040 against a driver of 12080, so their `cudaGetDeviceCount` returns error 35 while torch, carrying its own cu126 runtime, counts four devices in the same interpreter. Pinning `cuda-python<13` and `cuda-bindings<13` brings 12.9.7 and 12.9.8, after which the same call returns success and four devices, and cutlass 4.6.0 still imports. A 12.9 runtime on a 12.8 driver is fine; a 13.4 one is not.

The H200 recipe does not mention this because that box runs driver 595.58.03, which admits CUDA 13, so the dependency never surfaced. The recipe is therefore driver-dependent in a way it does not say, and the pin is now written into this box's `env.sh` next to the reason for it.


## Cell 1, and two silent failures on the way to it

The first pass read 18 passed and 1 skipped on planning, 12 on dispatch, 14 on combine and 14 on prefetch, with `test_e2e` and `test_grad_reduce` failing on `module 'cutlass.cute' has no attribute 'make_fragment'`. That is the pair the notes say fails on cutlass-dsl 4.6.0, and the one-line rename is supposed to be the answer, so the interesting part is why it was not in effect.

The setup script applied it as `git apply <patch> && echo CUTLASS46_PATCH_OK`, and the marker never appeared. The patch's paths carry no `moonep/` prefix, so `git apply` run from the repository root reports `grad_reduce.py: No such file or directory` and exits, and the `&&` simply skipped the confirmation instead of stopping. The same shape as the other gates that did not gate: a failure that leaves no trace unless something asserts on it.

The rename itself is one occurrence, `cute.make_fragment(` at `grad_reduce.py:295`. A blind substitution would also have caught `cute.make_fragment_like(`, which is a different function; there are none in this tree, but the replacement was written to match the open parenthesis so that it could not.

The local flavor was checked the same way, twice. Asking whether the string `moonep` appears in `repr(model_spec)` answered False, which looked like the flavor had not taken. Comparing the two specs instead shows the base spec carrying only `TokenDispatcher` and the moonep one carrying `MoonEP`, with the two differing. The first answer was a weak check, not a finding.

## Cell 5 passes, and the seed step had to be rewritten for current main

The forced-hot probe is the first of the training-side cells to land, on two ranks:

    rank 0/2  routing=hot  slots=[-1 x16]        rows_in_slots=0
    rank 1/2  routing=hot  slots=[1, 0, -1...]   rows_in_slots=1024
    HOT_PROBE_RESULT  slot_populated_somewhere=True  numerics_ok_all_ranks=True

Every token is sent to the experts homed on one rank, and the other rank's prefetch slots take 1024 rows while the loaded rank's stay empty. That is the balance claim, and the numerics hold on both ranks.

The matrix then aborted every cell with `SEED-COPY-FAIL`, which is the backend refusing to run cells without a seed checkpoint rather than comparing runs that started from different weights. The seed step itself had failed with `Unrecognized options: --checkpoint.create_seed_checkpoint`.

That option is gone by design. `create_seed_checkpoint` is a Trainer field carrying `tyro.conf.Suppress`, so it is deliberately not on the CLI, and `tests/unit_tests/cpu/test_no_new_cli_options.py` lists it among the fields that must stay off. The change came in with `ec953b36`, one of the nine commits between the branch's old base and current main, so the older runners were written against a CLI that no longer exists.

The repo's own answer is `scripts/_checkpoint_test_config.py`, which its comparison scripts use: `configure_checkpoint` writes a temporary registry module that loads the base config and sets the field, and returns the module and config names to pass instead. The seed step now goes through a small driver that calls it and runs the training as its own child, since the temporary module lives in a directory owned by the calling process. One run produces `checkpoint/step-0/__0_0.distcp` and `.metadata` and logs `Created seed checkpoint`.


## The cells needed the same rewrite as the seed

With the seed building, the matrix moved from `SEED-COPY-FAIL` to `ASSERT-SEED-FAIL`, which is the backend's other guard: the cell ran but its log never said `Loading the checkpoint from`, so the numbers would have come from freshly initialised weights rather than the shared seed. The cause is the same change: `Unrecognized options: --checkpoint.enable, --checkpoint.interval`. The whole `checkpoint.*` group is off the CLI on current main, which is what `_checkpoint_test_config.py` says in its own docstring, that its callers need to configure checkpointing for arbitrary registry configs without exposing the optional checkpointer through the training CLI.

So the cell command goes through the same helper with `mode="load"`, which enables the checkpointer and marks it load-only: read the staged seed, write nothing back. That is what a measured cell wants anyway.

Worth naming as a pattern rather than two separate fixes. The runners in the kit were written against `a3a819c67` and the branch now sits on `003beaabb`; the nine commits between them include a refactor that moved checkpointing off the CLI entirely. Anything in the kit that speaks to the trainer through flags is suspect until it has been run once, and the two guards that caught this, the seed-file count and the load assertion, are the reason the failure showed up as an abort rather than as a table of plausible numbers taken from unseeded runs.
