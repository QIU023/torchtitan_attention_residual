# MoonEP on the 4 x H100 box, 2026-09-19

Box `115.124.123.240:16923`, replacing every earlier address. 4 x H100 80GB HBM3, SM90, 192 cores, 2.2 TB RAM, 307 GB free.

## The gate the earlier H100 box failed

`nvidia-smi topo -m` reads NV18 between every pair and `nvidia-smi -q` reports Fabric State Completed, Status Success, so this is an NVSwitch fabric. All four devices report `CU_DEVICE_ATTRIBUTE_MULTICAST_SUPPORTED = 1`, read from the driver through `libcuda` after torch 2.11's `_SymmetricMemory.has_multicast_support` refused both argument forms tried.

That is the condition the 2026-09-15 box at `103.60.105.169` failed: four H100s on NV6 direct links, Fabric State N/A, multicast 0, and MoonEP asserts multicast in its buffers. So MoonEP can run here and could not run there.

## Toolchain, and why it is cu126 rather than the box's own 12.8

nvcc is 12.8, driver 560.35.03, and `/venv/main` carries torch 2.15 era wheels at cu128. That pairing cannot be used: the nightly index has no 2.15 build for cu128 (its newest cu128 is 2.12.0.dev20260408), and building `moonep._C` needs an nvcc matching torch's CUDA, which is what stopped the 09-15 box. cu126 has 2.15.0.dev20260905 through 20260907, and `cuda-toolkit-12-6` installs from the NVIDIA apt source already configured here, so the H200 recipe's pairing is reproduced exactly: toolkit 12.6 plus `torch==2.15.0.dev20260907+cu126`. The driver admits CUDA 12.8, so 12.6 needs no forward compatibility. Only `cuda-toolkit-12-6` is installed, never the `cuda` metapackage, which would pull `cuda-drivers` over the host driver.
