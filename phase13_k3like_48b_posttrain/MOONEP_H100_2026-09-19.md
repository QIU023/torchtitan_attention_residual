# MoonEP on the 4 x H100 box, 2026-09-19

Box `115.124.123.240:16923`, replacing every earlier address. 4 x H100 80GB HBM3, SM90, 192 cores, 2.2 TB RAM, 307 GB free.

## The gate the earlier H100 box failed

`nvidia-smi topo -m` reads NV18 between every pair and `nvidia-smi -q` reports Fabric State Completed, Status Success, so this is an NVSwitch fabric. All four devices report `CU_DEVICE_ATTRIBUTE_MULTICAST_SUPPORTED = 1`, read from the driver through `libcuda` after torch 2.11's `_SymmetricMemory.has_multicast_support` refused both argument forms tried.

That is the condition the 2026-09-15 box at `103.60.105.169` failed: four H100s on NV6 direct links, Fabric State N/A, multicast 0, and MoonEP asserts multicast in its buffers. So MoonEP can run here and could not run there.

## Toolchain, and why it is cu126 rather than the box's own 12.8

nvcc is 12.8, driver 560.35.03, and `/venv/main` carries torch 2.15 era wheels at cu128. That pairing cannot be used: the nightly index has no 2.15 build for cu128 (its newest cu128 is 2.12.0.dev20260408), and building `moonep._C` needs an nvcc matching torch's CUDA, which is what stopped the 09-15 box. cu126 has 2.15.0.dev20260905 through 20260907, and `cuda-toolkit-12-6` installs from the NVIDIA apt source already configured here, so the H200 recipe's pairing is reproduced exactly: toolkit 12.6 plus `torch==2.15.0.dev20260907+cu126`. The driver admits CUDA 12.8, so 12.6 needs no forward compatibility. Only `cuda-toolkit-12-6` is installed, never the `cuda` metapackage, which would pull `cuda-drivers` over the host driver.

## CPU side, done while the toolchain installed

The branch rebased onto current main `003beaabb` with no conflict, eight commits, and the per-file diff after the rebase is identical to the one before it, so main's nine commits touch nothing this branch touches.

Two of the audit's items turned out to be stale, and one of them was wrong as written.

`check_moonep_mesh` already asked core for the `efsdp` axis; what it also did was recompute `dp_shard * cp * tp // ep` when the query returned nothing. Removing that fallback, which is what the audit asks for read literally, breaks every supported configuration: `get_optional_mesh` hides an axis of size 1 and the check requires exactly `efsdp == 1`, so the query returns `None` on the path that is meant to pass. Asking with `include_singleton_axes=True` leaves one source for the degree and keeps the refusals. The test's `parallel_dims` double returned `None` for every query, so it had been exercising the copied formula and nothing else; it now returns an axis sized the way core sizes it.

The comment and docstring share of the added lines is 9.5 percent, not the 15.3 percent the audit recorded: the branch's fifth commit already cut once. 

The CPU test surface is 198 lines instead of 638. The 316-line in-process double existed to drive the dispatcher, the prefetch slots and the slot-grad reduction without the package, and the on-device test added at `84f2704ce` makes the same comparison against a dense reference with the real package on two GPUs, so it was a second assertion of the first one. What is left needs neither package nor device: what the spec selects, the import guard's message, and the mesh precondition.

Two commits, `822642a22` and `446a86225`, no trailers. **Not pushed.** `k3_moonep_seam` backs PR 4751, and the standing rule is that a branch behind a published PR is never pushed to directly, while the other standing rule is that no new branch is created unasked. ## The comment budget, measured against #4577 with one ruler

The audit asked for a trim pass on the grounds that comment plus docstring was 15.3 percent of the added lines against #4577's 4.3. Both numbers turned out to be measured differently from each other, so neither could settle anything.

Measured with a single classifier over production files only, excluding the BSD headers every new file carries and counting docstring delimiter lines the same way on both sides: this branch is 569 code, 20 comment, 34 docstring, which is 8.7 percent, and #4577 at `01dd6ddb8` is 224 code, 3 comment, 9 docstring, which is 5.1 percent. So the gap is real but smaller than either published figure suggested, and the 4.3 in the repo guide is not reproducible against that commit with this ruler.

What did not happen is cutting to the number. Read against the rule, which allows a comment for a non-obvious invariant and forbids one that narrates the next line, the comments here are almost all of the first kind: the shape-suffix legend, the `[in, out]` rows against the grouped-mm seam's `[row, out, in]`, `launch_grad_reduce` addressing rows by global expert id, the kernel fencing peers after its reads so the writes still need a fence of their own. Deleting those to reach 5.1 percent would remove what a reviewer of a foreign transport most needs. One comment did narrate its next line and is gone.

The docstrings are already one-liners except two module headers and one class, which the same rule permits.
