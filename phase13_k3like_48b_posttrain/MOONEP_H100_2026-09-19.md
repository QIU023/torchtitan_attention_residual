# MoonEP on the 4 x H100 box, 2026-09-19

Box `115.124.123.240:16923`, replacing every earlier address. 4 x H100 80GB HBM3, SM90, 192 cores, 2.2 TB RAM, 307 GB free.

## The gate the earlier H100 box failed

`nvidia-smi topo -m` reads NV18 between every pair and `nvidia-smi -q` reports Fabric State Completed, Status Success, so this is an NVSwitch fabric. All four devices report `CU_DEVICE_ATTRIBUTE_MULTICAST_SUPPORTED = 1`, read from the driver through `libcuda` after torch 2.11's `_SymmetricMemory.has_multicast_support` refused both argument forms tried.

That is the condition the 2026-09-15 box at `103.60.105.169` failed: four H100s on NV6 direct links, Fabric State N/A, multicast 0, and MoonEP asserts multicast in its buffers. So MoonEP can run here and could not run there.

## Toolchain, and why it is cu126 rather than the box's own 12.8

nvcc is 12.8, driver 560.35.03, and `/venv/main` carries torch 2.15 era wheels at cu128. That pairing cannot be used: the nightly index has no 2.15 build for cu128 (its newest cu128 is 2.12.0.dev20260408), and building `moonep._C` needs an nvcc matching torch's CUDA, which is what stopped the 09-15 box. cu126 has 2.15.0.dev20260905 through 20260907, and `cuda-toolkit-12-6` installs from the NVIDIA apt source already configured here, so the H200 recipe's pairing is reproduced exactly: toolkit 12.6 plus `torch==2.15.0.dev20260907+cu126`. The driver admits CUDA 12.8, so 12.6 needs no forward compatibility. Only `cuda-toolkit-12-6` is installed, never the `cuda` metapackage, which would pull `cuda-drivers` over the host driver.

## The box cannot run MoonEP's kernels as installed

Cell 1, MoonEP's own suites, fails on every test with `cudaErrorInsufficientDriver`, error code 35, raised inside cutlass DSL's own CUDA runtime check at `cudaGetDeviceCount`. torch sees all four GPUs from the same interpreter, so the driver is fine for torch's cu126 runtime; something in the cutlass path asks for more than the 560.35.03 driver admits, which tops out at CUDA 12.8. Every CUDA runtime package in the venv is cu12 at 12.6, with one exception that stands out, `nvidia-cuda-nvdisasm` at 13.4.92, so a CUDA 13 component came in as a dependency of something.

It is `cuda-python`. cutlass-dsl 4.6.0 pulls `cuda-python 13.4.1` with `cuda-bindings 13.4.2`, and those bindings report a runtime of 13040 against a driver of 12080, so their `cudaGetDeviceCount` returns error 35 while torch, carrying its own cu126 runtime, counts four devices in the same interpreter. Pinning `cuda-python<13` and `cuda-bindings<13` brings 12.9.7 and 12.9.8, after which the same call returns success and four devices, and cutlass 4.6.0 still imports. A 12.9 runtime on a 12.8 driver is fine; a 13.4 one is not.

The H200 recipe does not mention this because that box runs driver 595.58.03, which admits CUDA 13, so the dependency never surfaced. The recipe is therefore driver-dependent in a way it does not say, and the pin is now written into this box's `env.sh` next to the reason for it.

## Cell 5 passes, and the seed step had to be rewritten for current main

The forced-hot probe is the first of the training-side cells to land, on two ranks:

    rank 0/2  routing=hot  slots=[-1 x16]        rows_in_slots=0
    rank 1/2  routing=hot  slots=[1, 0, -1...]   rows_in_slots=1024
    HOT_PROBE_RESULT  slot_populated_somewhere=True  numerics_ok_all_ranks=True

Every token is sent to the experts homed on one rank, and the other rank's prefetch slots take 1024 rows while the loaded rank's stay empty. That is the balance claim, and the numerics hold on both ranks.

The matrix then aborted every cell with `SEED-COPY-FAIL`, which is the backend refusing to run cells without a seed checkpoint rather than comparing runs that started from different weights. The seed step itself had failed with `Unrecognized options: --checkpoint.create_seed_checkpoint`.

That option is gone by design. `create_seed_checkpoint` is a Trainer field carrying `tyro.conf.Suppress`, so it is deliberately not on the CLI, and `tests/unit_tests/cpu/test_no_new_cli_options.py` lists it among the fields that must stay off. The change came in with `ec953b36`, one of the nine commits between the branch's old base and current main, so the older runners were written against a CLI that no longer exists.

The repo's own answer is `scripts/_checkpoint_test_config.py`, which its comparison scripts use: `configure_checkpoint` writes a temporary registry module that loads the base config and sets the field, and returns the module and config names to pass instead. The seed step now goes through a small driver that calls it and runs the training as its own child, since the temporary module lives in a directory owned by the calling process. One run produces `checkpoint/step-0/__0_0.distcp` and `.metadata` and logs `Created seed checkpoint`.


## The cells needed the same rewrite as the seed

With the seed building, the matrix moved from `SEED-COPY-FAIL` to `ASSERT-SEED-FAIL`, which is the backend's other guard: the cell ran but its log never said `Loading the checkpoint from`, so the numbers would have come from freshly initialised weights rather than the shared seed. The cause is the same change: `Unrecognized options: --checkpoint.enable, --checkpoint.interval`. The whole `checkpoint.*` group is off the CLI on current main, which is what `_checkpoint_test_config.py` says in its own docstring, that its callers need to configure checkpointing for arbitrary registry configs without exposing the optional checkpointer through the training CLI.

So the cell command goes through the same helper with `mode="load"`, which enables the checkpointer and marks it load-only: read the staged seed, write nothing back. That is what a measured cell wants anyway.

Worth naming as a pattern rather than two separate fixes. The runners in the kit were written against `a3a819c67` and the branch now sits on `003beaabb`; the nine commits between them include a refactor that moved checkpointing off the CLI entirely. Anything in the kit that speaks to the trainer through flags is suspect until it has been run once, and the two guards that caught this, the seed-file count and the load assertion, are the reason the failure showed up as an abort rather than as a table of plausible numbers taken from unseeded runs.

## Correction: the grad probe was stale in five ways, not one

The row above first read "Trainer has no such attribute; build loads instead". The second half of that was wrong, and I wrote it without checking: I deleted the `trainer.checkpointer.load(...)` line, assumed `config.build()` loaded the checkpoint because the runner now passes `mode="load"`, and reran. The rerun failed, and the check that caught it was one the runner already had: `Loading the checkpoint from` appeared **zero** times in the probe log. A guess about where a load happens is exactly the kind of claim that guard exists to refuse.

What is actually true is that the probe's whole post-build body was written against an older `Trainer`. Five separate things, all of them silent until executed:

    engine.load_checkpoint()                    the load lives on the engine and is called by train(), not by build()
    trainer.microbatch_generator(...)           batch_generator was renamed
    engine.device / parallel_dims / optimizers  these moved from Trainer to TrainingEngine
    engine.model_parts[0]                       same move
    engine.forward_backward_microbatch(...)     forward_backward_step no longer exists anywhere in the tree

Fixing them one error at a time would have cost five runs of a job that copies a 4.2 GB checkpoint three times, so the rewrite went the other way: read `Trainer.train` and `Trainer.train_step` in full first, then write the probe as a copy of `train_step` truncated before `engine.optimizer_step()`. That also makes the probe honest by construction, since its gradients are now produced by the same call the training loop uses, over the same microbatch count and the same token normalisation, rather than by a hand-assembled forward that resembles it.

One thing was added rather than ported: the probe now also reports the step loss, computed the way `train_step` computes the logged one. That gives the run its own gate. The probe's loss has to reproduce the matrix cell's step-1 loss (12.54318 for `dp4ep4_std`, 12.56253 for `dp4ep4_moonep`) before any gradient it dumps is worth reading; if it does not, the probe is starting from different weights or different data and its per-parameter numbers describe nothing.

The general shape is the same one the four-place section ends on, one level sharper. A runner is a set of claims about an interface. When the interface has moved, the fix is not to patch the line that raised, because the line that raised is only the first claim to be evaluated; it is to re-read the caller the runner imitates and port the whole body.

## The step-1 difference, located

The trace captures every MoE layer's router input, scores, top-k ids and the routed-expert input and output, for both configurations, on the cache the matrix numbers came from. Both runs reproduce their losses before anything is read (`12.543177` and `12.562533`), so the trace describes those two cells.

It puts the origin in one place:

    module                        in maxabs   out maxabs   ids flips   scores maxabs
    layers.1.moe.routed_experts   0.000e+00    2.441e-04
    layers.1.moe.router           0.000e+00                        0      0.000e+00
    layers.2.moe.routed_experts   1.562e-02    1.590e-02
    layers.2.moe.router           3.125e-02                        6      3.984e-04
    ...
    layers.23.moe.router          4.031e+00                      528      3.994e-02

The first MoE layer receives a bitwise identical input and makes bitwise identical routing decisions (zero flips, scores identical), and its routed-expert output differs. That is the whole of the origin: one layer, same input, same routing, different output. Layer 2's router then sees an input perturbed at that scale and flips 6 of its 1024 top-k slots, and from there the two runs are routing different tokens to different experts; by layer 23 it is 528 of 1024. The step-1 losses differ in the third decimal because of that, not because of anything the gradient path does.

Two controls make those numbers readable. The standard dispatcher's own arithmetic is invariant to a layout change that reorders the same maths: at `ep 1` instead of `ep 4`, with a different dispatcher, different grouping and different grouped-GEMM offsets, layer 1's output is identical on all 131072 elements and the whole run reports the same `12.543177`. And the fresh-cache floor is bitwise zero on all 726 gradients. So the difference is not cache noise and not row order.

At layer 1 no token is dropped (zero all-zero rows on either side) and the per-token relative difference has median 2.57e-3.

### The operation

Both paths apply the routing weights identically: `routed_output.to(float32) * weights`, rounded back to bf16. What differs is the sum of a token's top-k expert copies. Core does it with `deterministic_scatter_add`, a `scatter_add` into a bf16 accumulator under `use_deterministic_algorithms`; MoonEP hands the weighted copies to its own combine kernel, which sums them itself.

That is a claim about an operation, so it was measured rather than asserted. Both dispatchers ran on the same tokens with the same expert weights, against one fp32 dense reference (`kit/moonep_vs_std_reference.py`, 2 ranks, 256 tokens, dim 512, 32 experts, top-k 4, the shapes of the on-device test):

    pair                          median rel    max rel
    standard vs fp32 reference     4.649e-03   5.648e-03
    moonep   vs fp32 reference     4.458e-03   5.478e-03
    standard vs moonep             2.913e-03   3.904e-03

The two are the same distance from the reference, with MoonEP marginally the closer of the two on this sample, and the distance between them is smaller than either one's distance to the reference. The bf16 discretisation of this operation is 4.5e-3 and the disagreement between the dispatchers is 2.9e-3 inside it. The isolated figure (2.9e-3) and the figure the real model shows at its first MoE layer (2.6e-3) agree, although the shapes are the on-device test's and not the debug model's, so they are two measurements and not one.

So neither output is the more correct one, and the difference is not a defect in the transport: it is which of two bf16 roundings of the same sum each path takes. What makes it visible at all is that a MoE router is a comparison, so a perturbation far below the bf16 floor of the layer still flips a near-tie, and the flip is discrete.

This is the same mechanism recorded for this model in the top-k near-tie note, reached from the other end: there a 3e-6 routing gap explained a 1e-2 gradient gap, here a 2.6e-3 activation difference explains six flipped slots and then everything downstream.


## Cell 9 answered, by not reading the thing that perturbs the run

The occupancy probe failed here because it read `plan.experts_to_copy`, which is backed by MoonEP's symmetric memory. The question it was asked, whether a rank ever computes on a row belonging to an expert homed elsewhere, does not need the plan: the per-row token counts that `dispatch` returns are an ordinary tensor, and the row layout is known without asking, since the first `E` rows are the global experts in order and the rest are this rank's slots.

So the answer came from a forward hook on `inner_experts` capturing its second argument, in the same trace probe that carries the loss gate. The gate is what says the reading is worth anything: the run reports `12.562533`, the cell's own step-1 loss, so this probe does not perturb the run the way the previous one did.

    rows per layer 40 = E 32 + B 8; rank 0 homes experts [0, 8)
    layers with tokens in a foreign expert's row   0 of 23
    home rows per layer                           1024 to 1664 tokens
    slot rows per layer                           0 to 768 tokens, 19 of 23 layers use a slot

At `dp 4 x ep 4` on the real model, across all 23 MoE layers, no token ever lands in a foreign expert's row, and 16 of the 40 rows (this rank's 8 experts plus its 8 slots) are the entire working set. That is the condition the audit named for compacting the `[E + B]` table to `[E / R + B]`, now met at ep4 on the model rather than at ep2 or by construction in a double. The compaction itself stays a follow-up, since it is a change to MoonEP's own kernel entry points.

## Cell 8 is not run, and why

The plan describes cell 8 as the 33-layer debug flavor at ep4 for three steps, "no new claim". There is no 33-layer flavor in the registry, and the debug flavor already carries 23 MoE layers, every one of which the trace above shows running through MoonEP for the full ten steps. Adding a flavor to run nine more of the same layers would add a registry entry against the flavor rule and would measure nothing the ten-step cells do not already measure, so it stays unrun and this is the record of the decision rather than a gap.
