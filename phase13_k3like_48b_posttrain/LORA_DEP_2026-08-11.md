# LoRA and DEP: the vision stage has nothing to train (diagnosed, then fixed)

> **Resolved 2026-08-12.** The diagnosis below is unchanged and correct; the
> conclusion in "What changed" is not. A stage with no trainable parameters is a
> legitimate state, not an incompatibility, and three places in core said otherwise.
> See "What actually fixed it" at the end. The LoRA matrix is now 18/18 with DEP on.

Found by running the multimodal matrix on BOTH arms with DEP on, which is the first time
that combination has been exercised.

## The result

`kimi_k3_debugmodel_report_arch_lora`, DEP=1, dynamic CP=1, 10 steps:

| | cells |
|---|---|
| pass, 10 | `dp1 fsdp2 cp2 tp2 fsdp2_tp2_cp2 ep2_fsdp2 ep2_fsdp2_tp2_cp2 ep8_fsdp8 tp4 cp4` |
| fail, 8 | `pp2 pp4 pp8 fsdp2_tp2_pp2 tp2_pp2_cp2 fsdp2_pp2_cp2 ep2_fsdp2_tp2_pp2 ep2_fsdp2_pp2_cp2` |

Every non-PP cell passes. Every PP cell fails, with

    ValueError: Optimizer param_groups pattern '.*' matched no parameters
    torchtitan/components/optimizer.py:188 in _build_param_groups

The full-parameter arm is 18/18 and byte-identical to its previous table, so this is
specific to LoRA.

## Attributed by control, not by the signature alone

The signature was already strong -- DEP only engages when `pp>1`, which is exactly the
failing set -- and the log names the culprit: rank 0's stage owns
`['vision__0', 'embed_tokens']`. But the same cell was run both ways:

    LoRA + pp2, DEP on     ValueError, no parameters matched
    LoRA + pp2, DEP off    trains: 12.04920, 12.05721, 12.07554

## Why

DEP puts the vision tower on its own pipeline stage. LoRA adapts neither part of what that
stage holds: the tower is not in `DEFAULT_LORA_TARGETS`, and the embeddings that ride with
it are frozen under LoRA by construction. The stage therefore owns zero trainable
parameters, and the optimizer's `.*` pattern legitimately matches nothing.

Note this is not a bug in the optimizer's check. That check exists to catch pattern typos,
and it is doing its job -- it simply cannot know that the empty match came from a
deliberate combination of two features.

## What changed first, and why it was the wrong call

A guard in `parallelize_kimi_k3` that raised when PP and DEP were on and the model
carried LoRA wrappers, naming both features and offering two ways out. It was a
limitation made explicit rather than a fix, on the reasoning that the real fix meant
adapting the tower or reshaping the DEP layout to keep an adapted module on the vision
stage.

Both of those are real features, and neither was necessary. The premise was wrong: the
stage does not NEED a trainable parameter. It needs the stack to accept that it has none.

## What actually fixed it

Three places treated a frozen-only model part as an error, and they had to be found in
sequence because each only surfaced once the previous one stopped raising:

| where | symptom |
|---|---|
| `_build_param_groups` | `ValueError: pattern '.*' matched no parameters` |
| `_post_init` | `ValueError: optimizer got an empty parameter list` |
| `LRSchedulersContainer.__init__` | `AssertionError: Must have at least one optimizer` |
| `LRSchedulersContainer.state_dict` | `IndexError: list index out of range` |

The empty-match check still raises when the model HAS trainable parameters -- that is the
pattern typo it was written to catch -- and warns and skips only when nothing requires
grad. `_post_init` passes an empty param GROUP rather than an empty param LIST, which
torch accepts, so the container stays a properly initialized `Optimizer` with working
hooks. The scheduler container tolerates an empty list and contributes no checkpoint keys
rather than a `last_epoch` it does not have.

Result: all eight PP cells train and checkpoint. The LoRA arm is 18/18 with DEP and
dynamic CP on, and the full-parameter arm was re-run because these are core files.

Worth noting what this does NOT do: adapting the tower is still unimplemented and is
still the interesting question, since the report trains MoonViT-V2 jointly. What is
settled is that DEP no longer forces that decision.

## Two annotations this retires

* `LORA_MATRIX_18_2026-08-07`'s "18/18" was already marked stale for its three TP+CP
  cells. **Those now pass** -- defect 2 was fixed on 2026-08-10 -- so that half of the
  annotation is retired. Its numbers were taken WITHOUT DEP, which is why they never saw
  this.
* The LoRA arm's TP+CP cells passing is independent confirmation that the defect-2 fix
  carries beyond the full-parameter flavor.
