**B2 NF4-QLoRA / MXFP4-QLoRA -- BLOCKED on the trainer flow (fix first):**
torchtitan.train is meta -> fully_shard -> init, but the quantized base
(NF4 or MXFP4 split-storage) must be quantize-THEN-shard. Post-shard
quantize breaks FSDP param management (probed: 'Linear has no attribute
weight'). RESOLUTION to implement on H200:
  - Add a build-on-device path for `lora_quantize_base` flavors: build+init
    on device, apply_lora, `quantize_lora_bases(model, mode=...)`, THEN
    fully_shard (the Phase-0 order, validated in qlora_sft_demo /
    mxfp4_lora_fsdp_real). Wire it as a trainer flag or a spec.build branch
    that skips meta for quantized flavors.
  - Then run B1's command with lora_quantize_base=nf4 (or mxfp4). NF4 cuts
    base all-gather ~4x; on NVLink real speed. MXFP4 = K3-native format.
  - CAVEAT (measured): post-hoc MXFP4 on the bf16 48B injects ~11%/step-0-
    36% error (FP4 E2M1 coarseness -- all FP4 formats similar, NVFP4 ~13%).
    NOT faithful. The faithful QLoRA wants K3's MXFP4-QAT weights (7.27) or
    Experiment C first.

## 4. Experiment C -- MXFP4-QAT (produce quant-robust weights)

QAT and QLoRA are DIFFERENT regimes (do NOT combine in one step): QAT
trains the base (bf16 master + STE fake-quant) so it becomes MXFP4-robust;
QLoRA freezes a quantized base. Sequence: QAT the base full-param, then
freeze + LoRA.
```bash
# mxfp4_qat.py: apply_mxfp4_qat(model) swaps target Linears for STE
# fake-quant (weight MXFP4 / act MXFP8). Full-param -> fp32 masters (H200).
# Run as an SFT with the QAT wrapper applied post-build; the base master
# learns to tolerate MXFP4. This reproduces (our best guess at) how K3's
# released MXFP4 weights are made. Reconcile the exact recipe at 7.27.
```
After QAT: the base is MXFP4-deployable; QLoRA on it (Experiment B2) is then
faithful (small error), unlike post-hoc quantizing the bf16 open weights.
