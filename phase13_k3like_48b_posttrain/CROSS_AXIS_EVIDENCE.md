判据见 `EVIDENCE_METHOD_2026-08-25.md`。

树:`k3_on_4025` @ `77a298ac5`(集成树,三条轴同时在场)。
flavor `kimi_k3_debugmodel_text_32l`(32 层)。全局 batch 8192,微批 512/dp rank,
seq 512。单一 seed,每格自带预热,每格断言 `Loading the checkpoint from`。
**12 格,0 挂**(其中两格重跑过,见第八节)。

矩阵目录 `mx3_cross_axis_0826_063558`。

## 一、这张表回答的问题

三个 PR 各自把**一条**轴对着纯数据并行测。它们谁也回答不了:一个把三条轴
**同时打开**的 mesh,还训不训同一个模型。这是那张表,跑在三条轴同时在场的集成树上。

## 二、格阵为什么是 12 不是 16

四条轴各取度数 2,枚举所有**合法**子集,按开了几条轴排序。

EP 在 data 轴内分片专家,所以**含 EP 的子集必须含 FSDP** —— `{ep}`、`{pp,ep}`、
`{cp,ep}` 三个不成立。16 减 3 得 13,再减去空集重复计数,落到 12 行。

两两组合不是凑数:三轴那行一旦异常,两两行能指出**是哪两条轴在互相干扰**;
没有它们,那行只是一个不可分解的事实。第七节就是靠它们读出来的。

**用 `pp2 x vp2` 而不是纯 `pp2`,是刻意的**:vp > 1 时每个 rank 持有多个 virtual
stage,那是 cross-stage delta transport **唯一**会生效的形状。纯 1F1B 每 rank 只有
一段,transport 没有可复用的栈 —— 用 pp2 的格子等于把 PP PR 的核心排除在组合验证
之外,表会全绿,但绿得没有意义。

## 四、加 PP x VP,step 1 一位都不动

五对,每对**只差 PP x VP 这一条轴**:

|---|---|---|---|
| `dp1` | `pp2_vp2` | 逐位相同 | 3.33e-5 |
| `cp2` | `pp2vp2_cp2` | 逐位相同 | 1.47e-4 |
| `dp2` | `pp2vp2_fsdp2` | 逐位相同 | 1.81e-4 |
| `cp2_fsdp2` | `pp2vp2_cp2_fsdp2` | 逐位相同 | 5.33e-6 |
| `dp2_ep2` | `pp2vp2_fsdp2_ep2` | 逐位相同 | 4.92e-4 |

五对全部逐位相同,而且是在 **delta transport 开着**的情况下,不是回退。

## 五、transport 逐格确认,不靠推断

PP 那次的教训:adapter 是数值中性的,"wrap 了"和"静默回退了"从外面看没有区别,
唯一的判据是那行专为此存在的日志。

六个 vp 格**全部**打印

    cross-stage cache adapter wrapped 2 stage(s): [0, 2]
    cross-stage cache adapter wrapped 2 stage(s): [1, 3]

stage 归属严格是 Interleaved1F1B 的 `R, R+P`(pp=2)。**零回退警告**。
六个非 vp 格 wrap 计数**全部为 0** —— 反向也对上了。

## 七、两两组合暴露出的一件事

`cp2` 单独是 1.40e-3,`dp2` 单独是 2.52e-4,而 `cp2_fsdp2` 是 **6.46e-3** ——
**大于两者分开之和**。而 `pp2vp2_cp2_fsdp2` 也是 6.46e-3,即在上面再加 PP 什么都不动。

所以这张表里最大的偏差来自 **CP 与 FSDP 的组合**,流水线那条轴是搭便车的。

bf16 下 step-2 这些量级都很小。**照测到的写,不作解释** —— 没有第二次 run 支持任何
机制性说法。

## 八、两格重跑

`pp2_vp2` 与 `cp2_fsdp2_ep2` 第一次 measure pass 报 `ASSERT-SEED-FAIL`:日志里是
`No checkpoint was provided, this is a fresh start`,即从随机初始化训练,
s1 = 12.47611 / 12.46125,明显离群。

原因是**磁盘**,不是并行配置:当时 `/workspace` 到了 93%(剩 30 GB),而 `mx3.sh` 的
闸门设在 20 GB,没拦住。47 GB 垃圾是三次中途 TaskStop 掉的 `cross_axis` 运行
(14G + 14G + 6.9G)加上中断的 `mm_dyncp8`(12G)留下的。

用 `matrix_scripts/rerun_cell.sh` 在**同一矩阵目录、同一 seed** 下重跑该两格,
所以它们仍属于同一张表,不违反"一张表 = 一次 run"。先例是 EP 表的 `ep4_fsdp4`
端口冲突那次。

两条教训:

* **文件数校验挡不住磁盘紧张下的其它失败模式**。上次加的 `SEED_FILES` 计数只能抓
  "没复制全";这次复制通过了计数,训练仍然找不到 checkpoint。发现它的是
  `ASSERT-SEED-FAIL` 那一列 —— 和上次一样,救场的是断言而不是数字。
* **闸门要提高,dump 也要及时清**。`mx3.sh` 现在每个 pass 只删 checkpoint,
  `comm_traces` / `structured_logs` 留着,12 格就是 8 GB。待办:pass 结束即删整个
  dump 目录。**这批证据贴完再改** —— 现在改会让已发布 PR 里链到 `611385d` 那版
  `mx3.sh` 与实际所用不一致。

## 九、不要跨表引用数字

本表 `dp2` 相对 dp1 只有 **2.52e-4**,而 `EP_TEXT_EVIDENCE.md` 里 dp2 相对 dp1 是
**3.7e-3**,差一个量级。因为这张表是 batch 8192 + seq 512 + 32 层 flavor,
那张是 batch 8192 + seq 256 + 24 层,不在同一条曲线上。

每张表只跟自己的 dp1 / dp2 比。

## 十、复现

    matrix_scripts/mx3.sh                # 报 step 1/3/10,含 seed 断言与磁盘闸门
    matrix_scripts/cross_axis_matrix.sh  # 本表 12 格
    matrix_scripts/rerun_cell.sh         # 单格重跑,复用同一矩阵的 seed

命令块里比单轴复现多一个 `--comm.init-timeout-seconds 3600`:冷 KDA/tilelang 编译
要七分多钟,超过 NCCL 默认 300 秒 watchdog,会在编译中途把进程打死。它只抬高那个
上限,不进任何数值路径。
