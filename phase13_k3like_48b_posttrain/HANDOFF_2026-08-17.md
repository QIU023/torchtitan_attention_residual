# Handoff, 2026-08-17

Successor to `HANDOFF_2026-08-16.md`, which is now wrong in two places: the CP path it
describes is no longer the one that runs, and its "delta mode is covered" reading of
`PP_STATUS_2026-08-14` does not hold. Read this instead; it says which parts of the older
file to distrust.

Four gate runs this round: **45 -> 58 -> 58 -> 58**. The first one's thirteen failures were
real and are what found two of the bugs below.

## The one change that alters what every CP run does

**`kda_cp_mode` now defaults to `"kcp"`.** Before this, seven CP cells across three arms --
21 of 58 -- reported CP passing while running KDA Ulysses, which is not what the report
describes (sec 5.1.2) and cannot reach the context length it targets: Ulysses gives every
rank the whole sequence for its head subset, so activation memory does not fall with cp.

Three things had to happen together:

* the wiring now checks per mode. It was enforcing the Ulysses head-divisibility rule on
  KDA layers even under KCP, where heads are never split, which rejects configurations that
  work;
* `_forward_kcp` loops the batch. fla's `causal_conv1d_cp` asserts `[1, T, D]`, so the CP
  path raised for B > 1 -- most of the gate. Flattening into one packed sequence would be
  wrong, not merely awkward: `build_cp_context` cuts the GLOBAL packed sequence into
  contiguous rank-ordered pieces while a rank holds piece r of EVERY sequence, so the
  layouts coincide only at B = 1;
* `conv_with_halo` unwraps its weight. KDA is NoParallel under TP, so the short-conv weight
  is a DTensor(Replicate), and handing that to fla's kernel surfaces as
  `CUBLAS_STATUS_INTERNAL_ERROR` or an illegal memory access -- thirteen cells in the first
  gate run. The Ulysses path had always unwrapped it; the KCP path never did, and could not
  have been caught earlier because the only flavor selecting KCP ran without TP.

**KCP is verified forward AND backward**, at cp=2, 4 and 8
(`matrix_scripts/kcp_batch_parity.py`). cp>=4 is the load-bearing case: it is the first with
a MIDDLE rank, so the prefix scan composes more than two fragments. Worst gradient error
1.36e-02 at cp=8 (bf16 noise), none missing. Both halves matter for a default path -- a
wrong gradient still lets the loss fall, so no gate cell can see it.

A CP run is KCP on the KDA layers AND Ulysses on the MLA layers, simultaneously. They apply
to disjoint layers; this is not a choice between two whole-model strategies.

## What the gate does not cover, stated correctly this time

The 58-cell gate never sets `TORCHTITAN_ATTNRES_CACHE`, so **58/58 is not a regression
statement about delta mode** -- `layout.py`, the capture/augment grad bridge, the rank-local
cache. That much was in the previous handoff.

What that handoff got wrong is treating `PP_STATUS_2026-08-14`'s twelve bitwise-equal delta
cells as coverage. Those cells ran through `run_cells.sh`, whose cell definitions come from
`run13_flav.sh`, which does not set a schedule -- so they ran 1F1B, delta mode is gated on
`isinstance(pp_schedule, Interleaved1F1B)`, and the adapter passed through on both halves of
every A/B. Two naive runs are bitwise equal. The wrap line
("cross-stage cache adapter wrapped N stage(s)") was added 2026-08-08, so it predates that
run and its absence is checkable; no log in the workspace carries it.

phase3's evidence is unaffected -- those scripts pass `--parallelism.pipeline_parallel_schedule
Interleaved1F1B` explicitly.

**Delta mode's real coverage** is now `matrix_scripts/run_attnres_cache_cells.sh`, and
getting one cell to enter delta mode took four attempts, each failing in a way that looks
like the thing under test:

| attempt | why it did not measure delta mode |
| --- | --- |
| matrix PP cells via run_cells.sh | default schedule, adapter passed through |
| report_arch_pp8vp4 | `num_blocks is None` -- not an AttnRes model at all |
| 30 layers over 4 stages | `BlockLayoutTables` needs `n_layers % num_stages == 0` |
| default first/last_stage_less_layers | uneven split, contiguous-layout check refuses it |

And the judge was wrong before it was right: it demanded bit equality with naive, which
delta mode does not provide by design -- the mid-stage block-stack rebuild is "the only
reorder point" (`attn_res_model.py`), so summation order differs and curves separate from
step 2. **Step 1 agreeing to the digit is the forward-is-unchanged check.** Had the bit
judge stood it would have condemned a correct change (A2).

## Delta mode's numerics, with the floor measured

3000 steps per arm, then a sign test across seeds:

| | result |
| --- | --- |
| delta vs naive, mean rel gap | 0.00245 (first 10%) -> 0.00342 (last 10%) |
| same config reseeded, same measure | 0.00465 -> 0.00555 |
| sign of tail difference, 6 seeds | +0.14, +0.24, +0.20, **-0.16**, +0.08, +0.14 (%) |

Mean +0.107%, five of six same-signed, which has probability 0.219 under no bias. **Not a
detectable systematic effect.** The first three seeds all landed positive and were written
up as a +0.19% bias; more seeds corrected it. Keep the sequence in mind: three seeds
produced a confident wrong reading and only more seeds fixed it.

The accurate claim: delta's difference is DETERMINISTIC in mechanism -- same seed, same
digits -- and unbiased in aggregate, at a magnitude inside one configuration's run-to-run
spread. It behaves like noise without being noise. A deterministic perturbation and a random
spread are different objects; comparing magnitudes answers "can I detect it", and only the
sign across seeds answers "is it biased".

`attn_res_cache` stays False, now for a stated reason: engaging delta mode needs
Interleaved1F1B, `n_layers % num_stages == 0`, and an even split. Most configurations
satisfy none of those.

## DEP bubble hiding: measured for the first time, and negative

Everything before this was occupancy, which is not hiding. Step time:

| shape | cost ratio | placed share | tps off -> on |
| --- | --- | --- | --- |
| pp8 x vp2, seq 4096, mb 16 | 0.493 | -- | OOM |
| pp8 x vp2, seq 2048, mb 16 | 2.0 | 2/16 | 432 -> 423 (**-2.08%**) |
| pp4 x vp2, seq 4096, mb 8 | **0.493** | 2/8 | 3726 -> 3690 (**-0.95%**) |

Better ratio and larger placed share both move it toward zero, as the theory says, and
neither reaches a gain.

**The binding constraint is the upfront prefix, not the cost ratio.** The report's design
cannot place the first micro-batches' encodes -- nothing precedes them to anchor on -- so at
pp=4 with mb=8, four of eight are unplaceable before anything runs, two stayed synchronous,
two were placed. A 25% ceiling does not cover a 4.0 ms encode plus plan and hook overhead.
Placed share is about `(mb - pp) / mb`, improving only with `mb >> pp`, and a larger mb is
what does not fit at seq 4096.

That is what the "60 GiB per GPU" figure means in behavioural terms: not that the
configuration fails to start, but that the ones which start leave too small a placeable
share. Reporting -0.95% as "the bubble does not work" would be the mirror image of reporting
8/8 occupancy as "it works".

## Bugs fixed this round

* **`kda_cp_mode` mode-blind wiring** (above), and **`conv_with_halo` DTensor weight**
  (above).
* **`ep_expected` read under a job-level guard.** It is assigned only when this rank has MoE
  layers, while `verify_ep_applied` was guarded on `parallel_dims.ep_enabled` -- a property
  of the job. Under PP a rank can hold only the vision-tower stage, so every ep+pp cell on
  the multimodal arms raised `UnboundLocalError`. Introduced by the previous commit's EP
  verifier, and the gate that blessed that verifier predates it.
* **The shape-inference placeholder had the wrong rank.** `_forward_shape_inference` builds
  what pipelining uses to size the next stage's recv buffer, so it must match what the
  runtime sends -- `torch.stack(pieces, dim=1)` over `[T, D]`, i.e. `[T, K, D]`. A stage
  committing NOTHING took `partial_out.shape` whole and produced a four-dimensional
  `[K, B, L, D]`; a stage committing something put the block axis first. Both need
  `expected_K != N` to reach, which no 16-layer pp2 x vp2 run produces.

  How it surfaced is worth remembering: `TypeError: forward() got multiple values for
  argument 'blocks'`, which reads as a signature problem and is not one.
  `_has_blocks_signature` tests `dim() == 3`, so a rank-4 carrier fails it, falls through to
  the naive call, and lands on `blocks`'s positional slot. **The traceback names the
  consumer; the defect is two stages upstream.** Found by probing the adapter's actual args,
  not by reading the error.
* **Two silent-degradation classes turned into failures**: a capture-count mismatch now
  raises rather than warning (it meant the step applied an incomplete gradient), and
  `verify_params_distributed` names a plain parameter rather than letting `clip_grad_norm_`
  report `aten._foreach_mul_.Tensor got mixed`.
* **Symmetric grad-bridge contract.** A consumer forced `requires_grad` on the cached block
  while the producer installed its hook only if its own block already required grad, so a
  deposit could land in a slot with nothing to pop it. Measured unreachable in training
  (the AttnRes graft projections are trainable even under LoRA) before recording it.

## Review items that were wrong as stated

* **B1's mutual exclusion is impossible.** `kda_cp_mode` is a single enum; and the "both at
  once" it feared is the design, across disjoint layers.
* **C1 is a false positive.** KDA is already counted as linear, AttnRes already has its own
  term, and LatentMoE needs none -- expert weights are latent-shaped so `6 * activated`
  carries it. The MLA term's factor of 6 matches upstream's own
  `get_moe_model_nparams_and_flops`. Bucketing verified: routed 16.52M found by name rather
  than falling into dense.
* **A3's ordering risk is not reachable.** The two `finally` blocks act on disjoint objects
  -- the tower's graph is held by the `GradQueue`'s own references and the cut already
  severed it from the text graph, while the sweep only drops block tensors and slots.

## Measured and deliberately not changed

* `dynamic_cp_min_patches` stays 256. Sweeping it on this tower gives 0.99x at 64 patches
  through 1.06x at 1024 -- every size sits near a 2.5 ms launch floor, so partitioning buys
  at most 6% at 16x the threshold, before charging the per-layer gather the probe does not
  charge for. A value tuned on that floor would be worse than a stated guess; the number has
  to come from K3's 447M tower.
* `_keepalive_touch` stays. 0.037 ms at 256x512 and at 4096x2048 alike -- launch-bound, not
  the O(T*D) reduction it resembles, so a cheaper formulation saves nothing.
* Sub-CP group pre-creation stays. 15.8 ms once at cp=8, and the count follows cp's
  DIVISORS, so cp=16 adds one round.

## Open, with the reason each is open

* **DEP hiding needs `mb >> pp` at seq 4096**, which does not fit in 15.5 GiB.
* **Whether delta's +0.107% is shape-dependent** is unknown for the SAME reason: the 48B
  carrier (d1280, 32 layers, 16 experts a layer) OOMs in 8 x 15.5 GiB at seq 1024, 512 and
  256 alike. One machine unblocks both.
* **Config-driven conversion**: `KimiK3AttnResModel`, `KimiK3MTPLayer`, `KimiK3Spec` ->
  flavor builder, then `kimi_k3/sharding.py`. Both classes already build their children
  through Configs; what remains is making them Configurable, which changes `self.config`'s
  type -- and `register_topology(model.config)` reads it. Needs a session where the matrix
  can run between attempts.
* **C3**: the static cost ratio's behaviour when image composition varies is undocumented.
  C4's per-encode timing is in the report now, so the observability half is done.

## Traps this round paid for

* **A PP failure that reports shapes is reporting the wrapper.** torch re-raises as
  `RuntimeError(exc_msg) from e`; the shapes-and-gradients summary surfaces while the real
  cause sits further up. Three OOMs were diagnosed as a shape bug and then as a PP-backward
  contract problem before anyone grepped for `e`.
* **Three seeds is not enough for a sign.** 3/3 same-signed is p = 0.25.
* **Two empty logs compare equal.** A cell that never started was reported as
  "bitwise-equal" -- require lines before comparing.
* **A green cell needs the mechanism's own engagement line**, not just a loss count. The
  wrap-line assertion caught an entire A/B that measured naive twice.
* **Interleaved1F1B needs vp >= 2 and multi-commit needs `layers_per_stage >
  layers_per_block`.** Together they are tight: 16 layers over blocks of 2 admits exactly
  one multi-commit geometry (pp2 x vp2). `kimi_k3_mini_attnres_multicommit_wide` (32 layers,
  16 blocks) exists to open the others, and all three run:

  | geometry | commits/stage | wrap | step 1 | max abs dLoss |
  | --- | --- | --- | --- | --- |
  | pp2 x vp2, lps=8 | 4 | 2 | identical | 0.00857 |
  | pp4 x vp2, lps=4 | 2 | 4 | identical | 0.01813 |
  | pp2 x vp4, lps=4 | 2 | 2 | identical | 0.02808 |

  Step 1 identical in all three says the forward is unchanged; the spread grows with the
  stage count, which is what more reorder points should do. No capture-count mismatch and no
  step-end slot sweep in any of them, so the grad bridge's per-commit accounting holds at
  four commits a stage and at pp4 -- not just at the single geometry 16 layers could
  express.
