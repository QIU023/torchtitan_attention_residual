here is present, runnable, and reproduced on the current fork head; nothing is
a plan. Reproduction commands are in
`phase13_k3like_48b_posttrain/run_full13_matrix.sh` and the multimodal runner
alongside it.

Fork: https://github.com/QIU023/torchtitan, branch `attention_residual_dev`.

`k3_pr_a_tp_kda`, `k3_pr_b_ep_grouped`, `k3_pr_c_pp_attnres`,

## 3. Pipeline parallel with Block Attention Residuals

PP8 x VP4, 32 layers, `layers_per_stage 1`, Interleaved1F1B:

    PP8xVP4      7.70437  7.40327  6.05897
    PP8 no VP    7.72073  7.43369  6.07240
    FSDP8 no PP  7.70620  7.30309  5.99934

|Dloss| vs the no-PP reference is 0.0018 at step 1.

The cross-stage adapter is cache-based and incremental: a hop ships only the
blocks the sending stage newly committed, the receiver rebuilds the stack from
its cached prefix plus the delta, and entries are dropped when the microbatch
finishes. The K3 report describes the same shape for Block AttnRes under PP,
citing Moonshot's own AttnRes preprint. The adapter stays private to the model
folder -- the generic mechanism was proposed upstream before and declined, and
this is not a re-proposal.

## 4. Context parallel

Gated MLA uses Ulysses head-sharding. KDA uses fla's merged KCP
(fla-org/flash-linear-attention#691, the implementation the K3 report cites) via
`chunk_kda(cp_context=...)` plus its `causal_conv1d_cp` for the short-convolution
halo. We do not carry our own recurrence: plain state summation is wrong for KDA
because the delta rule applies a token-dependent transition to the incoming
state.

The load balancer must stay off; K3's CP reassembles contiguous rank-ordered
shards and a permuting balancer breaks causal order silently. `parallelize`
raises if it is set.

## 5. Defects found, and why loss curves could not find them

This is the part worth reviewing, because each of these passes every check that
looks at a loss curve.

**Block AttnRes TP gradient.** A `Partial()` grad placement over-reduced by
exactly `1/tp`.

**`moe_sharding` `in_grad_placements`.** The layout was computed and then passed
only on the EP branch, so it was dropped whenever EP was off. Reproduces on
unmodified `deepseek_v3`: per-parameter gradient error 0.478 -> 0.0025. Filed
separately.

**KCP short-convolution halo.** A hand-rolled halo fetched the neighbour's state
with `dist.all_gather`, which is not autograd-aware, so the gradient each rank
owed its left neighbour's tail was dropped. Forward was bit-exact; rank 0's last
`W-1` tokens had ~60% gradient error while every interior token was exact.
Confined to `W-1` boundary tokens per rank, so it cannot move a loss curve.
Now uses fla's `causal_conv1d_cp`, which has a real backward.
Probe: `conv_halo_grad_probe.py`.

**Ten multimodal defects, none of which change a loss curve.** Six silently
reverted forward to its text-only branch -- an inherited text dataloader, a
missing multimodal tokenizer, forward parameters named for the model instead of
the collator's output keys (absorbed by `**kwargs`), an unreachable
`vision_token_id`, media token ids past the vocab, and a patch-layout mismatch.
Of the rest, one fires only under `--debug.deterministic` (bilinear interpolate
on a DTensor lowers to `aten._unsafe_index`), one only at cp>1 (a rank's shard
holding zero vision sentinels), and one manifests as a hang rather than an error
(returning early from that case deadlocks the other CP ranks inside a
collective).

The general lesson, which is why `vision_liveness_probe.py` exists: a
multimodal run with an inert tower produces a loss curve that is monotone,
converging, and consistent across parallelisms. No observable distinguishes it
from a working one.

**Measurement regimes.** Cold-seed step-0 checks are blind to zero-initialized
paths: LoRA's B is zero at init, so `grad_A = grad_out @ B^T` is exactly zero
and the check measures an inert adapter. The instrument that works is a shared
warm checkpoint, one varied dimension, and per-parameter attribution.

## 6. Quantization

The matrices above are **bf16 parameters with fp32 reduction, no QAT**. That is
deliberate and matches the report: K3's MXFP4 quantization is
**post-training**, not pretraining --

> "MXFP4 Quantization-Aware Post-Training ... We perform quantization-aware
> training (QAT) throughout the entire post-training stage, covering both SFT
> and RL, so that the model adapts to quantization-induced precision loss.
> During RL, rollout and training share the same quantization scheme."

so a pretraining-shaped parallelism matrix should not carry it. A separate
`kimi_k3_mini_qat_mxfp4` flavor implements the released scheme (MXFP4 routed
expert weights, MXFP8 expert activations, everything else higher precision, the
scope derived from the released `quantization_config` rather than a name list)
and runs: 7.68651 / 7.63050 / 7.43626 at fsdp2. A QAT parallelism matrix is the
right companion to the post-training work, not to this one.

## 7. Known gaps, stated plainly

- **LoRA under TP** carries a gradient defect: per-parameter ratio up to 2.26 at
  tp4, concentrated on `o_proj.lora_b` (the rowwise case), growing monotonically
  with tp degree. All five LoRA legs run without error; the defect is only
  visible to per-parameter attribution from a warm checkpoint. `lora.py`'s
  `Partial()` grad placement cites the Block AttnRes pseudo-query note as
  justification -- and that note was later disproven, since that `Partial()` was
  itself the bug. Under investigation.
- **Vision tower parallelism** is FSDP sharding plus replication on the TP mesh.
  The report's sec 5.2.3 optimizations are not implemented: dynamic CP along the
  patch dimension with gather-KV, and DEP's scheduling of ViT compute into
  pipeline bubbles. The latter needs an upstream interface that does not exist --
  `_ComputationType` is a closed enum and `_step_microbatches` raises on unknown
  actions.
- **2.8T has never been run by us.** The claim is: verified on 48B-real-weight
  shapes and K3-faithful downscales; scale-out is config-level.
- The report's "<2% overhead" is algorithm FLOPs; our "+2.7% step-time" is
  PP-adapter communication on PCIe. Different quantities.
