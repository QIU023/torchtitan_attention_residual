# What MLM PR 6840 has that PR 4312's head does not (2026-09-18)

Read from the source on both sides, not from the earlier note: 6840 at `upstream/pr6840` (`megatron/core/transformer/attention_residual.py`, 770 lines) and the current `pp_review5` (`291f3844a`, 23 commits on main `a3a819c67`). Every line number below is from `pp_review5`; all three gaps were re-checked there on 2026-09-18 and all three still hold. The 2026-09-14 migration note compared the pipeline cache; this one is about the two mechanisms that save memory inside the model, which is what a maintainer asking "what else does 6840 have" is asking about.

Nothing here is a cache item. The cache comparison stands where it was: sections 3c and 3d of `MEGATRON_ATTNRES_VPP_MIGRATION_2026-09-14.md`.

## 1. The block stack is a list of references, never a re-concatenation

6840 keeps the sources in a Python list. `AttnResStageSources.graph_sources` is appended once per block start by `append_block_start(hidden_states)`, and the aggregation takes the values as a sequence: `exit_aggregate_values` returns `[*self.graph_sources, partial]`. No tensor is built to hold the stack.

4312 builds the stack as a tensor, twice over:

    model.py:167   values_TND = torch.cat((block_residual_TND, partial_block_TD.unsqueeze(1)), dim=1)
    model.py:251   block_residual_TND = torch.cat((block_residual_TND, x_TD.unsqueeze(1)), dim=1)
    pipeline_stage.py:83, 102   stack_TND = torch.stack(pieces, dim=1)

The first line runs once per sub-layer aggregation and the second once per block start. Each produces a fresh `[T, N, D]` that autograd holds until backward, so the retained bytes grow with the number of blocks already in the stack: a stack of `N` sources costs `N` saved tensors of widths 1, 2, ... N rather than `N` references to tensors that already exist. The list form has the same arithmetic and none of that retention.

This is the item the report paragraph's first sentence describes ("generated once at the boundary layer and shared by all subsequent layers"), and it is the one the memory entry names as torchtitan's gap.

## 2. The aggregation saves per-token statistics, not hidden-size intermediates

6840's eager path is a custom `autograd.Function`, `_AttnResAggregation` (line 663). Its own docstring states the problem and the remedy:

    A naive autograd implementation retains O(n) fp32 [.., h] intermediates
    (upcast copies and normalized keys) per sublayer. This Function saves only
    references to the incoming values plus per-token fp32 statistics
    (dots, inverse RMS, softmax weights; no hidden-size factor) and recomputes
    everything else in backward.

`forward` calls `_attn_res_fwd_math` and saves `(pseudo_query, key_norm_weight, alpha, dots, rstds, *values)`. Of those, `alpha`, `dots` and `rstds` are per-token, and `values` are references to tensors that already exist. `backward` calls `_attn_res_bwd_math`, which recomputes the upcast and the normalized keys.

4312's `_apply_attention_residual` is the naive implementation that docstring describes. In the fp32 body it creates, and autograd retains, exactly the intermediates 6840 avoids:

    values_float = values_TND.float()                       fp32 [T, N, D]
    keys_TND     = values_float * torch.rsqrt(...)          fp32 [T, N, D]
    probs_T1N    = torch.softmax(scores_TN, ...)            [T, 1, N]
    output_TD    = torch.matmul(probs_T1N, values_float)

So each sub-layer aggregation holds two fp32 tensors of the full hidden size for the whole forward. At bf16 model dtype each is four times the size of the stack it came from.

6840 has three paths behind one interface, which is worth copying as a shape: the FLA fused kernel (`_get_fla_fused_attnres`, `checkpoint_level=1`), a compiled path (`_get_compiled_attn_res`, where AOTAutograd generates the recomputing backward from the plain forward and the custom Function is bypassed), and the eager custom Function above. 4312 has the eager naive path only.

This is a different remedy from PR 4656's AC reuse. AC reuse wraps the whole computation in checkpointing and recomputes all of it; 6840 keeps the cheap statistics and recomputes only the expensive parts inside the op. The two are alternatives, not the same thing, and the report paragraph's second sentence is matched by 6840 in effect rather than by a checkpoint wrapper.

## 3. The received payload is unpacked as views, and this one does not port

Listing this as a third borrowable item was wrong. Correcting it here rather than deleting it, because it looks like a candidate and the next reader should see why it is not.

What 6840 does: `unpack_attn_res_payload` returns `torch.chunk` slices of the received tensor, which share its storage, so gradients accumulate into the one tensor handed back to the schedule. `assemble_stack` instead builds the stack with `torch.stack` and then `detach().requires_grad_(True)`, a copy followed by a fresh leaf.

Why the view form cannot be taken. 6840 reads the accumulated gradient off `leaf.grad`. Under `torch.distributed.pipelining` that slot does not survive: `stage_backward` appends `val.grad` to its outputs and then assigns `val.grad = None`. The fresh leaf is what lets `backward_one_chunk` take `(grad_hidden, grad_stack)` out of `self.bwd_cache` after the base class has run, and hand the columns out itself through `split_stack_grad`, the received ones dense in wire order and the stored ones as deposits. Remove the `detach` and the stage has nothing to split at a point where torch has not already cleared it. The `detach` is load bearing, not an oversight, and the earlier sentence claiming a view form "would remove one copy per hop" overstated both the saving and its availability.

What it costs to not have it, measured rather than asserted. Shapes from the PR's own pp8 x vp4 recipe scaled to the real model: 2048 tokens per micro-batch, `D` 7168, bf16, 93 layers at block size 12, so 8 blocks and one slice is 28.00 MiB.

    side            what it pays per micro-batch
    ours            one stack copy on each receiving stage, k slices for a stage holding k blocks
                    k=1: 28.0 MiB   k=4: 112.0 MiB   k=8: 224.0 MiB, and only the last stages hold 8
    6840            12 extra slices on every hop, from padding to the uniform width: 336.0 MiB
                    pp8 vp2: 16 slices, 448.0 MiB; pp4 vp4: 8 slices, 224.0 MiB

Both copy once on the send side as well: `route_payload` stacks the outgoing blocks, and `pack_attn_res_payload` cats them into what its own docstring calls "a fresh, viewless tensor", required by Megatron's `deallocate_output_tensor`. So 6840's only saving is the receive-side copy, not the whole path.

Read together, not implementing this leaves no deficit. The copy is bounded by the blocks a stage actually holds and is paid in device memory; 6840's padding is paid on the wire on every hop and exceeds our worst stage. The exact per-hop delta is the better trade at these shapes, and it is 4312's.

## How this sits with PR 4656's AC reuse

AC reuse is already filed, so the question is whether 6840's item 2 conflicts with it. Read from its own base (`origin/k3_on_4025`), the branch is two commits and three files; the one that matters is `2e93aa4ae`, 50 lines added across `model.py` and `parallelize.py`. It adds `_checkpointed_attention_residual`, which wraps the existing `_apply_attention_residual` in `remat.checkpoint(region_name=...)`, plus a `checkpoint_residual` flag the block reads and `parallelize_kimi_k3` clears when a Selective, Full or Region AC policy already checkpoints the whole block. The body of `_apply_attention_residual` is untouched.

So the two are alternatives in effect and independent in text:

- In effect they exclude each other. Wrapping the region in a checkpoint discards the forward's saved tensors and recomputes all of it; a custom Function that carefully saves `alpha`, `dots` and `rstds` would have those thrown away and recomputed too. Doing both spends the recompute twice and saves nothing extra. One or the other.
- In text they touch different lines. AC reuse adds a wrapper and changes call sites; a 6840-style rewrite changes the body of `_apply_attention_residual`. They would not collide in a merge. The choice has to be made deliberately rather than discovered by a conflict.

Which one is better is not settled here and needs a measurement: checkpointing recomputes the whole aggregation including the depth softmax, while 6840 keeps the per-token statistics and recomputes only the upcast and the normalized keys. The second recomputes less for slightly more retained bytes. That comparison belongs on the H100, against the same shape, before either is proposed upstream.

## What is not worth taking

- `_AttnResGradTap` (line 346), 6840's gradient bridge, adds `leaf.grad` into the in-graph gradient. It does not fit `torch.distributed.pipelining`: `stage_backward` reads each input's `.grad` and then sets it to `None`, so the slot 6840 relies on is cleared underneath. 4312's stage-level split and deposit is the right shape here and stays.
- The uniform payload width. 6840 pads every hop to the maximum delta over all boundaries because the interleaved schedule carries one `tensor_shape`; measured against its own helper that costs between +12.0% and +27.1% of payload slices depending on the shape. 4312 sends the exact width per hop.
- `pack_attn_res_payload` deliberately returns "a fresh, viewless tensor", which Megatron's `deallocate_output_tensor` requires. That constraint is Megatron's, not torchtitan's.

## Order to do them in

1. The list of references, item 1. It is the largest retention win, it is what the report describes, and it changes the model only.
2. The recomputing aggregation, item 2. Independent of item 1, and the compiled path may give most of it for free once the forward is plain.
Item 3 is not on the list: it does not port, and the measurement above says there is nothing to recover by trying.

Item 1 and item 2 interact in one place worth naming before either is written: if the stack stays a list, the aggregation's `values` argument is already a sequence, which is the signature `_AttnResAggregation` takes. Doing item 1 first makes item 2 a smaller change.

## What `pp_review5` carries that the PR branch does not

Checked with both lines on the same base, since `pp_review5` sits on `a3a819c67` and the PR head `de6f29514` was replayed onto it as `ab8ea5f61`. The answer is close to "nothing", but not exactly nothing.

    pp_review5      23 commits over main, 13 files
    PR head         37 commits over main, 16 files
    subjects only on pp_review5     2 of 23
    subjects only on the PR head   14 of 37

The two are `config: module_fqns_per_model_part and pipeline_parallel_layers_per_stage are exclusive` and `pipeline_parallel: the LLM split takes modules pinned to the first and last stages`. Both are superseded rather than missing: the PR head reinstates the exclusivity check in `ParallelismConfig.__post_init__` and moves the split into Kimi K3's own `kimi_k3_module_fqns_per_model_part`, so core's `pipeline_parallel.py` keeps upstream's shape. By identifier the PR head is a superset: `kimi_k3_module_fqns_per_model_part`, `_kimi_k3_num_stages`, `_as_attn_res_stage` and `_swap_in_attn_res_stages` are all absent from `pp_review5`.

So the reading that the two differ only by a rebase is nearly right, with the correction that the PR head is the later line, not an equal one. The real increments over the PR branch are the two stacked drafts, each one commit and three files over `de6f29514`:

    pp_offload_review1   attn_res_cache_offload, the rank store on pinned host memory   +58/-7
