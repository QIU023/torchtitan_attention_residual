# What MLM PR 6840 has that PR 4312's head does not (2026-09-18)

Read from the source on both sides, not from the earlier note: 6840 at `upstream/pr6840` (`megatron/core/transformer/attention_residual.py`, 770 lines) and 4312's head `de6f29514` as replayed onto main `a3a819c67`. The 2026-09-14 migration note compared the pipeline cache; this one is about the two mechanisms that save memory inside the model, which is what a maintainer asking "what else does 6840 have" is asking about.

Nothing here is a cache item. The cache comparison stands where it was: sections 3c and 3d of `MEGATRON_ATTNRES_VPP_MIGRATION_2026-09-14.md`.

## 1. The block stack is a list of references, never a re-concatenation

6840 keeps the sources in a Python list. `AttnResStageSources.graph_sources` is appended once per block start by `append_block_start(hidden_states)`, and the aggregation takes the values as a sequence: `exit_aggregate_values` returns `[*self.graph_sources, partial]`. No tensor is built to hold the stack.

4312 builds the stack as a tensor, twice over:

    model.py:167   values_TND = torch.cat((block_residual_TND, partial_block_TD.unsqueeze(1)), dim=1)
    model.py:251   block_residual_TND = torch.cat((block_residual_TND, x_TD.unsqueeze(1)), dim=1)
    pipeline_stage.py:83, 102   stack_TND = torch.stack(pieces, dim=1)

The first line runs once per sub-layer aggregation and the second once per block start. Each produces a fresh `[T, N, D]` that autograd holds until backward, so the retained bytes grow with the number of blocks already in the stack: a stack of `N` sources costs `N` saved tensors of widths 1, 2, ... N rather than `N` references to tensors that already exist. The list form has the same arithmetic and none of that retention.

This is the item the report paragraph's first sentence describes ("generated once at the boundary layer and shared by all subsequent layers"), and it is the one the memory entry names as torchtitan's gap.

## 2. The aggregation saves per-token statistics, not hidden-size intermediates

6840's eager path is a custom `autograd.Function`, `_AttnResAggregation` (line 663). Its own docstring states the problem and the remedy:

    A naive autograd implementation retains O(n) fp32 [.., h] intermediates
    (upcast copies and normalized keys) per sublayer. This Function saves only
    references to the incoming values plus per-token fp32 statistics
    (dots, inverse RMS, softmax weights; no hidden-size factor) and recomputes
    everything else in backward.

`forward` calls `_attn_res_fwd_math` and saves `(pseudo_query, key_norm_weight, alpha, dots, rstds, *values)`. Of those, `alpha`, `dots` and `rstds` are per-token, and `values` are references to tensors that already exist. `backward` calls `_attn_res_bwd_math`, which recomputes the upcast and the normalized keys.

4312's `_apply_attention_residual` is the naive implementation that docstring describes. In the fp32 body it creates, and autograd retains, exactly the intermediates 6840 avoids:

    values_float = values_TND.float()                       fp32 [T, N, D]
    keys_TND     = values_float * torch.rsqrt(...)          fp32 [T, N, D]
    probs_T1N    = torch.softmax(scores_TN, ...)            [T, 1, N]
    output_TD    = torch.matmul(probs_T1N, values_float)

So each sub-layer aggregation holds two fp32 tensors of the full hidden size for the whole forward. At bf16 model dtype each is four times the size of the stack it came from.

6840 has three paths behind one interface, which is worth copying as a shape: the FLA fused kernel (`_get_fla_fused_attnres`, `checkpoint_level=1`), a compiled path (`_get_compiled_attn_res`, where AOTAutograd generates the recomputing backward from the plain forward and the custom Function is bypassed), and the eager custom Function above. 4312 has the eager naive path only.

This is a different remedy from PR 4656's AC reuse. AC reuse wraps the whole computation in checkpointing and recomputes all of it; 6840 keeps the cheap statistics and recomputes only the expensive parts inside the op. The two are alternatives, not the same thing, and the report paragraph's second sentence is matched by 6840 in effect rather than by a checkpoint wrapper.

## 3. The received payload is unpacked as views

`unpack_attn_res_payload` returns contiguous views of the received tensor: "The slices are contiguous views of the received leaf tensor, so gradients accumulate into the single tensor handed back to the pipeline schedule." Nothing is copied on the receive side, and the gradient lands in one place.

4312's `assemble_stack` calls `torch.stack(pieces, dim=1)`, which copies every piece into a new tensor. The stage then splits that tensor's gradient again on the way back. The view form would remove one copy per hop per microbatch.

## What is not worth taking

- `_AttnResGradTap` (line 346), 6840's gradient bridge, adds `leaf.grad` into the in-graph gradient. It does not fit `torch.distributed.pipelining`: `stage_backward` reads each input's `.grad` and then sets it to `None`, so the slot 6840 relies on is cleared underneath. 4312's stage-level split and deposit is the right shape here and stays.
- The uniform payload width. 6840 pads every hop to the maximum delta over all boundaries because the interleaved schedule carries one `tensor_shape`; measured against its own helper that costs between +12.0% and +27.1% of payload slices depending on the shape. 4312 sends the exact width per hop.
- `pack_attn_res_payload` deliberately returns "a fresh, viewless tensor", which Megatron's `deallocate_output_tensor` requires. That constraint is Megatron's, not torchtitan's.

## Order to do them in

1. The list of references, item 1. It is the largest retention win, it is what the report describes, and it changes the model only.
2. The recomputing aggregation, item 2. Independent of item 1, and the compiled path may give most of it for free once the forward is plain.
3. The view-based unpack, item 3. Smallest, and it touches the stage rather than the model.

Item 1 and item 2 interact in one place worth naming before either is written: if the stack stays a list, the aggregation's `values` argument is already a sequence, which is the signature `_AttnResAggregation` takes. Doing item 1 first makes item 2 a smaller change.
