## The three candidates, and what measurement did to them

    candidate                                        verdict after measurement
    1. block stack as a list of references           real, and it is the same change as 2
    2. aggregation that saves per token statistics   real, and it is the largest win by far
    3. received payload unpacked as views            still does not port, for a reason in the schedule

Items 1 and 2 are not two changes. 6840's `_AttnResAggregation` takes the values as a sequence, so keeping the sources as references and saving only statistics are the same edit. Treating them as separable is what produced the earlier "narrow form removes almost nothing" reversal: measured alone, dropping the concatenation really does save little, because the concatenation is not what autograd retains.

## What the aggregation actually retains

`_apply_attention_residual` (`model.py:153`) builds `values_TND` by concatenation and then upcasts:

    values_float = values_TND.float()                  fp32 [T, N+1, D]
    keys_TND     = values_float * torch.rsqrt(...)     fp32 [T, N+1, D]

Both survive to backward. At the PR's own shape (2048 tokens per micro batch, `D` 7168, bf16, one slice 28.0 MiB) a stack of 8 plus the partial retains 1008.2 MiB for one call, which is exactly the two fp32 tensors and nothing else. The bf16 concatenation itself is not among the retained storages: its cost is a transient allocation and one copy, so removing only the concatenation removes only peak and bandwidth, not residency. That is the point the earlier version got backwards in both directions.

The aggregation runs twice per layer, at `model.py:263` and `model.py:280`, and once more at the model level (`model.py:523`). The growing concatenation at `model.py:251` runs once per block. So residency is dominated by the per layer aggregations, by a factor of roughly twice the block size.

## Correctness of 6840's backward, checked rather than assumed

`_attn_res_bwd_math` is hand derived, so it was worth checking rather than trusting. Transcribed and run under `torch.autograd.gradcheck` in float64 it passes at two shapes, as does autograd on the same forward:

    T=5 N=3 D=4   explicit backward True    autograd on the same forward True
    T=3 N=5 D=6   explicit backward True    autograd on the same forward True

An earlier run of this check failed, and the failure was mine: the transcription left one `.float()` in the output accumulation, so a float64 probe was truncated to fp32 exactly where the values enter the output. The signature of that bug is instructive. The gradients of `pseudo_query` and `key_norm_weight`, which reach the output only through the float64 softmax path, matched to 1e-8, while the value gradients were wrong by 5 percent. Any explanation that did not account for the two passing inputs would have been wrong.

## The result is not bitwise, and by how much

The reference form reorders the same arithmetic: it takes the dot product first and scales by the inverse RMS, where the current form normalises the values first and then contracts. The difference is input conditioned, because the depth softmax amplifies it when the logits are extreme.

    pseudo query scale     |logit| max   mean max prob    out dev   grad dev
    N(0,1)                      131.50           0.966      3.70%      3.45%
    N(0,1) / sqrt(D)              4.41           0.336      0.42%      0.35%

At a realistic logit scale the deviation is about one bf16 ulp (2^-8 is 0.39%). At an unrealistic scale, where the softmax is nearly one hot, reordering decides near ties and the deviation is an order of magnitude larger. This matters for how the change is justified: it cannot be claimed under the usual bitwise step 1 bar against the pre change baseline, because it is a different summation order. The honest bar is a step 1 gradient comparison against the current form with the deviation sized next to it, on one warm cache, plus the float64 gradcheck above as the correctness argument.

## How this sits with PR 4656's AC reuse, re judged

The earlier version judged this against a baseline of plain `today`, which was the wrong baseline: AC reuse is not tied to the PP cache and it is on by default. Read from its own base (`origin/k3_on_4025`), the branch is now three commits and four files (`fd0a9b6c6`, `615908fcd`, `362b6cc70`), not the two the earlier version described. `KimiK3TransformerBlock.checkpoint_residual` is initialised to `True`, `_attention_residual` routes to `remat.region` under RegionAC, to `_checkpointed_attention_residual` otherwise, and `parallelize_kimi_k3` clears the flag only when a Selective, Full or Region policy already checkpoints the whole block. So the default configuration checkpoints the residual.

With that as the baseline, the table above answers the question directly. At N=8 the reference form retains 0.2 MiB against AC reuse's 224.0, peaks at 280.2 MiB in forward against 1988.1, peaks at 560.3 MiB in backward against 3024.0, and its backward costs 27.87 ms against 53.48. The reference form dominates on all four.

That comparison is narrower than it first reads, and an earlier version of this section overstated it. Three corrections.

First, the overlap is one flag, not the PR. 4656 is four files: the residual checkpoint is a small part of `model.py`, and the bulk is the `remat.region` declarations for `KimiMLAAttention`'s q, kv, inner attention, gate and wo, plus the KDA regions, none of which this Function touches. Only `checkpoint_residual`'s effect on the aggregation overlaps.

Second, even that overlap is conditional, and the condition is the one that decides the question. The table above is measured with no block level AC, which is not how this model trains. Under Full, Selective or Region AC the block is already checkpointed and `parallelize_kimi_k3` clears `checkpoint_residual` itself, so the independent checkpoint path measured above is not the path that runs. What runs under RegionAC is the named region, and that path is measured in the region table below: there the two compose rather than exclude, and the Function is what makes a saved region cheap enough to keep saved. So "the reference form makes the checkpoint redundant" was wrong twice, once for being stated unconditionally and once for resting on a configuration this model does not use.

Third, the evidence classes are not equal. Everything above is a single op microbenchmark on a 5060. 4656's memory gain was measured end to end. A microbenchmark does not overturn an end to end measurement, and the comparison that would settle the two is peak memory for one real cell in four configurations on the H100: the PR head, the PR head with the checkpoint, the PR head with the Function, and both. Until that exists, the two should be read as independent changes that happen to touch the same region.

Wrapping the reference form in a checkpoint would discard statistics it deliberately kept and recompute them, so doing both is not obviously right either; that is also a question for the four way measurement rather than an answer this document can give.

Three things follow, and the first is the one the earlier text got wrong.

4656's residency gain is real and reproduces exactly: 1008.2 MiB down to nothing for this region. What the earlier text omitted is its price, which is 41% more backward time (39.22 to 55.24) and 50% more backward peak (2015.8 to 3024.0). Reporting the gain without the price was the actual error, not the direction of the result.

The checkpoint does not lower forward peak at all, 1764.2 against 1764.3. It cannot: the forward still materialises both fp32 tensors and simply declines to keep them. Since peak is what decides an out of memory, that matters. The Function lowers forward peak 6.3x and backward peak 3.1x, because those tensors are never built.

Doing both is a loss in that configuration. It buys the last 0.2 MiB of residency and pays 55% more backward time for it, 28.88 to 44.81.

That whole comparison, however, assumes no block level activation checkpointing, and that is not the configuration this model trains in. With a block level policy the residency question is already answered by the block checkpoint, and what 4656 does under RegionAC is something else entirely: `_attention_residual` declares the residual as a named region and lets `remat_should_recompute` decide, so a region matched by `save_patterns` is kept rather than replayed. The gain there is backward time, not residency. This reverses the earlier reading, and the reversal is the point.

4656's gain under AC is real and it is a time gain: choosing save over recompute takes backward from 56.17 to 40.78 ms, 27% off, at a cost of 1036.2 MiB of residency.

The Function does not replace that. It makes it affordable. With the Function the same save costs 28.2 MiB instead of 1036.2, a factor of 37, and backward goes 46.04 to 30.31. What was a gigabyte traded for fifteen milliseconds becomes twenty eight megabytes traded for sixteen, which is the difference between a switch nobody can afford to turn on and one that can default to on.

The two are orthogonal in construction as well as in effect: the Function changes the body of `_apply_attention_residual`, 4656 wraps that same function in a region, and all four combinations above run. And the Function carries one thing no checkpoint style remedy can give, which is forward peak: 1764 MiB down to 280. A checkpoint still builds both fp32 tensors and merely declines to keep them, so it leaves forward peak untouched, and peak is what decides an out of memory.

The earlier conclusion in this section was drawn with no block level AC, a configuration this model does not train in, and it was wrong in the direction that matters. The rest of 4656, the regions for the MLA projections, the inner attention, the gate, wo and KDA, is untouched by any of this.

## Item 3, why it does not port

What 6840 does: `unpack_attn_res_payload` returns `torch.chunk` slices of the received tensor, which share its storage, so gradients accumulate into the one tensor handed back to the schedule. `assemble_stack` instead builds the stack with `torch.stack` and then `detach().requires_grad_(True)`.

Why the view form cannot be taken. 6840 reads the accumulated gradient off `leaf.grad`. Under `torch.distributed.pipelining` that slot does not survive: `stage_backward` appends `val.grad` to its outputs and then assigns `val.grad = None`. The fresh leaf is what lets `backward_one_chunk` take `(grad_hidden, grad_stack)` out of `self.bwd_cache` after the base class has run and hand the columns out itself through `split_stack_grad`. The `detach` is load bearing.

What it costs not to have it, at the PR's own pp8 x vp4 recipe, 93 layers at block size 12, so 8 blocks and one slice of 28.00 MiB:

    side     what it pays per micro batch
    ours     one stack copy on each receiving stage, k slices for a stage holding k blocks
             k=1: 28.0 MiB   k=4: 112.0 MiB   k=8: 224.0 MiB, and only the last stages hold 8
    6840     12 extra slices on every hop, from padding to the uniform width: 336.0 MiB
             pp8 vp2: 16 slices, 448.0 MiB; pp4 vp4: 8 slices, 224.0 MiB

Both copy once on the send side as well. So not implementing item 3 leaves no deficit: the copy is bounded by the blocks a stage actually holds, while 6840's padding is paid on the wire on every hop and exceeds the heaviest stage here.

## What is not worth taking

- `_AttnResGradTap` (line 346), for the `stage_backward` reason above.
- The uniform payload width, measured at between +12.0% and +27.1% of payload slices depending on the shape.
- `pack_attn_res_payload` returning "a fresh, viewless tensor", which Megatron's `deallocate_output_tensor` requires. That constraint is Megatron's, not torchtitan's.

## The change, and why it is smaller than the earlier version claimed

The earlier version proposed a narrow form that changes the helper's signature and its three call sites, and a wide form that changes the cross stage contract and both SPMD declarations. Neither is needed for the measured win.

`block_residual_TND` appears in `model.py` (18 references) and `sharding.py` (3). The three in `sharding.py` are `_block_residual_placement` plus the layer's `in_src` and `in_dst` entries, all keyed on the layer argument name and its rank. `pipeline_stage.py`, `mtp.py`, `cp_kda.py` and `layout.py` have none.

The whole win is inside `_apply_attention_residual`. Replacing the concatenation with `unbind(dim=1)`, which returns views and copies nothing, gives the sequence the Function wants, and the helper keeps its exact signature. That leaves untouched: all three call sites, both SPMD declarations, the layer to layer contract, the stage code, and the review diff 4312 is being read on. The growing concatenation at `model.py:251` stays, and is second order next to what the aggregations retain.

Precedent for the mechanism is in core, not only in Megatron: `torch.autograd.Function` appears in `components/loss.py`, `models/common/linear.py`, `models/common/dist_gemm.py`, `models/common/aux_loss.py`, `models/gpt_oss/moe.py` and the quantization modules. `RMSNorm.eps` is a plain float, so it crosses the Function boundary as a non tensor argument. The residual norm and projection weights are declared TP unsharded in `sharding.py`, so the backward's reductions are over replicated weights and need no collective. K3's `parallelize.py` calls no `torch.compile`, so there is no graph break to manage today.

Test surface before the change: no test under `tests/` referenced `attention_residual` or `block_residual`. `test_kimi_k3_pp_exact_block_grads.py` builds its own synthetic `_ExactStage` with `torch.arange` weights, so it covers the transport and not the aggregation math. A change confined to the helper was therefore uncovered, which is why one was added with it.

The backward was re-derived here rather than trusted. All five paths match the
code: the softmax Jacobian (`p * (pairing - sum p pairing)`), the score path
(`grad_logits * inverse_rms`, contracted with the query), the variance path
(`grad_logits * scores * -0.5 * inverse_rms^3`, times `2/D` times the value),
the query accumulation as a per-source GEMV, and the product rule splitting
`grad_query` onto the two weights. The five return values line up with the five
forward arguments, `eps` correctly returns None, and the empty-stack branch in
backward is guarded.

Three things to add to what is written above.

- The weight product changed precision, and part of the reported bf16 deviation
  is avoidable. The current form computes `norm.weight.float() *
  projection.weight.squeeze(0).float()`, two upcasts then an fp32 multiply; the
  shipped form computes `(score_weight_D * norm_weight_D).float()`, which under
  FSDP mixed precision multiplies two bf16 tensors and rounds before upcasting.
  Measured at D 7168 with bf16 weights: `query_D` is off by 3.86e-3 at most and
  1.40e-3 on average, and propagated through the depth softmax at a realistic
  logit scale that alone moves the output by 0.169%. The table above reports
  0.457% and 0.376% in bf16 and attributes it to the reordering; this part is not
  reordering and goes away by upcasting both factors before the multiply, in the
  forward and in the backward's copy of the same line.
- The verification list has no run of the cell that type checks. The change sits
  in `model.py`, so it is on every path, not only the pipeline: `kimi_k3_mm`
  (`kimi_k3_debugmodel_mm`, fsdp 2 x tp 2 with SP x ep 2) runs with SPMD type
  checking on, and `spmd_types.register_local_autograd_function`'s own docstring
  says that "unregistered autograd functions that reach the type checker leave
  their outputs untyped or raise in strict mode". Precedent cuts both ways: of
  the five core modules cited above, only `models/common/linear.py` registers,
  while `components/loss.py`, `dist_gemm.py`, `aux_loss.py` and `gpt_oss/moe.py`
  do not. So this is a question to settle by running that cell on this branch,
  not a defect on paper; if it does need registering, the Function qualifies as
  local (the N axis is never sharded and the contraction is over a TP-replicated
  D).

## End to end on the H100, four configurations (2026-09-18)

Every other number in this document is a single op microbenchmark on a 5060. This is the training step. PP4 x VP4 on four H100 cards, the K3 debug flavor, 5 steps, the box held exclusively, peak taken as the maximum over all four ranks.

    cell   tree           region policy              peak GiB
    A      no Function    SelectiveAC, recomputed      8.51
    B      no Function    RegionAC, saved              8.81
    C      Function       SelectiveAC, recomputed      8.35
    D      Function       RegionAC, saved              7.88

The best configuration is D, both changes together: 0.63 GiB under the current default A, which is 7.4%, and 0.93 GiB under B, which is 4656's value path on its own, 10.6%. So the reading that the two compose rather than exclude holds end to end and not only in the microbenchmark.

B above A by 0.30 GiB is the price of a saved region paid in a real step: without the Function, keeping the residual costs residency instead of recompute. That is the same effect the microbenchmark sized at 1036.2 MiB per aggregation, and the gap between 1036 MiB and 300 MiB is the point below.

The magnitudes do not transfer, and the microbenchmark's multiples must not be quoted as step level numbers. This cell runs the debug flavor, `dim` 1024 over 24 layers with a stack that reaches 2. The microbenchmark runs the real shape, `dim` 7168 with a stack of 8. The real model should gain considerably more, and that has not been measured here.

One result was not predicted and is left as an observation rather than a conclusion: D sits 0.47 GiB below C, so with the Function the saved region lowers peak rather than raising it. The plausible reading is that saving the region removes the intermediates that backward would otherwise rebuild during recompute, but nothing here establishes that.

Three limits belong with these numbers. The H100 is SM90 and is not on the Attention Gym KDA allow list, so the guard was widened locally to run at all, which the K3 KDA path should be assumed to be affected by even though the residual comparison is not. Only 5 steps were run, with peak settling by step 2. And an earlier version of this runner lost three of its four cell logs while reporting success for all four; the cause was never established, and this version only avoids it by writing each cell's evidence to a separate file the moment the cell ends. That is a workaround, not a diagnosis.

## SPMD type checking rejects the Function as written

The `kimi_k3_mm` cell, which is the one that runs with SPMD type checking on, fails on `pp_review5` at `2488b7a17`:

    SpmdTypeError: _AttentionResidualAggregation.apply: autograd Function is not
    registered for SPMD type checking.

This is a real defect on the branch, not a paper question. The checker's rule is at `spmd_types/_checker/__init__.py:2907`: an autograd Function that is not in `_LOCAL_AUTOGRAD_FUNCTIONS` raises under `_state.is_strict()` and silently leaves its output untyped otherwise. The `mm` cell runs strict, so it raises. Since the change sits in `model.py` and takes effect on every path, this blocks the cell regardless of parallelism.

The fix is one of the two the error names, `register_local_autograd_function` or an `spmd_typecheck` staticmethod. Whether the first suffices is being measured; it is not yet answered here.

## Scope: these two commits do not belong in 4312

This document compares 6840, which is Megatron's whole AttnRes implementation (the model, the aggregation op, payload pack and unpack, the VPP cache and the gradient tap), against PR 4312, which does one thing: add a VPP cache to an eager AttnRes that upstream already merged. Those are different scopes, and the comparison above mixes them. The line at the top of this document, that nothing here is a cache item, is the admission: gaps 1 and 2 are model-layer findings measured against upstream's own code, and gap 3 is the only cache-layer one, which does not port.

The aggregation is upstream's, not 4312's. `_apply_attention_residual` arrived with #4025 on 2026-08-24 and sits on `upstream/main` today: `model.py:162` builds `values_TND` by concatenation, `:163` upcasts it, `:165` builds the normalized keys, and autograd holds both fp32 tensors. Its three call sites carry no pipeline guard and the model file imports nothing from the pipeline, the stage or the layout, so the two tensors are retained at dp1 on a single card, under TP, and under EP, with no PP anywhere. 4312's own change to `model.py` is +40/-23 and is a contract adaptation: `prefix_sum_TD` becomes the optional `partial_block_TD` because a stage boundary may carry no partial block, the concatenation becomes a ternary, the block-boundary concatenation moves, and call-site variables are renamed. The softmax, the upcast, the inverse RMS and the matmul are untouched.

So the two commits on `pp_review5` (`1ad999623`, `2488b7a17`, with the test `3f6f35127`) optimise upstream's model code and have nothing to do with pipelining. They sit on that branch only because it is the branch currently being worked on, which is the same scope error in another form. They belong in a separate small PR against main, not in 4312's review diff.

The reasons are practical. The reviewers of a model change are not the reviewers of a pipeline change. The evidence the change needs reproduces at dp1 on one card, forward peak 1764 to 280 MiB and residency 1008.2 to 0.2 MiB, with no eight-card pipeline cell involved. The relationship to 4656 is one sentence there, since the two touch the same function from the inside and the outside and all four combinations run. And 4312's diff does not move while it waits for review, which matters because this change is not bitwise and takes effect on every path, so putting it inside a pipeline PR would add an argument that has nothing to do with pipelining.

The cost is that it is not bitwise, a reordering plus one bf16 ulp, so it owes a step 1 gradient comparison against the current form with the deviation sized next to a floor. That is already Order item 2, and the four configuration end to end peak memory is Order item 3. Those two are the Results section of that separate PR.

What is adoptable from 6840 into 4312 is a cache question and lives in `MEGATRON_ATTNRES_VPP_MIGRATION_2026-09-14.md`, sections 3c, 3d and 3e, not here.
