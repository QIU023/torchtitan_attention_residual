## 一、改变了每次 CP 运行的那件事

**`kda_cp_mode` 默认从 `ulysses` 改成 `kcp`。**

改之前：矩阵里 7 个 CP 格子 × 3 臂 = **21 格报告「CP 通过」，跑的却是 KDA Ulysses**——那不是报告 5.1.2 描述的方案，而且它给每个 rank 全序列（只切 head），激活显存不随 cp 下降，K3 的上下文长度根本达不到。

三件事必须同时做才能切默认：

1. **wiring 分模式**。原来对 KCP 也强加 Ulysses 的头数整除规则，而 KCP 从不切 head——那会拒掉本来能跑的配置。
2. **`_forward_kcp` 逐条循环 batch**。fla 的 `causal_conv1d_cp` 断言 `[1, T, D]`，所以 B>1 直接 raise，而矩阵大部分格子 B=8。**不能展平成一条 packed 序列**：`build_cp_context` 是把**全局** packed 序列按 rank 连续切块，而本 rank 持有的是每条序列的第 r 段，两种布局只在 B=1 时重合。逐条也正好是递推需要的——delta 规则的状态不能跨序列传播。
3. **`conv_with_halo` 解包权重**。KDA 在 TP 下是 NoParallel，短卷积权重是 `DTensor(Replicate)`，交给 fla 内核会报 `CUBLAS_STATUS_INTERNAL_ERROR` 或非法内存访问——第一轮矩阵 13 格就是这个。Ulysses 路径一直在自己的 `conv_subset` 里解包，KCP 路径从来没有，而且**以前不可能发现**：唯一选 KCP 的 flavor 不带 TP。

**KCP 的前向和反向都验过**，cp=2/4/8（`matrix_scripts/kcp_batch_parity.py`）。cp≥4 才是承重情形——它是第一个有**中间 rank** 的配置，prefix scan 要组合两个以上片段。cp=8 最差梯度误差 `1.36e-02`（bf16 噪声），无缺失。默认路径必须两半都验：**错的梯度也能让 loss 下降**，任何矩阵格子都看不见。

一次 CP 运行是 **KDA 走 KCP、MLA 走 Ulysses，同时生效**。它们作用于互不相交的层，不是两种整模型策略之间的选择。

## 二、矩阵覆盖不到的地方（这次说准确了）

58 格从不设 `TORCHTITAN_ATTNRES_CACHE`，所以 **58/58 不是对 delta 模式的回归陈述**。

8-16 那份交接把 `PP_STATUS_2026-08-14` 的「12 格 delta 逐位相同」当成覆盖，那是错的：那些格子经 `run_cells.sh`，格子定义来自 `run13_flav.sh`，**不带 schedule 参数**，于是跑 1F1B，而 delta 模式硬门在 `isinstance(pp_schedule, Interleaved1F1B)`——adapter 两侧都 passthrough。**两次 naive 当然逐位相同。** wrap 行（`cross-stage cache adapter wrapped N stage(s)`）是 2026-08-08 加的，早于那次运行，所以它的缺失是可查的；workspace 里没有任何日志带它。

phase3 的证据不受影响——那些脚本显式写了 `--parallelism.pipeline_parallel_schedule Interleaved1F1B`。

**让一格真正进入 delta 模式花了四次尝试**，每次的失败都长得像被测对象出问题：

| 尝试 | 为什么没测到 delta |
| --- | --- |
| 经 run_cells.sh 用矩阵 PP 格 | 默认调度，adapter passthrough |
| report_arch_pp8vp4 | `num_blocks is None`，根本不是 AttnRes 模型 |
| 30 层 / 4 stage | `BlockLayoutTables` 要求 `n_layers % num_stages == 0` |
| first/last_stage_less_layers 默认非零 | 切分不均，连续布局检查拒绝 |

**判据本身也先是错的**：它要求与 naive 逐位相同，而 delta 模式**设计上就不逐位相同**——mid-stage 重建块栈是代码注释自己写的「唯一重排点」，浮点求和顺序不同，曲线从第 2 步开始分开。**step 1 逐位一致才是「前向未变」的判据。** 那条错判据若留着，会判定一个正确改动（A2）是错的。

多提交现在覆盖四种几何（`kimi_k3_mini_attnres_multicommit_wide`，32 层 16 块）：

| 几何 | commits/stage | step 1 | max abs Δloss |
| --- | --- | --- | --- |
| pp2×vp2 (lps=8) | 4 | 逐位相同 | 0.00857 |
| pp4×vp2 (lps=4) | 2 | 逐位相同 | 0.01813 |
| pp2×vp4 (lps=4) | 2 | 逐位相同 | 0.02808 |

偏差随 stage 数增长（重排点更多）。四种都没触发 capture-count 断言、没有 slot 泄漏，所以梯度桥的**按提交计数**在 4 commits/stage 和 pp4 下都成立。

**一个几何上的硬约束**：Interleaved1F1B 要 vp≥2，多提交要 `layers_per_stage > layers_per_block`，两者夹逼下 16 层/块 2 的 flavor **只有 pp2×vp2 一种多提交几何**（`pp×vp` 必须整除 16 且乘积 <8 且 vp≥2 → 只有 4）。

## 三、delta 模式的数值：地板测出来了

3000 步 × 3 臂，然后跨种子符号检验：

| | 结果 |
| --- | --- |
| delta vs naive 平均相对差 | 0.00245（首 10%）→ 0.00342（末 10%） |
| **同配置换种子**，同一度量 | 0.00465 → 0.00555 |
| 6 个种子的末段差符号 | +0.14, +0.24, +0.20, **−0.16**, +0.08, +0.14 (%) |

均值 **+0.107%**，6 个里 5 个同号——无偏假设下概率 0.219，**不是可检出的系统性效应**。前三个种子全为正，我当时写成了「+0.19% 偏置」，**加种子才纠正过来**。这个过程本身要记住：三个种子给出了一个自信的错误读数。

准确说法：delta 的差**机制上确定**（同 seed 逐位可重现），**总体上无偏**，量级在同配置的运行间离散度之内。它行为像噪声但不是噪声。**确定性扰动和随机离散是不同的对象**：比较量级回答「能不能察觉」，只有跨种子符号回答「是否有偏」。

`attn_res_cache` 保持 False，理由从「还不敢信」换成具体条件：进入 delta 模式需要 Interleaved1F1B、`n_layers % num_stages == 0`、切分均匀，多数配置一条都不满足。

## 四、DEP 气泡隐藏：首次测到，且为负

之前全是占用率，占用不是隐藏。step time：

| 形状 | cost ratio | 放置份额 | tps off → on |
| --- | --- | --- | --- |
| pp8×vp2, seq 4096, mb 16 | 0.493 | — | **OOM** |
| pp8×vp2, seq 2048, mb 16 | 2.0 | 2/16 | 432 → 423（**−2.08%**） |
| pp4×vp2, seq 4096, mb 8 | **0.493** | 2/8 | 3726 → 3690（**−0.95%**） |

更好的 ratio 和更大的放置份额都把数字推向零（与理论一致），但都没到正收益。

**真正的约束是 upfront 前缀，不是 cost ratio。** 报告自己的设计无法放置最前面几个 micro-batch 的 encode——它们之前没有动作可以锚定。pp=4/mb=8 时 8 个里 4 个在运行前就不可放置，2 个仍同步，2 个被放置。**25% 的天花板盖不住 4.0 ms 的 encode 加上计划与 hook 开销。** 放置份额约 `(mb − pp) / mb`，只能靠 `mb >> pp` 改善，而更大的 mb 正是 seq 4096 装不下的。

这才是「约 60 GiB/GPU」在行为上的含义：**不是配置起不来，而是起得来的配置里可放置份额太小**。反过来说，把 −0.95% 报成「气泡没用」，和把 8/8 占用报成「气泡有用」是同一个错误的镜像。

**DEP 是完整实现吗**：三层都实现且数值正确（解耦 / 前向并发两条互斥路径 / 反向 graph cut + 延迟重放，梯度逐位正确），但 `vit_dep_stages>1` 是**我们的推广**（报告没给 stage 数），**收益未证明且在当前硬件上不可能证明**。

## 五、本轮修的 bug

1. **CP wiring 模式盲** + **`conv_with_halo` 的 DTensor 权重**（见上）。
2. **`ep_expected` 在 job 级守卫下被读**。它只在「本 rank 有 MoE 层」时赋值，而 `verify_ep_applied` 守在 `parallel_dims.ep_enabled`——那是 **job 的属性**。PP 下一个 rank 可能只持有视觉塔 stage，于是多模态臂所有 ep+pp 格 `UnboundLocalError`。**这是我上一个 commit 的 EP 验证器引入的**，而祝福那个验证器的矩阵跑在它之前。
3. **shape-inference 占位符 rank 错**。`_forward_shape_inference` 造的东西决定下游 recv buffer 尺寸，必须等于运行时发的 `torch.stack(pieces, dim=1)` over `[T, D]`，即 `[T, K, D]`。**不提交任何 block 的 stage** 拿 `partial_out.shape` 整个 → `[K, B, L, D]` 四维；提交了的拿 `new_blocks_out.shape[1:]` → block 轴在前。两者都要 `expected_K != N` 才走到，16 层 pp2×vp2 恰好相等。

   **它怎么现形值得记住**：报错是 `TypeError: forward() got multiple values for argument 'blocks'`，看起来像签名问题而不是。`_has_blocks_signature` 测 `dim() == 3`，rank-4 过不了，落到 naive 调用，占了 `blocks` 的位置。**traceback 指着消费方，缺陷在两级之外的生产方。** 靠打印 adapter 实际收到的 args 才找到，不是靠读报错。
4. **两类静默降级改成失败**：capture-count 不匹配现在 raise（原来只 warn，而它意味着这一步应用了残缺梯度）；`verify_params_distributed` 点名 plain 参数，而不是让 `clip_grad_norm_` 报 `aten._foreach_mul_.Tensor got mixed`。
5. **梯度桥两侧契约对称化**。消费方原来无条件对缓存块 `requires_grad_(True)`，而生产方只在自己的块已需要梯度时装 hook——于是 deposit 可能落进没人 pop 的 slot。**先实测确认在训练中不可达**（LoRA 下 AttnRes graft 投影也是可训练的，所以块始终 requires_grad），才把这个不变量记进代码。

**C3 的答案比 review 设想的明确**：`dep_cost_ratio.py` 既不平均也不取上界over分布——它是**分析式**的（参数量 + FLOP 形状，不跑 kernel），取单一 patch 数、默认 1024 即 collator 的 `max_patches`。那是**单张图成本的上界**，所以对含小图的批次高估 ViT 侧，而 ratio 偏高 → 放置更少。**失效方向是单侧的：只会过度保守。** 这个区分有实际意义——超出气泡才拖慢 step，没放置只是少赚。

## 九、这轮踩过的坑

* **PP 的失败报告里出现形状清单时，那份清单是包装器。** torch 用 `raise RuntimeError(exc_msg) from e` 重抛，「shapes 和 gradients 都在」浮在最上面，真正的 `e` 在日志更靠上。三次 OOM 被先诊断成形状 bug、再诊断成 PP backward 契约问题，才有人去 grep 原始异常。

* **绿格子需要机制自己的 engagement 行**，不只是 loss 计数。wrap-line 断言挡住了一整个「两次 naive 互比」的 A/B。
* **把 `grep -l` 的文件名命中当成继承事实。** 我据此写了「三个文件 subclass `GroupedExperts`」，实际只有一处；另外三个分别是动态工厂、`isinstance` 判断、注释提及。和「把日志行当检查」是同一类错误。
* **不要凭感觉宣称 context 快用完。** 一次长会话里我在实际还剩 27%/24%/20%/20% 时分别声称「约 15%/10%/8%/5%」，每次都借此压缩了工作。已写进 memory 作为规则。
