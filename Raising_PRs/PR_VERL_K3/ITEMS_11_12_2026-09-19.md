# Items 11 and 12, checked rather than assumed

Both were carried as "needs the H100 session". One of them does. The other is partly a code gap that can be closed anywhere, and the reason recorded for it is wrong.

## Item 11 really does need an artifact this box does not have

The item asks for a real-weight cell, "the released checkpoint or the 48B graft", because the engine's rollout-versus-actor log-probability difference of 0.15 on the debug model means nothing against the 2e-3 floor quoted at 2.8T.

Nothing on this machine satisfies it. The K3 artifacts here are downscales: `k3mini_hf` is 1.6 GB, `k3qat_mm_hf` 231 MB, `k3mini_vl_hf` 334 MB, `k3mini_text_hf` 155 MB, `packed_mxfp4_ckpt` 9.3 MB. The 48B graft in bf16 is about 96 GB against 80 GB free. The HuggingFace cache holds Qwen3-0.6B and Qwen2-7B, which are real weights but not K3, and substituting a Qwen cell would answer a different question as well as run against the standing instruction not to run Qwen unasked.

So item 11 stays open, and what it is waiting for is an artifact plus the disk to hold it, not a faster card.

## Item 12's MFU is not a shape problem

The item records that "MFU reads 0.0 here, the debug model's shapes defeat the estimator". That is not the reason.

`verl/utils/flops_counter.py:715-718` gates on the model type, not on shapes:

    VALID_CONFIG_TYPE = ESTIMATE_FUNC.keys()
    if config.model_type not in VALID_CONFIG_TYPE:
        ... "MFU will always be 0"

`ESTIMATE_FUNC` carries entries for qwen2, llama, qwen2_moe, the qwen3 family, deepseek_v3, minicpm, mistral, gemma3_text, seed_oss, apertus and glm4v. It has no `kimi_k3` and no `kimi_linear`, and both K3 configs on this box report `model_type: "kimi_k3"`. So MFU would read 0 for K3 on an H100 with a real batch and a hundred steps, exactly as it does here.

That splits item 12 in two. The step time and peak memory halves need the card, as recorded. The MFU half needs an estimator entry for K3, which is local work and is not blocked by hardware at all.

Writing that entry is a task rather than a line: K3 is MLA plus a latent MoE plus KDA linear attention, and `_estimate_deepseek_v3_flops` is the nearest template but covers MLA and MoE only. A formula that looks plausible and counts KDA wrong produces a confident wrong MFU, which is worse than the honest zero, so it is left here as the named next step with its template identified rather than guessed at tonight.

## What changed

Item 11's blocker is confirmed and renamed: an artifact and disk, not a card. Item 12 splits: two of its three numbers wait for the card, and the third waits for code that can be written on any machine.

## The MFU half is now written

Deferring it was stopping short of what the machine can do, so it is done: `_estimate_kimi_k3_flops` in `verl/utils/flops_counter.py`, registered for `kimi_k3` and `kimi_linear`, committed to `kimi_k3_integration_rebased` as `515b162c` and carried into patch 05, which grows 754 to 855 lines.

It follows the schedule the config states rather than an average, because K3 alternates two attention kinds and averaging them would be wrong in both directions. `full_attn_layers` take the deepseek_v3 MLA term. `kda_layers` take KDA's own: q, k and v projections at `kda_num_heads * kda_head_dim`, the output projection back to model width, the two-stage forget gate through `forget_a` and `forget_b`, `beta`, the output gate, three depthwise short convolutions, and the delta-rule state, which is read and written once per token at head_dim squared. KDA is linear attention, so only the MLA layers enter the quadratic term; putting KDA there would have inflated long-sequence numbers by the thing the architecture exists to avoid.

The MoE branch handles both shapes the tree produces. With `routed_expert_hidden_size` set, the routed experts run at that width behind a down and an up projection and the shared experts stay at model width, which is the latent MoE; without it, the plain form. The adapter maps `routed_expert_down_proj` and `routed_expert_up_proj`, so the released layout carries them, while the debug artifacts on this box do not and take the fallback.

**It was checked rather than asserted.** For `k3mini_hf` the formula's active parameter count is 261.1 M. The checkpoint holds 422.1 M, but 220.2 M of that is the routed experts of which a token uses 8 of 32; scaled that way the checkpoint's active count is 256.9 M. The two are 1.6 percent apart, and the residual is norms, convolution kernels and biases, which the formula does not count and which do not enter a matmul FLOPs term.

End to end the counter now builds for K3 without its warning and returns 13.477 TFLOP/s for four sequences of 2048 tokens in a second.

One thing this does not fix, and it is worth knowing before the H100 session: `get_device_flops` returns infinity for an unrecognised card, and this box's RTX 5060 Ti is unrecognised, so MFU still divides by infinity here and reads zero. H100 and H200 are in that table at 989 and A100 at 312, so on the card the PR targets the ratio is real. MFU had two causes and this closes the one that would have followed the work to any machine.

## Item 11's premise, tested from data already on disk

The item rests on a claim rather than a measurement: that the engine's rollout-versus-actor log-probability difference of 0.15 "means nothing" because the debug model's weights are random. That claim is checkable here even though the cell it asks for is not, and it holds.

Trajectories read off runs that already exist, no new compute:

    K3 debug, fsdp2 x tp2 x ep2        0.1551  0.1491  0.1462
    K3 debug, image dp2 cp2 tp2 ep2    0.1658  0.1640  0.1506
    K3 debug, image drop, no images    0.1814  0.1542  0.1684
    Qwen3-0.6B, real weights           0.0149  0.0147  0.0149  0.0144  0.0147

Two things follow. The same engine reads **0.0147 on a model with trained weights and 0.15 to 0.18 on one without**, an order of magnitude apart, so the 0.15 is a property of the weights and not of the transport. And the K3 debug figure **falls** as training proceeds, 0.1551 to 0.1462 over three steps, while the real-weight figure is flat, which is what untrained weights settling looks like.

What this does not do is test the K3 path with real weights, because that needs the artifact. It narrows item 11 from "unmeasured" to "premise confirmed on this engine, one architecture-specific cell outstanding", and it means the expensive cell is being run to confirm a number rather than to discover whether the approach works.

A longer debug run is going, thirty steps rather than three, to see whether the K3 figure keeps descending or flattens well above the real-weight regime. Either answer is useful: continuing descent supports the reading above, an early plateau would say something about the K3 path specifically and would be worth knowing before anyone rents a machine.

### The long debug run answers in eight steps, and the answer is that it cannot go further

Thirty steps were asked for; eight were enough, and the run was stopped there rather than spending the rest.

    step            1        2        3        4        5        6        7        8
    diff mean    0.15670  0.14784  0.14994  0.14872  0.14947  0.14962  0.14806  0.14645

Read alone that looks like a plateau at 0.149, an order of magnitude above the real-weight 0.0147, and the tempting conclusion is that the K3 path has a floor there. The control says otherwise:

    actor/grad_norm    1.101 1.115 1.132 1.126 1.123 1.128 1.126 1.131
    actor/entropy      11.52 11.52 11.52 11.52 11.52 11.52 11.52 11.52
    critic/score/mean  0.869 0.867 0.872 0.874 0.873 0.872 0.866 0.870

The policy's entropy is identical to four significant figures across all eight steps and the gradient norm is flat. The weights are not moving in any way that changes the model's behaviour, so the plateau measures the weights standing still, not a property of the transport. The first step's drop from 0.157 to 0.148 is the only real movement in the run.

That closes this line of attack rather than extending it: GRPO on the debug model does not train it enough to stop being random, so no number of steps here turns a random-weight model into the real-weight cell the item asks for. The cross-model comparison, 0.0147 on trained weights against 0.15 on untrained ones through the same engine, remains the evidence that the premise holds, and the architecture-specific confirmation still needs the artifact.

Worth keeping as a method note: the trajectory on its own supported a conclusion the control refuted. A flat metric is not evidence about the thing being measured until something independent says the system was actually moving.
