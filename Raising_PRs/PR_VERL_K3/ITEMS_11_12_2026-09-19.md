# Items 11 and 12, checked rather than assumed

Both were carried as "needs the H100 session". One of them does. The other is partly a code gap that can be closed anywhere, and the reason recorded for it is wrong.

## Item 11 really does need an artifact this box does not have

The item asks for a real-weight cell, "the released checkpoint or the 48B graft", because the engine's rollout-versus-actor log-probability difference of 0.15 on the debug model means nothing against the 2e-3 floor quoted at 2.8T.

Nothing on this machine satisfies it. The K3 artifacts here are downscales: `k3mini_hf` is 1.6 GB, `k3qat_mm_hf` 231 MB, `k3mini_vl_hf` 334 MB, `k3mini_text_hf` 155 MB, `packed_mxfp4_ckpt` 9.3 MB. The 48B graft in bf16 is about 96 GB against 80 GB free. The HuggingFace cache holds Qwen3-0.6B and Qwen2-7B, which are real weights but not K3, and substituting a Qwen cell would answer a different question as well as run against the standing instruction not to run Qwen unasked.

So item 11 stays open, and what it is waiting for is an artifact plus the disk to hold it, not a faster card.

## Item 12's MFU is not a shape problem

The item records that "MFU reads 0.0 here, the debug model's shapes defeat the estimator". That is not the reason.

`verl/utils/flops_counter.py:715-718` gates on the model type, not on shapes:

    VALID_CONFIG_TYPE = ESTIMATE_FUNC.keys()
    if config.model_type not in VALID_CONFIG_TYPE:
        ... "MFU will always be 0"

`ESTIMATE_FUNC` carries entries for qwen2, llama, qwen2_moe, the qwen3 family, deepseek_v3, minicpm, mistral, gemma3_text, seed_oss, apertus and glm4v. It has no `kimi_k3` and no `kimi_linear`, and both K3 configs on this box report `model_type: "kimi_k3"`. So MFU would read 0 for K3 on an H100 with a real batch and a hundred steps, exactly as it does here.

That splits item 12 in two. The step time and peak memory halves need the card, as recorded. The MFU half needs an estimator entry for K3, which is local work and is not blocked by hardware at all.

Writing that entry is a task rather than a line: K3 is MLA plus a latent MoE plus KDA linear attention, and `_estimate_deepseek_v3_flops` is the nearest template but covers MLA and MoE only. A formula that looks plausible and counts KDA wrong produces a confident wrong MFU, which is worse than the honest zero, so it is left here as the named next step with its template identified rather than guessed at tonight.

## What changed

Item 11's blocker is confirmed and renamed: an artifact and disk, not a card. Item 12 splits: two of its three numbers wait for the card, and the third waits for code that can be written on any machine.
