### Where this stands

Since K3's release we have been building the parallelism side against the full architecture -- KDA, Gated MLA, Stable LatentMoE, Block Attention Residuals, and the MoonViT-V2 vision pathway. That work is complete and running, and we are posting it now as early evidence rather than waiting for the eager reference (#4025) to land.

Branches (fork `QIU023/torchtitan`), all currently carrying the complete implementation; they will be sliced per-topic and rebased onto `torchtitan/models/kimi_k3/` once the eager reference lands:

| slot | scope | branch |
|---|---|---|
| A | TP: KDA NoParallel, Gated MLA, LatentMoE placements | `k3_pr_a_tp_kda` |
| B | EP + grouped GEMM | `k3_pr_b_ep_grouped` |
| C | PP + Block AttnRes cross-stage adapter | `k3_pr_c_pp_attnres` |
| D | CP: Ulysses for MLA, fla's merged KCP for KDA | `k3_pr_d_cp_ulysses` |

The dev branch also carries work outside those four slots that exists today and is not proposed for upstreaming in this pass: LoRA, Muon, quantile balancing for the router (report sec 2.3.3), and MXFP4 QAT.

### Results

Multimodal debug model, seed 42, `--debug.deterministic`, gradient accumulation on. Two model configurations: the eager reference's debug architecture, and the same with the report's trailing Gated MLA appended so the final layer is global (`full_attn_layers = [4, 8, 12, 13]` at debug depth, mirroring the released list's `[..., 92, 93]`).

Degree-2 matrix, thirteen configurations -- `dp1`, `fsdp2`, `pp2`, `cp2`, `tp2`, every 3-of-4 combination of FSDP/TP/PP/CP, and the same again with EP:

| | eager | compiled |
|---|---|---|
| 3 steps | 13/13 | 10/13 |
| 10 steps | 13/13 | -- |
| 100 steps | 13/13 | -- |
| 100 steps, report architecture | 13/13 | 10/13 (3 steps) |

Max-degree cells on top of those, 3 steps, run without changing the config:

| cell | |
|---|---|
| `ep8_fsdp8` | passes -- 8 experts over 8 ranks is one expert per rank, so empty expert groups occur every step |
| `pp4` | passes -- 13 layers over 4 stages is uneven, vision tower entirely on stage 0 |
| `tp4`, `cp4` | pass -- one attention head per rank |
| `pp8` | **fails**, see below |

So **17 of 18 attempted**, not 13 of 13. Cells the config cannot express are recorded rather than accommodated: `tp8`/`cp8`/`tp4 x cp4` have only 4 attention heads to shard, and `pp8 x vp4` cannot host 32 virtual stages on 13 layers. High-degree coverage on our own flavors (tp8, cp8, PP8xVP4, EP@896) exists separately.

Step-1 losses span 12.0385 to 12.0797 across the degree-2 set, against `ln(163840) = 12.006`. Two independent full matrix runs agree bit-for-bit on every leg.

`pp8` over 13 layers is an open defect on our side, stated rather than omitted: torch's pipeline P2P rejects a gradient receive buffer as non-dense (`[1, 256, 256]` with stride `[256, 768, 1]`). `pp2` and `pp4` pass on the same model and `PP8xVP4` passes on our 32-layer flavor, so pipeline degree 8 is not broken generally; the 13-layer split is. Cause not yet established.

Three qualifications, stated here rather than left for someone to find:

1. **The 100-step run overfits a smoke dataset** (12.06 -> 0.37). It shows thirteen configurations behaving consistently and stably over that window; it is not a convergence result. Real curves need a real pretraining run, which is queued.
2. **The three compiled failures are one upstream cause, not ours.** `torch._grouped_mm` rejects an operand whose contraction dimension is zero, which is the shape the weight-gradient form takes when an expert group is empty. Five-line reproduction with no model, no compile and no distributed; being filed against pytorch/pytorch separately. Empty groups themselves are fine in both modes.
3. **The model used for the matrix is the eager reference's debug architecture, not the report's.** One difference, which we are raising on that PR as a config-level question: its final layer is KDA where report sec 2.1 places an additional Gated MLA "ensuring that the final layer always performs global attention". Our own configs implement the report's layout; we ran the matrix on theirs deliberately, so the comparison is our parallelism against their model rather than two different models.

One shared-code fix already came out of running this matrix at the gradient level: on the TP-without-EP legs (`tp2`, and every FSDP/PP/CP combination with EP off), gradients below the routed experts came back systematically under-reduced -- a 3.10x whole-model grad_norm gap at dp2 x tp2, invisible in loss curves because Adam is scale-invariant. The root cause is in the shared MoE sharding config, reproduces on unmodified deepseek_v3, and is filed with the per-parameter evidence as #4054. The EP-on legs were never affected.

### The interfaces the PP and EP slices touch, and who adds them: we do

Nothing to merge yet and nothing we are asking anyone to build.

**PP (slot C).** The eager reference's decoder loop already threads the right pair -- `(h_BLD, block_residual_TND)` in and out of every layer -- so the PP slice needs only two seams: the block-residual stack is currently created inside the forward (a stage cannot pass an incoming stack in), and the loop always runs all layers. **Our PP PR adds both** -- an optional initial-stack argument and a layer-range slice, returning the pair when the range stops short -- as its first, separately reviewable commit.

**EP (slot B).** The released checkpoint stores routed experts per-expert; grouped-GEMM training wants them stacked on the expert dimension. The conversion already exists on `k3_pr_b_ep_grouped` and ships with that PR: a bidirectional key map over the full released key set, including the sliced-tensor indexing where one released key maps to one slice of a stacked tensor (`...experts.3.w1.weight <-> w1_EFD[3]`), plus the grouped experts module itself. It composes with the eager per-expert adapter rather than replacing it -- both layouts stay loadable and savable.

Stated here so the interfaces are on the record before those PRs open. TP and CP need no seam at all and rebase cleanly.
