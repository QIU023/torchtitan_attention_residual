## 报告原文（K3 技术报告 5.2.3）

> A single large image is partitioned along the patch dimension across multiple devices, and attention is computed by gathering key–value pairs (gather-KV) across CP ranks. In addition, we divide each CP group into several sub-CP groups and distribute multiple large images across them in a load-balanced manner, preventing the communication fraction from growing with scale.

报告只规定大图怎么处理，没有写小图怎么编。所以小图沿用 main（#4639）的做法，每个 CP rank 都整张编码。

## `923f8bd47` 的两个问题（移植时一起修）

1. **非 PP 时会卡死。**
   - 开 CP 后，旧代码对每张复制编码的图单独调用一次 tower（`_replicated` 逐张循环），切分的大图再按子组各调用 n_passes 次。
   - 不开 PP 时，tower 是单独的 FSDP 单元，默认 `reshard_after_forward=True`，每次调用都在 dp_shard × cp 的 FSDP mesh 上做一次 all-gather。
   - 所以只要不同 DP rank 的图片数不同，或者大图分到各子组的张数不均，各 rank 的 all-gather 次数就对不上。
   - 最小复现：2 卡、一个 FSDP 单元，rank 0 调用两次、rank 1 调用一次，NCCL watchdog 超时（scratchpad `fsdp_callcount_probe.py`）。
   - 09-22 的矩阵没暴露这个问题，因为 cc12m-test 每个 micro-batch 恰好一张 192 patch 的图。main 自己用 dummy 输入保证每个 micro-batch 恰好调用一次 tower（#4777）。
2. **多子组时重复编码。** `rest` 里不只有小图，还有分给其他子组的大图，这些大图会在本 rank 上整张再编一遍。数值上是对的，但抵消了分组的意义，也是问题 1 里调用次数不均的来源之一。

## 新设计（`wt_cpmm_1006`）

- **tower 只调用一次：**
  - 每个 micro-batch 只调用一次 tower，和 main 一样，所以 FSDP 的调用次数在所有 rank 上天然一致。
  - 打包后的流是：前面是要整张编码的图（小图，或者高度不能按 merge block 切的图），后面是本 rank 所在子组里每张大图的行带（每一帧同样的行，按 merge block 切，尾部 rank 用重复行补齐）。
- **attention：**
  - `KimiK3VisionCPAttention` 收到 `VisionCPLayout` 时，只对行带部分在子组内 all-gather K/V（子组大小为 1 时不 gather）。
  - 用一个按图编号的 BlockMask：小图只看自己，大图看自己所有 rank 上的真实行，padding 行的编号是 −1，谁都匹配不上。
  - 收到普通 BlockMask 时，直接走父类。
- **拼 bank：**
  - tower 输出后，各子组行带的 merged 特征补齐到同一长度，在整个 CP 组做一次 all-gather；每个 rank 按规划把每张大图的真实行按 rank 顺序拼回去，和整张图的 raster 顺序一致。
  - 返回的 bank 和 main 一样，按原图顺序排列，所以 `_prepare_multimodal_embeds` 一行不用改。
- **没有大图时：** 就是 main 的单次调用，逐位相同。
- **代码位置：**
  - 子组在 `KimiK3Model.parallelize` 里建（collective，所有 rank 都要调用，包括 PP 下没有 tower 的 stage），交给 tower 的 `set_cp_subgroups`；
  - 阈值 `dynamic_cp_min_patches` 放在 tower 的 config 里（默认 256）；
  - 不再改 `models/common/vision_encoder.py`（旧版给通用 `VisionAttention` 加了一个忽略的 `cp_plan` 参数）；
  - 不再需要 `fsdp.py` 的 `add_zero_valued_dependency` 和 `_PlainGradBoundary`。
- **纯规划** 在 `vit_cp_plan.py`：`plan_dynamic_cp`、`key_runs`，加上原来的 `row_partition` / `subgroup_layout` / `balance_images` / `classify`。

### 10-08 阈值（默认 `dynamic_cp_min_patches` = 256）要不要改（用户："2的实验还需要H100吗 ... 我希望你先解决2"）

- **生产路径不编译 tower：** K3 的 `local_compile_regions` 只编 loss、gated_rmsnorm、fused_binary_activation、fp32_to_bf16_split；tower 的 block 是 eager 加 SAC（`policy.apply(self.vision_encoder)`），只有 flex 单独编译。所以 tower 基准里的 SAC 数就是生产路径上 tower 的表现。
- **为什么单张中等图会慢（profile，1008 px，CP2，SAC，`results_h100_1008/thr/prof/`）：**
  - main 一步 GPU 85.6 ms、CPU 168 ms，受 CPU 限制；本 PR 的 GPU 计算 49 ms，但每步多了 109 次 all-gather 和 55 次 reduce-scatter（27 层 × K、V × 前向和 SAC 重算，加一次 bank gather）。
  - 微基准（`gather_bench.py`，rank 同步）：一次 gather 加反向不论 3.8 还是 30 MiB 都是约 650 µs；换成 spmd 的单张量接口（main 的 CP attention 用的 `spmd.redistribute`）约 850 µs，强制 `NCCL_PROTO=Simple` 或 LL128 也不变（NCCL 2.29.3，P2P/CUMEM，NVLS 可用）。所以不是 NCCL 协议或接口，是 eager 下每次 collective 在 c10d 里约 200 µs 的 CPU 开销；profile 里 NCCL kernel 1.2 ms 的平均时长主要是在等对端。
