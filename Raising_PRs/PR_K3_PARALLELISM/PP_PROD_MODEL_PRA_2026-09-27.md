# 生产模型：PR A 之后的 2.8T 显存（2026-09-27）

**全部是模型值**，出自 `pp_prod_model_2026-09-27.py`（在 09-24 版 `pp_prod_model_2026-09-24.py` 上加了 `pra` 方案），没有任何实测。原始输出 `prod_pra_*.out.txt`，汇总 `prod_pra_summary_2026-09-27.txt`（由 `prod_pra_summary.py` 生成）。

运行：`PYTHONPATH=<含 kimi_k3 layout 的 checkout>:. python pp_prod_model_2026-09-27.py --recipe {fullac,report} --only <布局> [--host-gbps 25] [--unfused]`；`--consistency` 打印下面的一致性检查。

## `pra` 方案改了什么

- **rank store：** 每个 block 一块，从它到达（接收）或开出来（提交）起，到把它带进本 rank 的那个 stage 的反向结束为止。
- **开 block 不再复制 stack：** 每层 checkpoint 只多存一个 [T, D]，没有 stack 副本。
- **输入梯度 send：** 在第一个能证明对端已收到的前向时 wait。
- **其余不变：** 静态显存、反向临时量、hidden、host 和网卡链路、offload 与 balance 的搜索。
- **回归检查：** 表里的对照行 "V4 + early grad wait" 与 09-24 的汇总逐位相同。

## 结论

- **(a) FullAC，PR A 之后，H100 不 offload 放不放得下：** 聚合融合时放得下（PP8 × VP4 最大 71.1，PP16 × VP2 最大 70.6，HBM 74.5）。现在代码里的聚合不融合（整体转 fp32），反向临时量在峰值处多约 14 GiB，PP8 × VP4 最大 83.7，放不下；加 offload 也只到 77.1，还是放不下，因为临时量搬不走。所以 FullAC 在 H100 上的下一个杠杆是聚合的临时量，不是 offload。
- **(b) 报告配方，PR A 之后：** 必须 offload（PP8 × VP4 不 offload 最大 251.0）。host 50 GB/s 时放得下（聚合融合 64.6；不融合 78.6，放不下）；host 25 GB/s 时链路饱和，最大 195.3（PP16 × VP2 为 240.7），放不下。
- **(c) balance：**
  - 叠在 offload 上：所有 host 50 的场景都没有收益；唯一有变化的是 H100 PP8 × VP4 报告配方 host 25，最大从 195.3 到 194.4，离 HBM 还差得远。
  - 单独用：只在各 rank 不均时削最大值（FullAC PP8 × VP4 71.1 → 70.1，PP16 × VP2 70.6 → 69.2，均值基本不变；报告配方 PP8 × VP4 251.0 → 239.9，PP16 × VP2 289.6 → 278.5；GB300 PP4 × VP4 报告配方 257.4 → 253.2），GB300 FullAC 和 PP2 × VP8 上没有收益；没有一个场景因为 balance 从放不下变成放得下。
- **(d) 假设：**
  - host 链路每卡每方向 H100 50 GB/s（敏感性 25 GB/s，两卡共用 PCIe 交换芯片），GB300 200 GB/s；
  - 网卡 400 Gb/s，H100 上一半留给 EP 的 all-to-all，GB300 上 EP 在 NVL72 内，全部留给 PP；
  - AttnRes 聚合默认按融合 kernel 算，反向临时量 FullAC 40 个单位、报告配方 20 个单位；不融合时每个 block 条目再加约 16 个单位（fp32 的 values、keys 和乘积，每层两次聚合，估计值，没实测）；
  - 报告配方：逐元素算子重算，其余 FP8 存储，每层约 15 个单位可搬；
  - 单位为 8192 × 7168 bf16 = 0.109 GiB；8K token 一个 micro-batch，EP 按表中布局。
