# PP lower bound 这条线：三步的实现与测量（2026-09-26）

用户定的顺序：①pp_review_optimize（rank store 到下界）→ ②引入统一内存管理器 → ③offload 和 balance 一起做。每一步都测三样：cache 显存（rank store 高水位和每个 rank 的峰值）、fwd/bwd 耗时、通信与计算的重叠。

**数字说明：**
- 下面的数字全部是 8 × RTX 5060 Ti 实测。
- 切分用的是生产切分：93 层、block 12、pp8 × vp4（32 个 stage）。只把 dim 缩到 2048、seq 缩到 2048。其余设置：M16、FullAC、seed 42、deterministic。
- 显存取第 5 步，它和第 3 到第 20 步完全相同。
- 耗时取被追踪的第 8 步。
- H100 还没有测，原来那台机器的 host key 变了，公钥也被拒。
- 测量套件在 `kit_pp_lowerbound_2026-09-26/`（见其中的 README）。

## ① PR A：按 block 传输和存储，在 bringer 反向时释放

**改了什么：**
- 模型的 block 残差从 [T, N, D] 张量改成 [T, D] 的列表，开 block 时追加，不再复制整条 stack。聚合在函数内部现拼，数值不变。
- 每一跳按 block 发，每个 block 一个张量。收到的 block 就是它的接收缓冲，本 stage 产生的 block 就是模型自己的张量；store 只存引用。
- 每个 block 在把它带进本 rank 的 stage（bringer）反向结束时释放。
- 同时修掉了 diff 审核里的几处问题：µfmt；测试类放在 main guard 之后；注释；接收方默认连续行；dtype 取自 hidden；靠 `dim() == 3` 认 payload。另外补了单 stage schedule（1F1B）的数值测试，以及"每个 block 由 bringer 释放"的测试。

## ② 统一激活存储

**改了什么：**
- `torchtitan/distributed/activation_storage.py`（新）：所有被 autograd 保存的张量都经过 `torch_remat.saved_tensors_hooks`，由策略给每个张量选后端。选择推迟到 stage 前向结束时再做，这样前向中途才被 store 登记的 block 一定留在 GPU 上。
- rank store 在放入 block 时向管理器登记，释放时注销。
- 由 `KimiK3Model.Config.pp_memory.manager` 打开。这一步不配任何后端，没有后端时 pack 直接返回。

**显存：** 8 个 rank 的峰值和 PR A 完全相同（5.14 到 6.82 GiB）。管理器登记的 block 峰值是 0.39 到 0.49 GiB，比探针统计的 store 高水位（0.70 到 0.86）少的那部分是梯度 deposit：登记只算 block。

**数值：** 20 步 loss 和 grad norm 与 4312 逐位相同。

**耗时（ms，均值）：** 一步 22773（PR A 22755），计算 7408（7407），前向 1741（1744），反向 5633（5630），NCCL 驻留 15172（15219），重叠 2377（2394），暴露的通信 12795（12825），tps 179（180）。管理器没有可测的开销。

**09-26 修复：** 第三步的诊断（§4）查出管理器的一个问题。装了后端之后，留在 GPU 上的保存也会被管理器多握一段时间：要到反向走到上一层才放，而没有管理器时 autograd 在用完后立刻就放。现在只有真正搬走的保存才登记进管理器，留在 GPU 上的交给 autograd；`_unpack` 和 `finish` 里也调用 `_drain()`。这个修复在第二步的提交里（`7b43e1d01`）。第二步本身不配后端，第三轮重测的结果和修复前逐字节相同：显存和 PR A 一样，20 步逐位一致，一步 22793 ms，tps 179。

## ③ offload 与 balance 一起做

**改了什么：**
- 加入 host 后端和 mooncake 远程后端。远程池由各源的跨度首尾相接拼成，每段按该源同时停放的最大字节数定。
- 加入 `MemoryPlan` 和 `PPMemoryController`：第 1 步什么都不搬，只做 profiling，记录每个计算动作的峰值和耗时，以及每个 (stage, micro-batch) 可搬的字节数；第 1 步 `step()` 返回后，各 rank 交换 profile，各自算出同一份计划，从第 2 步起执行。
- 由 `pp_memory.offload`、`pp_memory.balance` 打开。

**第一版的测量（第二轮，已被修复取代）：**
- 数值和第二步逐位相同。
- 显存几乎没降：最大值 6.82 → 6.75、均值 5.91 → 5.88 GiB。可计划写的是 rank 7 从 6.12 降到 5.58（第 1 步没有 AdamW 状态，比稳态少 0.70）。
- 计划：rank 7 停 23 个条目到 rank 0，rank 3 停 11 个到 rank 2，rank 5 停 1 个到 rank 1。每个条目 24 MiB，即 3 层的 FullAC 输入。

**已定位的两个原因（§4）：**
1. **源张量释放得晚。** 源张量只在 `_drain()` 时释放，而它只在前向保存或预取时才跑，步末只剩反向时就很少调用。再加上 5060 走 TCP 的拷贝比预算的 2 GB/s 慢。结果进入 31B15 前实际只少了 0.36 GiB，计划以为是 0.54。
2. **stage 31 最后两个反向里多出 0.29 GiB 的临时量。** 输出头的 AttnRes 聚合不在 checkpoint 里，它存的 fp32 张量有好几个 [T, 9, D]（每个约 151 MB），被记在第 92 层名下。管理器又多握了它们，一直等到第 92 层反向做完才放，正好压在峰值上。修法见第二步的"09-26 修复"。

- **计划与实测：** 最重的 rank 7，profile 峰值 5.83 GiB，计划降到 5.29（−0.54），稳态实测 −0.36。剩下的差距对应 5060 上 TCP 拷出比预算的 2 GB/s 慢。计划用的带宽应该按机器实测来设。

## 4. 定位：峰值落在哪里

**方法：** 用 `PPMEM_ACTION_TRACE` 逐个计算动作记录动作内峰值、动作后的显存和 store 字节数（`diag_actions.py`、`peak_where.py`）；再用 `replay_plan.py` 读回计划器的输入，离线重算计划，和实测逐动作对照。

**PR A 之后，每个 rank 的峰值都在这一步的最后一个反向：** 它最高那个 stage、最后一个 micro-batch（rank 7 是 31B15，rank 0 是 24B15）。动作内的最高峰值和显存格子的整步峰值完全相等，所以峰值在 PP 的动作里，不在优化器那一步。这时：
- 其他 micro-batch 的激活和 block 基本都已释放；
- 步末剩下的是参数、梯度和优化器状态，约 2.7 到 4.5 GiB；
- 峰值就是这部分加上这一次反向的临时量；store 当时只剩 0.62 到 0.75 GiB。

**V4 的情况：** rank 0、1、2、4 的峰值在步中间（16B1、17B1、18B1、28B9），那时激活和 block 都还在。所以去掉 `cat` 副本后 rank 0 和 4 降了 1.3 到 1.4 GiB；其余 rank 本来就是步末的峰值，store 再省也碰不到。

**这对下界这件事意味着什么：**
- 在这个配置下（dim 2048、FullAC，每层只存一个 [T, D] 输入），PR A 之后 cache 已经不是决定峰值的那一项。
- 要继续压峰值，该降的是最后一个反向的临时量（`PP_LOWER_BOUND_PLAN_2026-09-25.md` §2 第 6 条：聚合整体转 fp32 的临时量）和静态显存。
- H100 生产尺寸下，激活比例大得多，报告的配方是每层约 15 个单位，结论可能不同，要在 H100 上测。
