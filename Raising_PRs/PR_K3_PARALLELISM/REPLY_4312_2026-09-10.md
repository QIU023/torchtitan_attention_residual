--- REPLY 1 (thread on `pipeline_stage.py`, the two options) ---

Thanks for laying the two options out. The PR is a third shape, and it is worth stating exactly, because it is what the tech report calls "cache-based pipeline communication" and it decides the message volume:

- Traffic stays on adjacent edges only (the schedule's own P2P, no skip connections, no new communicator), so the topology is your option 2.
- But no hop ever carries a block the receiving rank already holds. Each rank keeps the blocks it has seen in a per-rank store keyed by the micro-batch id, and a routing table (`layout.py`, a pure function of the layer split and the stage->rank map, computed identically on every rank before the first send) says for every hop which blocks the next rank still lacks. So a block committed at stage S is on the wire for at most P-1 hops, once per edge, and then every rank has it; that is option 1's volume (each block reaches each later rank exactly once) without option 1's non-neighbour sends.

Per micro-batch, per edge, the payload is `hidden [T, D]` plus the missing blocks `[T, k, D]`:

- plain 1F1B (one stage per rank): edge s -> s+1 carries every block committed on stages <= s, because rank s+1 has seen none of them. With 93 layers in blocks of 12 (8 blocks) over pp=8, that is 1, 2, ..., 7 blocks on edges 1..7: the last edge carries 8 x [T, D] against the standard 1 x [T, D]. This is the "[PP degree] times" you describe, and it is per micro-batch, not only the first, because blocks are activations of that micro-batch. It is bounded by the block count (8 for K3), not by the layer count, and `attn_res_cache=False` in the PR is exactly the naive variant (every hop carries the whole stack) that every results table runs as the A/B: same losses bitwise, the difference is bytes.
- interleaved (V virtual stages per rank, S = v*P + R): a block is fresh on the wire for P-1 hops and afterwards served from the store on every rank, so the per-hop payload is bounded by the commits of the last P-1 stages, not by the stage index. pp8 x vp4 with the 33-layer debug model carries at most 2 blocks per hop.

On contention: nothing is sent to a non-neighbour, so there is no fan-out from rank 0; the cost is the larger message on the late edges of plain 1F1B, which interleaving removes. On multi-node this shape is also what keeps the schedule STATIC (no metadata on the wire), which the transport work with @elfiegg on top of this head relies on.

Memory follows the same table: a rank releases a stored block when the micro-batch's backward on that rank has consumed it (the store is keyed by micro-batch, the slot goes with the backward), which is the report's "released as soon as the micro-batch finishes".

Agreed that #4486 is not the route for this; the design note lists what the library would need (a multi-consumer output, rank-local delivery for same-rank consumers, the micro-batch id in the hook context, dense backward buffers) if this pattern spreads, and I am happy to walk through it on a call at any time that suits you.

--- REPLY 2 (thread on `model.py` L222, the activation policy) ---

Yes to the first part: every layer reads all earlier blocks, the stack is materialised once per block boundary, and the redundancy is bounded by the block count. Concretely, with your example, 2 blocks of 4 layers (layers 0-3 in block 0, 4-7 in block 1), one micro-batch of T tokens, width D:

Forward, what exists after each layer:

- Layer 0 (block 0 starts): the stack is `cat(embedding)` -> `stack0 [T, 1, D]`, the partial block is empty. Each layer does two reads, before attention and before the FFN: `read(partial, stack) = softmax over the stack's blocks (plus the partial) of a learned query` -> `h [T, D]`, then the sub-layer over `norm(h)`, then the partial accumulates the sub-layer's output. Autograd saves per layer what a standard pre-norm layer saves (the norm inputs, the attention and FFN inputs, the attention/FFN internals) plus, per read, the read's softmax weights `[T, b]` (b = blocks in the stack, tiny) and a reference to `stack0` and to the partial. `stack0` is one tensor shared by all four layers of block 0 and by everything downstream; the references cost nothing extra.
- Layers 1-3: the same, still on `stack0`; the partial is a running sum of the layer outputs of block 0 (a fresh `[T, D]` per layer, held because the next layer's read and the residual add use it).
- Layer 4 (block 1 starts): the partial of block 0 is committed: `stack1 = cat(stack0, partial) [T, 2, D]` (a new tensor; `stack0` stays alive because block 0's layers' backward needs it). Layers 4-7 read `stack1` and a new partial.
- End of forward: alive stacks are `stack0 [T,1,D]` and `stack1 [T,2,D]`, i.e. 1 + 2 = 3 block rows; for K3's 8 blocks it is 1 + 2 + ... + 8 = 36 rows of `[T, D]`, against 93 residual-stream tensors a standard model of that depth would hold anyway. The two reads per layer add `2 x [T, b]` softmax weights and no `[T, D]` copies: the read's output `h` is the norm's input, which a standard layer saves too.

Backward, when things are released:

- Backward runs layers 7..0. `stack1` is released after layer 4's backward (its last reader); `stack0` after layer 0's backward. A partial's `[T, D]` tensors are released as their layer's backward passes.
- The read's backward is the transposed softmax mixing: the gradient of `h` is scattered to the stack rows and the partial with the saved weights, plus the query's gradient from the saved logits; no recompute is needed for that in this PR.

Recomputation: this PR does not checkpoint the residual read (the saved set above is the whole story). The report's "AttnRes entirely wrapped with checkpointing" corresponds to a follow-up on the integration branch, `ac_reuse_attention` with a checkpoint wrapper on the residual math: selective AC wraps only the MoE / feed-forward, the attention and the residual math keep their activations, which drops the recompute of the KDA kernel that a whole-block wrap would cause; the read is recomputed from (partial, stack) in backward there. I kept it out of this PR to keep the diff to the stage; it is a separate small PR.

Under PP the same policy holds per stage and per micro-batch; the only addition is that a block received from another rank lives in the rank store as a value (no upstream graph) until the micro-batch's backward on that rank has consumed it, and its gradient rides the schedule's backward P2P back to the producer (the deposit slot handles the same-rank case of interleaved schedules).
