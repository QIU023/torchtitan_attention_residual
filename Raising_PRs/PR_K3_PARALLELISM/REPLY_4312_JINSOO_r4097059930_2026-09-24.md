## The position and its cost (not for pasting)

- **Principle.**
  - The function consumes the knob: it is an input of `_get_pipeline_metadata`, the same call that sizes the split.
  - It would overwrite a configured split, which is an output.
  - Refuse only what it would overwrite. That also meets tianyu's principle, since nothing of the user's is overridden when the knob stays on the copy.
- **Cost of keeping the refusal for Kimi K3, the main case** (CPU probe `scratchpad/lps_probe_k3.py`: the released 93 layers, pp8, Interleaved1F1B, the end modules pinned):
  - the default gives 16 stages (vp2);
  - `layers_per_stage=3` gives 32 stages (vp4) on `901ef34de`, and `ValueError` on `dbd13d397`;
  - the 2.8T sizing's H100 PP8 x VP4 and GB300 PP4 x VP8 (both modelled) are both 32 stages, which is `layers_per_stage=3`;
  - with the refusal, a K3 recipe must spell out the 32-part split.
- **Cost for the other models on the path**, a regression against main:
  - `qwen3_5`, plus `qwen3_6` and `qwen3_8`, which build `Qwen35Model`;
  - `kimi_k2_7`;
  - `muse_glimmer`.
  - Only llama3 recipes set the knob, so CI never showed it.
- **What keeping the refusal buys:** nothing technical once the both-set check is gone. tianyu's lgtm is not a reason on its own; it was conditional on every reviewer.
- **The split half stays on the same principle.** It guards direct callers: `BaseModel.pipeline` and `pipeline_kimi_k3` never pass a configured split in.

> What is the reason for rejecting `pipeline_parallel_layers_per_stage` already being set?

It came from @tianyu-l's review ([here](https://github.com/pytorch/torchtitan/pull/4312#discussion_r4056259393)), where it replaced a silent override, and nothing needs it now; the latest push drops it. The override was this function clearing the knob on the copy it passed to `pipeline_llm`. The knob had been consumed, not lost: the split was already sized by it through `_get_pipeline_metadata`. The copy dropped the knob only because `dataclasses.replace` re-runs the both-set check in `ParallelismConfig.__post_init__` ([here](https://github.com/pytorch/torchtitan/pull/4312#discussion_r3984964516)). That check has since been removed, and I should have dropped the refusal with it; my reply to tianyu also misstated the split as sized by the default stage count.

The refusal takes the knob away from every model on this path. At Kimi K3's released 93 layers under pp8 Interleaved1F1B, `layers_per_stage=3` gives 32 stages (vp4) where the default gives 16; with the refusal, a recipe has to spell out all 32 parts. `qwen3_5` (with `qwen3_6` and `qwen3_8`, which build the same model), `kimi_k2_7` and `muse_glimmer` derive their split here too, and main accepts the knob for them under PP. CI misses this because only llama3 recipes set the knob.

The split check stays for the opposite reason: a configured split is an output this function would overwrite, so it refuses one, and `BaseModel.pipeline` sends a configured split straight to `pipeline_llm` ([here](https://github.com/pytorch/torchtitan/pull/4312#discussion_r4090997460)). `test_layers_per_stage_sizes_the_derived_split` covers a knob whose stage count differs from the default. @tianyu-l, this reverses the check you asked for after your lgtm, so please take another look: the knob is now honored rather than overridden.
