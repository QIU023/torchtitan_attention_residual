## The position and its cost (not for pasting)

- **Principle.**
  - The function consumes the knob: it is an input of `_get_pipeline_metadata`, the same call that sizes the split.
  - It would overwrite a configured split, which is an output.
  - Refuse only what it would overwrite. That also meets tianyu's principle, since nothing of the user's is overridden when the knob stays on the copy.
- **Cost of keeping the refusal for Kimi K3, the main case** (CPU probe `scratchpad/lps_probe_k3.py`: the released 93 layers, pp8, Interleaved1F1B, the end modules pinned):
  - the default gives 16 stages (vp2);
  - `layers_per_stage=3` gives 32 stages (vp4) on `901ef34de`, and `ValueError` on `dbd13d397`;
  - the 2.8T sizing's H100 PP8 x VP4 and GB300 PP4 x VP8 (both modelled) are both 32 stages, which is `layers_per_stage=3`;
  - with the refusal, a K3 recipe must spell out the 32-part split.
- **Cost for the other models on the path**, a regression against main:
  - `qwen3_5`, plus `qwen3_6` and `qwen3_8`, which build `Qwen35Model`;
  - `kimi_k2_7`;
  - `muse_glimmer`.
  - Only llama3 recipes set the knob, so CI never showed it.
- **What keeping the refusal buys:** nothing technical once the both-set check is gone. tianyu's lgtm is not a reason on its own; it was conditional on every reviewer.
- **The split half stays on the same principle.** It guards direct callers: `BaseModel.pipeline` and `pipeline_kimi_k3` never pass a configured split in.

> What is the reason for rejecting `pipeline_parallel_layers_per_stage` already being set?

It traces back to @tianyu-l's suggestion to error out when a split and `pipeline_parallel_layers_per_stage` are both given ([here](https://github.com/pytorch/torchtitan/pull/4312#discussion_r3984964516)), since `pipeline_llm` then uses the split and silently ignores the knob. This PR put that check in `ParallelismConfig.__post_init__`, which `dataclasses.replace` re-runs, so it also fired on the copy that `pipeline_with_first_stage_modules` from your #4560 writes its derived split into. This function first cleared the knob on that copy to get past the check, and after that was flagged as overriding the user's config ([here](https://github.com/pytorch/torchtitan/pull/4312#discussion_r4056259393)), it refused the knob instead. The result was backwards: the knob alone, which your helper turns into a split through `_get_pipeline_metadata`, was refused for every model on this path, while a split and the knob given together went through unchecked once the `__post_init__` check was dropped.

The latest push restores your helper's behavior: the knob sizes the derived split and stays on the copy, so `qwen3_5`, `qwen3_6`, `qwen3_8`, `kimi_k2_7` and `muse_glimmer` accept it under PP again. The both-given check moves to `TrainingEngine.Config.__post_init__`, which validates the user's config and which the helper's `dataclasses.replace` of `ParallelismConfig` never re-runs. This function still refuses a configured split, since it would overwrite it; `BaseModel.pipeline` sends a configured split straight to `pipeline_llm`.

Kimi K3 needs each input on its own. At its released 93 layers under pp8 Interleaved1F1B, `layers_per_stage=3` gives 32 stages (vpp4), while the 17-layer debug model's vpp4 cell spells its split out, since no knob value gives 8 stages. `test_layers_per_stage_sizes_the_derived_split` and `test_engine_config_refuses_a_split_with_layers_per_stage` cover the two halves. @tianyu-l, this moves your check from the helper to the config after your lgtm, so please take another look.
