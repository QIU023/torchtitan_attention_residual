## Summary

Kimi K3 pipeline ranks balance their memory: from a profiled first step they plan which saves to park in pools on lighter pipeline ranks and, when host offload is on, which to send to host memory, and apply the plan from the second step on.

- `MemoryPlan` and `PPMemoryController` (`kimi_k3/pipeline_parallel/activations.py`): the first step records each compute action's peak, its duration and each stage micro-batch's saved bytes, offloading every eligible save and adding the bytes then off the device back when host offload is on; when that step returns the ranks exchange these profiles and each derives the same plan, which marks the saves it moves `MUST_CPU_OFFLOAD` and routes them.
- `RemoteBackend` (`torchtitan/distributed/activation_storage.py`): a pool on another pipeline rank reached through mooncake's transfer engine, in pinned host memory over `tcp`, and in device memory over `rdma` or over `nvlink_intra` between the GPUs of one node. A pool is its sources' spans laid end to end, each sized by what that source parks at once.
- `KimiK3Model.Config.pp_memory`: `balance` on its own parks and never offloads to host memory; `cpu_offload = "planned"` adds host offload for what no pool takes. With `target_gib`, `host_gbps`, `peer_gbps`, `remote_protocol`. Off by default.

## Design

With balance alone the profiled step keeps every save and its peaks are the timeline the plan starts from. With host offload it offloads every eligible save, so a configuration that only fits when it offloads can start, and adding back what was off the device during each action gives the timeline.

A move lowers a rank's timeline from the action by whose middle its copy out has finished to the action that starts its copy back, both taken from the measured durations and the budgeted bandwidth. The plan takes the rank with the highest peak and moves the largest stage micro-batch whose window covers that peak, to a rank whose peak plus pool stays under the target or else to host memory, and repeats until every rank is under the target or nothing that fits the link time is left. The target defaults to the mean of the ranks' profiled peaks, which is the balanced memory the Kimi K3 report aims for; `target_gib` sets a cap instead.

`CheckpointPolicy` has no value for another rank's memory, so the plan marks a parked save `MUST_CPU_OFFLOAD` like one it sends to host memory, and the storage's route names the pool.

The plan is built after the profiled step returns. A pipeline stage cannot issue the collective inside its last backward: its input gradient send is a later action, and the previous rank waits for it. Core's schedules have no hook after a step, so the controller wraps the schedule's `step`.

## When offloading and balancing pay

Modelled, not measured: the released 2.8T layout at 8K tokens per micro-batch with #4765 underneath, `pp_prod_model_2026-09-27.py`. Peak per PP rank in GiB as min / mean / max, against 74.5 GiB of usable HBM; host link 50 GB/s per GPU unless stated, half of a 400 Gb/s NIC for PP on H100.

| layout, recipe | #4765 | + offload | + balance alone | + both |
|---|---|---|---|---|
| H100 PP8 x VP4, full AC, fused aggregation | 67.5 / 69.4 / 71.1 | 62.3 / 62.8 / 63.5 | 69.0 / 69.6 / 70.1 | as offload |
| H100 PP8 x VP4, full AC, unfused aggregation | 80.6 / 82.3 / 83.7 | 74.9 / 75.8 / 77.1 | 81.6 / 82.6 / 83.4 | as offload |
| H100 PP16 x VP2, full AC | 60.7 / 66.9 / 70.6 | 56.6 / 60.3 / 62.2 | 63.8 / 67.0 / 69.2 | as offload |
| H100 PP8 x VP4, report recipe | 188.5 / 221.4 / 251.0 | 63.4 / 64.0 / 64.6 | 198.7 / 222.1 / 239.9 | as offload |
| H100 PP8 x VP4, report recipe, host 25 GB/s | 188.5 / 221.4 / 251.0 | 163.7 / 178.7 / 195.3 | 198.7 / 222.1 / 239.9 | 164.2 / 179.8 / 194.4 |
| GB300 PP4 x VP4, report recipe, host 200 GB/s | 209.4 / 237.0 / 257.4 | 79.0 / 79.8 / 80.6 | 229.4 / 244.5 / 253.2 | as offload |

The report recipe (elementwise recompute, FP8 storage, about 15 units per layer) needs offloading and fits on H100 at 50 GB/s of host link, not at 25. Full AC fits without offloading once the aggregation is fused; unfused, its backward transient keeps the peak above HBM even with offloading. Balancing lowers the heaviest rank when ranks differ, adds nothing on top of offloading at 50 GB/s, and turns no layout that does not fit into one that does. The report recipe's FP8 storage is not in this PR.
