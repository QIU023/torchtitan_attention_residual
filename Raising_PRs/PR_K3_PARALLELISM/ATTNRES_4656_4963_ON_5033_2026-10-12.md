# #4656 和 #4963 rebase 到开着 #5033 编译的 main（2026-10-12 夜）

用户 goal："overnight在本机把4656和4963 review分支rebase后重新兼容开5033 compile的改动 不能关闭"。

## 问题

main 的 #5033（acisseJZhong，10-09）把 attention residual 的聚合做成 `AttentionResidual`，`@local_compile("attention_residual", batch_invariant=True, dynamic=True)`。`local_compile` 固定 `fullgraph=True`，K3 的 `local_compile_regions` 默认就开着它。编译区的输入是堆叠张量 `block_residual_TND` 加可选的 partial，源的个数 N 是符号维度，所以一张图。#4656 把载体改成列表。

- 列表直接传进编译区：dynamo 按列表长度特化。按 flavor 数（`(块数, 有没有 partial)`）：debugmodel 9 张图、Kimi-K3 15 张；默认上限 8，`fullgraph=True` 超限直接 `FailOnRecompileLimitHit`（CPU 上复现过）。
- 在调用处先 stack 再传张量：一张图，但编译区把输入存下来做反向，每次调用多存一份拷贝，比 main 还费显存。

## 做法

本机 torch nightly（venv_1006，2.15.0.dev20261005）的 `torch.compile` 有按区域的 `recompile_limit`，`local_compile` 原样转发 `torch.compile` 的参数。

- 聚合改成接收一个源列表 `sources_TD`（先 blocks，后 partial），和 FLA 的 `fused_attnres(query, residuals: Sequence[Tensor], ...)` 一样（#5033 的 Triton override 就是从它改来的，FLA 原版用指针表读各个源，不拼接）。编译区内部 `torch.stack`。
- 调用处自己拼列表，所以图的个数只看源的个数：debugmodel 5 张（2 到 6 个源）、Kimi-K3 8 张（2 到 9 个源）。`recompile_limit=32`，留出训练和评估两种 grad 模式。
- Triton override 也接收源列表：一个 autograd.Function 把源 stack 成 bank 交给原来的 kernel，反向时重新 stack；存下来的是源本身，不存 bank。
- 测试：编译区 GPU 测试改成源列表，参考对比覆盖 1 到 10 个源（10 张图，超过默认上限）；override 测试加一条：列表路径和 bank 路径逐位相同，且 saved tensors 里没有 bank。

## #4656 的提交

- `507a2f7d5` 列表载体（rebase 到 main `b663c1673`），就是 #4656 的新内容。批量不变单测用 main 那组输入值，作为 4 个连续的源传入；在 5060 上通过。
- 另有一个没放进 #4656 的提交 `41d67c159`（在 `507a2f7d5` 上）：加权求和改成对源的归约，不再用 `[T, 1, N] x [T, N, D]` 的 bmm。补丁在 kit 的 `weighted_sum_reduction.patch`。

这个归约提交的来由（全是本机测的）：

- main 的编译区在 sm120 上不是 batch invariant：cuBLAS bmm 的结果随 token 数变。随机输入 20 组里 main 5 组、列表版 3 到 7 组前向输出随批大小变化；bmm 换成归约后 0 组。main 自己的 batch invariance 单测靠那组固定输入才过。列表版用同一组值：作为 unbind 出来的跨步视图传入时不过（视图走另一张图），作为 4 个连续张量传入时通过，所以 `507a2f7d5` 的测试用后者；换成另一组随机输入（4 个新张量）时列表版不过，main 也有 5/20 的输入不过。
- 归约版本：在 [2048, 9, 7168] 上前向加反向 10.18 ms，main 12.37 ms，列表加 bmm 13.78 ms；单次调用的增量峰值 0.99 GiB 对 1.24 GiB。编译区存给反向的是 bf16 的 stack，不是 fp32 的拷贝（看生成的代码：main 和列表加 bmm 都返回 fp32 的 `[T, N, D]`）。
- 第二个提交改的是 #5033 的算子数值，用户可以决定留在 #4656 里、单独开 PR，还是不要。

## 数值：和 main 不再逐位相同

列表版的编译区里 N 是常量，main 里是符号：

- softmax 在 main 是循环归约（`triton_red_..._prepare_softmax_online`），列表版是展开的逐点计算；
- 加了 `unroll_reductions_threshold=1` 和关 persistent reduction 也不逐位（20 组里输出 6 到 7 组不同、梯度 16 到 19 组不同）。

所以 rebase 之后的说法要改：不是"算术不变"，而是"和 main 在编译算子的归约顺序上有 ulp 级差别"，大小见下面端到端的结果。噪声基线用 main 自己的两种算子：编译（#5033）对 eager（#5033 之前）。

## 本机结果（8 × 5060，venv_1006，不进 body）

kit `kit_4656_5033_2026-10-12/`（`run_4656_5033.sh`、`run_grads_1012.sh`、`run_pp_1012.sh`、`summarize_1012.py`），日志在 scratchpad 的 `m4656_5033/`。树：main `b663c1673`；c1 = 列表载体（跑的是 `e34e0ed53`，和最终的 `507a2f7d5` 只差一个测试文件和 override 里一行 docstring）；c2 = c1 加归约（`ba8f071d1`）。K3 debug 模型（dim 256，17 层，每 4 层一个 block），seed 42，deterministic，local compile 全开。数值格子都在同一份缓存（每种配置 10 步预热）的副本上跑。

单卡，默认 seq，20 步（debug 集在第 40 步之后被记住，这里只到 20 步）：

| 配置 | 和 main 相同的步数（loss 和 grad norm） | 第一个不同的步 | 20 步内最大相对 loss 差 | 第 1 / 10 / 20 步 loss |
|---|---:|---:|---:|---|
| main 再跑一遍（噪声基线） | 20 / 20 | 无 | 0 | 8.21584 / 6.06893 / 5.48066 |
| main，聚合不编译（#5033 之前的算子） | 1 / 20 | 2 | 3.65e-3 | 8.21584 / 6.06908 / 5.46063 |
| c1，AC none / selective / full / region | 1 / 20（四种 AC 一样） | 2 | 4.67e-3 | 8.21584 / 6.06601 / 5.46775 |
| c2，四种 AC | 0 / 20 | 1 | 3.48e-3 | 8.21545 / 6.06791 / 5.46192 |

第 1 步梯度（AC none，465 个参数）：

- main 对 main：465 个逐位相同。
- main 对"聚合不编译"：463 个相同，2 个不同，相对差最大 2.2e-8（`layers.16.ffn_res_proj.weight`、`layers.9.attention_res_proj.weight`）。
- main 对 c1：462 个相同，3 个不同，相对差最大 2.2e-8（同样是 attention residual 的投影权重）。c1 第 1 步的差别和 #5033 自己的编译对 eager 是同一个量级。
- main 对 c2：431 个不同，最大 0.40（`layers.0.ffn_res_proj.weight`），router gate 的梯度差 7% 到 8%：归约改了输出的个别 bf16 位，MoE 的 top-k 跟着翻转（见 [[moe-routing-near-tie-is-the-floor]]，没有逐个数翻转）。对 fp64 金标准，main、c1、c2 三个编译区的输出误差（7.8e-3）和梯度误差（1.5e-2）一样，所以 c2 的算子本身不比 main 差。

PP 格子（B200 suite 的 8 卡格子，FSDP 2 × TP 2 × EP 2 × PP 2 × VPP 4，20 步，同一份缓存）：

- main 对 main：160 / 160 行逐位相同。
- c1：第 1 步相同（loss 8.02080，grad norm 1.9609），第 2 步开始不同，第 20 步 3.06757（main 3.06835）。
- c2：第 1 步 loss 8.02053，grad norm 相同。
- 峰值：第一个 stage 的 rank 都是 0.73 GiB；最后一个 stage 的 rank main 0.65 到 0.66，c1、c2 0.63 到 0.64。

算子单测（单卡，[2048, 9, 7168]，bf16，前向加反向）：main 12.37 ms、增量峰值 1.238 GiB；c1 13.78 ms、1.238 GiB；c2 10.18 ms、0.992 GiB。

Triton override（单卡，[2048, 9, 7168]，前向加反向）：main 的 bank 加 partial 签名 4.47 ms、增量峰值 0.328 GiB（和 #5033 在 H100 上的 0.328 一致）；列表包装（stack 给原 kernel，反向再 stack）7.23 ms、0.574 GiB。多出来的就是两次 stack 和一份临时 bank。要去掉，得把 kernel 改成按指针读各个源（FLA 原版的做法），这次没做，body 里写成后续。

pyrefly：main、`507a2f7d5`、`57790e1c6` 都是同样的 19 个错误（逐行相同），新增的只在 override 文件里，被文件级 `ignore-errors` 压住。

结论：#4656 只带 c1。c1 编译开着、所有 AC 和 PP 都能跑，第 1 步 loss 和 grad norm 和 main 逐位相同，第 1 步梯度的差别和 main 自己编译对 eager 一样小。c2 是另一件事（批量不变、更快、省 fp32 拷贝），但它第 1 步就改数值，存成 kit 里的 `weighted_sum_reduction.patch`，由用户决定要不要单独开 PR。
