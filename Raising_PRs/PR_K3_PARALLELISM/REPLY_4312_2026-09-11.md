In your notation, four ranks with two virtual stages each (stage `s` on rank `s % 4`, one block opened per stage):

```
[this PR]
Relay like option 2, but every rank keeps what it has already seen, so a hop
carries only the blocks committed since the receiving rank last ran.

rank 0 sends 0     to rank 1
rank 1 sends 0+1   to rank 2
rank 2 sends 0+1+2 to rank 3
rank 3 sends 1+2+3 to rank 0   (rank 0 already has 0)
```

18 block-messages against option 2's 28 for the same shape. The first pass around the ranks is identical to option 2 -- nobody has seen anything yet -- and from the second pass on the payload stops growing, capped at `P - 1` blocks (3 here) however deep the model is. With one stage per rank there is no second pass, so this is exactly option 2 and the tables above show all three schemes at the same number.

The volume column for this PR equals option 1's in every shape, and every message is still between adjacent stages: a block is relayed forward, and a hop carries only what the receiving rank does not already hold. A rank keeps what it has seen for its own later virtual stages, which is what makes the relay cost the same as the direct sends -- no block is ever delivered twice to the same rank.

Why the relay rather than the skip edges. A literal option 1 sends from a producer rank to ranks it is not adjacent to, which means P2P outside the schedule's own batches. That is the shape @elfiegg's two-node GB200 run died on with the previous tree: traffic on the pipeline group that the schedule does not order, reached in different orders by neighbouring ranks under 1F1B. The contention you were unsure about is the mild version of the same thing. Relaying avoids it by construction -- the block rides the forward hop that has to happen anyway, so it adds no message and no latency of its own, and the stage issues no collective and no object P2P.

Two corrections to the cost of option 2, since it is the fallback in this PR and we measured it:

- It is not `[PP degree]` times more data. Measured: 2.6x at pp8 x vp4, 5.7x at pp4 x vp8, 4.0x at pp2 x vp4. The multiplier is roughly `S / (2(P-1))` -- it grows with the number of virtual stages and shrinks with the PP degree, and at one stage per rank it is 1.
- It is not confined to the first micro-batch. Block residuals are activations, not weights, so with the whole stack on every hop every micro-batch pays it again. That is what the rank-local cache removes.

At one stage per rank all three schemes coincide (28 / 28 / 28 above): the receiving rank holds nothing, so the delta is the whole stack and there is nothing to skip. That is also why `pp2` alone cannot tell the two transports apart, and why the A/B in the results needs virtual stages.

Option 2 is in this PR, exactly as you describe it: `attn_res_cache=False` is one field in the routing tables (`layout.py`, `cache=False`), selected by a recipe, and it is the A/B every results table carries. We kept it because it is the simple thing to reason about and because it bounds what the cache is worth.

Noted on #4486 -- we will not build on it.

## 2. The activation save / release policy (the question that needs a worked example)

评论：`model.py:222` (09-10 08:13) — "yes we would save all previous blocks' result for each layer,
despite the redundancy" 对不对；以及 "be very specific about the activation save / recomputation
policy... every block has 4 layers, there are two blocks -- what exactly are you saving in forward,
after each layer, and when exactly would things be released?"

--- PASTE BEGIN ---

Correct, with one refinement: the stack is not re-saved per layer, it is one tensor that grows once per block and is read by every layer.

The worked example, 8 layers, `attn_res_block_size = 4`, so two blocks. `block_residual_TND` is `(T, N, D)` and travels with the hidden states.

- Layer 0 opens block 0: the incoming stream is concatenated onto the stack, so `N` goes 0 -> 1 and the stack holds `[x_0]`. Layers 1, 2, 3 do not grow it; each carries the block's running partial sum as a separate `(T, D)` and reads the same `N = 1` stack.
- Layer 4 opens block 1: the partial sum block 0 committed is concatenated, `N` goes 1 -> 2, stack `[x_0, s_0]`. Layers 5, 6, 7 read `N = 2`.
- The stage that owns `lm_head` runs the final aggregation over the stack plus the last partial sum; that is why `output_res_proj` / `output_res_norm` are pinned to it.

What autograd saves in forward, per layer, is the concatenation `_apply_attention_residual` forms: `(T, N+1, D)`, for the softmax backward. Summed over the model that is quadratic in the *block* count, not the layer count -- for the 93-layer model, `N` at layer `i` is `i // 12`, so the sum is `sum over blocks of (block index + 1) * 12`, about 36 stacks of `(T, D)`, not 93. This is what the report means by wrapping the AttnRes computation in checkpointing: with that region recomputed, only the `N` committed block entries stay live (8 for 93 layers, 2 in the example above) and the `(T, N+1, D)` concatenations are rebuilt in backward. That AC wrap is a follow-up PR, not this one; this PR saves them.

Release, under PP: a block entry is held by the rank that produced or received it, in the rank-local cache, keyed by micro-batch id. It is dropped when the last stage on that rank that reads it has run its backward -- that is the `PPRankLocalCache` release path, and it is why the cache is per rank rather than per stage. With `attn_res_cache=False` nothing is held: the whole stack rides every hop and dies with the hop's autograd graph.

--- PASTE END ---

Worth separating what her fix addresses from what this PR does. The old tree ran the runtime in DYNAMIC mode: its adapter sent per-micro-batch metadata objects (`send_object_list`) on the whole-PP communicator, interleaved with the schedule's own tensor batches, plus a serial P2P vote chain on the same communicator. Under 1F1B at PP=8 the neighbouring ranks reach those operations in different orders, which is a circular wait on one communicator; her diagnosis chain starts exactly there ("AttnRes needs dynamic metadata P2P"). This PR removes that first link rather than working around it: `AttnResPipelineStage` issues no object P2P and no collectives of its own -- the routing tables fix every hop's payload before the first send, so the stage runs STATIC and the only traffic is the schedule's own batched tensor P2P between adjacent stages, two tensors per hop instead of one.

What that leaves is the STATIC-mode gap the runtime already documents: the vote protocol warms the two-rank sub-communicators the homogeneous `_batch_p2p` path uses, but the group communicator behind the mixed send/receive batch is created lazily at the first 1F1B steady-state batch, and DYNAMIC-mode metadata inference is what happened to warm it. That is model-agnostic -- any model running a STATIC 1F1B pipeline across nodes meets it, not just this one -- which is why I would rather not carry a workaround for it inside a model PR. If the two-node run on `k3_pp_transport` shows it is real, the right place is `torch.distributed.pipelining` (whose vote protocol already builds two-rank sub-communicators internally), or a standalone torchtitan PR with the knob in `CommConfig` rather than an environment variable, with her evidence attached.

To be explicit about what is and is not verified here: single node is complete (both transports bitwise at pp2, pp8 and pp8 x vp4; and a socket-path simulation with `NCCL_P2P_DISABLE=1 NCCL_SHM_DISABLE=1` across two torchrun agents passes with and without the warm-up, with the INIT log showing every communicator created before step one). Two nodes is not verified on this tree -- that run is @elfiegg's, and I will report it here either way.
