## 2. The activation save / release policy (the question that needs a worked example)

评论：`model.py:222` (09-10 08:13) — "yes we would save all previous blocks' result for each layer,
despite the redundancy" 对不对；以及 "be very specific about the activation save / recomputation
policy... every block has 4 layers, there are two blocks -- what exactly are you saving in forward,
after each layer, and when exactly would things be released?"

--- PASTE BEGIN ---

Correct, with one refinement: the stack is not re-saved per layer, it is one tensor that grows once per block and is read by every layer.

The worked example, 8 layers, `attn_res_block_size = 4`, so two blocks. `block_residual_TND` is `(T, N, D)` and travels with the hidden states.

- Layer 0 opens block 0: the incoming stream is concatenated onto the stack, so `N` goes 0 -> 1 and the stack holds `[x_0]`. Layers 1, 2, 3 do not grow it; each carries the block's running partial sum as a separate `(T, D)` and reads the same `N = 1` stack.
- Layer 4 opens block 1: the partial sum block 0 committed is concatenated, `N` goes 1 -> 2, stack `[x_0, s_0]`. Layers 5, 6, 7 read `N = 2`.
- The stage that owns `lm_head` runs the final aggregation over the stack plus the last partial sum; that is why `output_res_proj` / `output_res_norm` are pinned to it.

What autograd saves in forward, per layer, is the concatenation `_apply_attention_residual` forms: `(T, N+1, D)`, for the softmax backward. Summed over the model that is quadratic in the *block* count, not the layer count -- for the 93-layer model, `N` at layer `i` is `i // 12`, so the sum is `sum over blocks of (block index + 1) * 12`, about 36 stacks of `(T, D)`, not 93. This is what the report means by wrapping the AttnRes computation in checkpointing: with that region recomputed, only the `N` committed block entries stay live (8 for 93 layers, 2 in the example above) and the `(T, N+1, D)` concatenations are rebuilt in backward. That AC wrap is a follow-up PR, not this one; this PR saves them.

Release, under PP: a block entry is held by the rank that produced or received it, in the rank-local cache, keyed by micro-batch id. It is dropped when the last stage on that rank that reads it has run its backward -- that is the `PPRankLocalCache` release path, and it is why the cache is per rank rather than per stage. With `attn_res_cache=False` nothing is held: the whole stack rides every hop and dies with the hop's autograd graph.

--- PASTE END ---

## 3. The numerics challenge

评论：`parallelize.py:267` (09-11 02:12) — "I'm not convinced that the numerics gap can be this
large. Could you give simple examples of how accum order would change with this flag off / on vs.
without PP? How do you prove it's not caused by bugs?"

--- PASTE BEGIN ---

The bar this change is claimed on is step-1 bitwise against one GPU, and it holds in every cell: 2 to 32 stages, uneven splits, both transports, the same `12.41967`. A routing or gradient defect cannot be bitwise at step 1, so what moves later is summation order, and below is exactly which sum reorders.

A block entry is read by every layer after it, and those readers now sit on different stages, so its gradient is a sum of one term per reader. The three configurations associate that sum differently:

- No PP: all readers are in one autograd graph on one device; the sum is the graph's own accumulation order, reader by reader in backward order.
- PP, `attn_res_cache=False`: every hop carries the whole stack, so each stage receives its own copy of the entry and returns its own gradient; the sum is formed hop by hop along the pipeline, with one partial sum per stage boundary.
- PP, `attn_res_cache=True`: the entry is sent once to a rank and the stages on that rank deposit into one slot, so the terms of the readers that share a rank are summed rank-locally first, and that partial joins the remote one at the boundary.

Same terms, three different association orders, so three different roundings at the last bit, which Adam then amplifies -- the second moment divides by a square root, so a relative difference of 1e-7 in a gradient does not stay 1e-7 in the update.

Three things separate that from a defect:

1. Step-1 gradients, per parameter, not just the loss: every parameter group is inside the stated floor, counted N/N, with sign flips reported (0.27%, against 23% when we injected a real routing error to calibrate what a defect looks like).
2. The same run in float32 end to end, with no optimizer step at the stage boundaries, stays within the fp32 floor for the whole matrix; the spread appears when bf16 and Adam are put back.
3. The control that settles it: llama3 and deepseek_v3 on stock `pipeline_llm`, with none of this PR's code in the path, track dp1 to 1e-5 and 3e-4 at step 10 on the same box. Plain pipeline parallelism on unmodified core already spreads at that order of magnitude, so the carrier is the pipeline's own summation order, not the block residual.

The full write-up, with the per-parameter census and the control table, is in `phase13_k3like_48b_posttrain/PP_NUMERICS_FOR_4312_2026-09-05.md` (logbook). One thing that cannot be made bitwise by construction: the block residual spans the whole depth, so the split decides the summation tree, and loss and grad norm are therefore not identical across pipeline configurations with either transport -- step 3 reads 7.66420 / 7.64929 / 7.60614 for whole-stack pp2 / pp4 / pp8. Step 1 is bit-identical in every cell regardless.

--- PASTE END ---
