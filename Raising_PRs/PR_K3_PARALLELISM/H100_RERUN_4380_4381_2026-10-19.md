### 5060 诊断（10-20）：数值的差来自 main #5250，tower 本体和副本的权重梯度精度不同

kit `kit_h100_2026-10-19/diagdep/`。H100 数值格的设置，宽度换成 debug 的 256（`DEPW_DIM=256`），2 步，每格在一份预热 cache 的副本上跑。新树 `7529daeea` 用 venv_1006（torch 10-05 nightly）加 `main_pins_1016`；旧树 `4e2ec143b` 用 venv_0928（torch `68e0ae496`，和 10-02 / 10-04 H100 上源码编的是同一个 commit；10-05 的 torch 跑不了旧树，旧的 `AttnResPipelineStage` 要 `fwd_cache`）。

- 第 1 步梯度和更新后的参数（`dep_upd1.py`、`analyze_diagdep.py`）：
  - 新树：K2.5 和 bubble 对 DEP 关，4 个 rank 的文本梯度全部逐位相同；tower 22 个梯度里 7 个相同，15 个不同（18.9% 的元素，最大相对差 5.2e-3）；第 2 步 loss 7.09406 对 7.09410，和 H100 的形态一样。
  - 旧树：K2.5 和 bubble 对 DEP 关全部逐位相同（tower 22/22），和 10-04 的结论一致。
- 两条路怎么累加（`dep_mbgrad.py`、`analyze_mbgrad.py`：录下每个副本每个 micro-batch 的 tower 梯度，离线重算）：
  - DEP 开：两棵树都等于"fp32 累加、最后舍入成 bf16 一次"（22/22），和 `VisionDep._reduce_gradients` 一致。
  - 旧树 DEP 关：也等于这个（22/22），所以旧 main 上两条路是同一个算法，逐位相同。
  - 新树 DEP 关：不等于 fp32 累加（7/22），也不等于按 stage 0 的反向顺序在 bf16 里逐个累加（0/22）。
- tower 本体的每个 micro-batch（`dep_ownergrad.py`、`analyze_owner.py`，在 FSDP 的 unsharded 参数上挂 post-accumulate hook）：新树 DEP 关时，第一个 micro-batch（mb 0）就和副本对不上，不同的 15 个全是矩阵权重（attention 的 wq、wk、wv、proj，MLP 的 fc1、fc2，patch_embed，projector），值是 fp32；相同的 7 个是向量参数。
- 原因：main 的 #5250（`06dd3abe2`，"In-place WGRAD accumulation for the bf16 Linear"，在 `db050eb3f` 之后合入）让 `_LinearFunction` 按参数的 `grad_dtype` 产出权重梯度（`torch.mm(..., out_dtype=grad_dtype)`）。FSDP 给 stage 0 上的 tower 设 `grad_dtype` = reduce dtype（fp32），所以 DEP 关时矩阵权重的梯度直接以 fp32 出来；DEP 的副本是普通 bf16 模块，没有 `grad_dtype`，每个 micro-batch 的权重梯度先舍入成 bf16。旧树没有 #5250，两边都是 bf16，所以逐位相同。
- 本地补丁验证（只在 scratchpad 的导出树 `new_gd` 里，没有进任何分支）：`build_vision_replica` 里给副本参数设 `param.grad_dtype = TORCH_DTYPE_MAP[training.mixed_precision_reduce]`。结果：第 2 步 loss 7.09406，和 DEP 关相同；第 1 步更新后的参数 465/465 逐位相同；第 1 步 tower 梯度只剩 330 万个元素里 85 到 103 个不同（最大相对差 1.2e-3，fp32 求和顺序不同，舍入成 bf16 时落在边界上）。
- 20 步（`run_gd20.sh`，同一份 cache 的副本）：不打补丁的 K2.5 从第 2 步起和 DEP 关不同；打补丁的 K2.5 和 bubble 从第 3 步起不同（第 3 步 5.64702、5.64741 对 5.64715）。剩下的差是加法顺序：副本在各 rank 上先求 fp32 部分和再跨 rank `reduce`，tower 本体按 micro-batch 顺序在 fp32 里累加；fp32 末位的差在舍入成 bf16 时偶尔落在边界上。要完全逐位，得让 stage 0 按原顺序逐个加每个 micro-batch 的梯度，不值得。
- 结论：
  - 新 main 上 DEP 开和关不再能逐位相同；第 1 步 loss 和文本梯度逐位相同是能守住的标准。
  - 不改代码时，tower 权重梯度在 18.9% 的元素上差一个 bf16 单位（精度不同）；给副本设 `grad_dtype` 后只剩约 0.003% 的元素（顺序不同）。
  - 设 `grad_dtype` 是让副本和 FSDP 管的 tower 用同样的梯度精度，属于 DEP PR 该做的事，要不要加由用户定；加了以后 DEP 的 CPU 和 GPU 测试、H100 数值表都要重跑。
