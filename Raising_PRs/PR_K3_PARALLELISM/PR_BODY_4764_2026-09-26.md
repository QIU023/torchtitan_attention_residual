## Summary

Kimi K3 pipeline ranks plan what to offload to host memory and what to park on a lighter rank as one plan, from a profiled first step, and apply it from the second step on.

- `HostBackend`, `RemoteBackend` (`torchtitan/distributed/activation_storage.py`): pinned host memory, and a pool on another pipeline rank reached through mooncake's transfer engine. A pool is its sources' spans laid end to end, each sized by what that source parks at once.
- `MemoryPlan`, `PPMemoryController` (`kimi_k3/pipeline_parallel/activations.py`): the first training step moves nothing and records every compute action's peak and duration and what each stage micro-batch could move; when that step returns the ranks exchange these profiles and each derives the same plan.
- `KimiK3Model.Config.pp_memory.offload` and `.balance`, with `target_gib`, `host_gbps` and `peer_gbps`. Off by default.

## Design

A move lowers a rank's profiled timeline from the action by whose middle its copy out has finished to the action that starts its copy back, both taken from the measured durations and the budgeted bandwidth. The plan takes the rank with the highest peak and moves the largest stage micro-batch whose window covers that peak, to a rank whose peak plus pool stays under the target or else to host memory, and repeats until every rank is under the target or nothing that fits the link time is left. The target defaults to the mean of the ranks' profiled peaks, which is the balanced memory the Kimi K3 report aims for; `target_gib` sets a cap instead.

The plan is built after the profiled step returns. A pipeline stage cannot issue the collective inside its last backward: its input gradient send is a later action, and the previous rank waits for it. Core's schedules have no hook after a step, so the controller wraps the schedule's `step`.

The rank store's blocks are pinned in the storage (#4765), so no plan moves a block the rank keeps for its later stages.

## Results

8 x RTX 5060 Ti, the same layout as #4765: 93 layers in blocks of 12, pp8 x vp4, dim 2048, seq 2048, 16 micro-batches, full AC. Peak allocated memory per PP rank in GiB at step 5; the plan is built after step 1:

| rank | #4765 | offload and balance |
|---:|---:|---:|
| 0 | 5.14 | 5.14 |
| 1 | 5.67 | 5.67 |
| 2 | 5.64 | 5.64 |
| 3 | 6.37 | 6.16 |
| 4 | 5.87 | 5.87 |
| 5 | 5.92 | 5.88 |
| 6 | 5.87 | 5.87 |
| 7 | 6.82 | 6.46 |
| max | 6.82 | 6.46 |
| mean | 5.91 | 5.84 |

Loss and grad norm are identical to #4765 on all 20 steps. The traced step takes 22.79 s either way: the copies add 40 ms of forward and 90 ms of backward compute stream time per rank, and the step here is bound by pipeline communication. The heaviest rank's plan expects 0.54 GiB off its peak and gets 0.36, because the copies out run slower than the 2 GB/s the plan budgets on this box. The box has no RDMA NIC, so the pools sit in the destinations' pinned host memory behind mooncake's TCP transport; H100 numbers go here once measured.
