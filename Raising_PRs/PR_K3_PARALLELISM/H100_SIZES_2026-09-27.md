## 0. 规则，以及作废的设置

- **规则：** 所有实验从现在 main 的 debug model 出发（`f35966713` 的 `_debugmodel`：17 层，block 4，full attention {3, 7, 11, 15, 16}，8 专家 top-2，2 shared，vocab 2048），只放宽度。debug model 里和 dim 成比例的宽度都乘同一个倍数 s = dim / 256：头数（每头维度 64 / 32 / 64、KDA 128 不变）、q_lora、kv_lora、dense hidden、latent、expert hidden；视觉塔在 debug model 里和文本同宽（dim 256、qkv 512、hidden 512、4 头、2 层），宽度一起放大，层数不变。层数、block、专家数、vocab 都不变。
- **作废：**
  - 46 层、block 6（09-24 的 H100 计划，为凑 16 个 stage 改了层数）。
  - 93 层、block 12（5060 上 PR A 实验的结构）：这是 2.8T 发布模型的深度，四卡上只能把 MoE 缩成 8 个小专家、16 个头才塞得进去，既不是发布模型，也不是 debug model。
  - 09-27 H100 上"48 层、dim 2048、block 4"的表（我编的）。
  - 09-17 H200 的 24 层和 48 层单卡网格：48 层是加深，不是加宽；单卡按同一规则另定（第 4 节）。

## 1. 模型：debug model 放大 24 倍，dim 6144（PR A 和 DEP 共用）

- **宽度：** dim 6144，96 头，q_lora 3072，kv_lora 1536，dense hidden 12288，latent 3072，expert hidden 3072；视觉塔 dim 6144、qkv 12288、hidden 12288、96 头。一共 13.3 B 参数，其中视觉塔 1.67 B（在 rank 0）。
- **为什么是 6144：** #4656、#4780 以前用过的宽度是 1024（09-17 的 debug model）、4096、7168（#4780 算子级"从 debug flavor 到发布模型的 hidden size"）。5060 上实测三个小宽度，推到 H100：

| 最重的 rank，allocated（GiB，推算） | dim 4096 | dim 5120 | dim 6144 | dim 7168 |
|---|---:|---:|---:|---:|
| PR A 的布局，main（最重的树） | 22.8 | 33.1 | 45.2 | 59.2 |
| 已提交的 DEP 格 | 22.1 | 31.2 | 41.7 | 53.6 |

  - 7168 时 PR A 的 main 是 59 GiB allocated。5060 上 reserved 是 allocated 的 1.15 到 1.3 倍，折算 68 到 77 GiB，离 80 GB 太近。4096 只用到 23 GiB。所以取 6144，两个实验都在 45 GiB 左右，放得下也用得上。
  - **怎么推的（推算，`kit_h100_sizing_2026-09-27/widened_debug/`）：** 5060 上 pp4 × vp2 实测 dim 512、768、1024（第 3 步，每个 rank，GiB）。PR A 布局：1.10 / 1.36 / 1.36 / 1.20，1.91 / 2.26 / 2.23 / 1.92，2.84 / 3.24 / 3.19 / 2.69。DEP 格：1.09 / 1.51 / 1.49 / 1.22，1.84 / 2.40 / 2.37 / 1.95，2.69 / 3.39 / 3.31 / 2.72。参数和优化器状态随 s² 长、激活随 s 长，所以每个 rank 按 A + Bs + Cs² 过三个点外推。另一种算法得到的结果一样：meta 上数参数，按 8 B/参数算静态（recipe 的 `training.dtype` 是 bf16，权重、梯度、AdamW 两个状态都是 bf16），激活按 s 线性外推。在 dim 6144 下，rank 0 用这种算法是 44.6 GiB，拟合是 45.2 GiB。
  - 外推跨了 6 倍，所以上机第一步两个实验各跑 2 步核对；放不下就退到 5120。

## 2. PR A（对 main、#4656、#4780、全叠；#4765 / #4764 冒烟）

- **布局：** 4 × H100，pp4 × vp2（Interleaved1F1B 默认每个 rank 2 个 stage，8 个 stage，和已提交的 DEP 格同形），16 个 micro-batch × 2048 token，FullAC，AdamW，seed 42。训练设置照 PR A 在 5060 上那张表（M16、seq 2048、FullAC、AdamW 探针 `probe_lb`），只换模型（本地探针 `widened_debug/probe_lbw.py`）。
- **推算 main 每个 rank：** 45.2 / 40.0 / 39.7 / 28.7 GiB allocated。rank 0 带 embedding 和视觉塔，静态最重。
- **每格：** 一份预热 cache（每格各跑一步预热，再各拷一份），10 步看每个 rank 的峰值和逐位一致，第 8 步 trace 计时（`campaign2.sh` 的协议）。五棵树：main `f35966713`、#4656 `aa6d9fedc`、#4780 `f14d681f4`、PR A `439bd2088`、全叠 `e8d0a4aec`。FullAC 下 #4780 只在 output aggregation 上多一个 checkpoint，所以 #4780 列除最后一个 stage 外应当和 #4656 相同，全叠对 PR A 同理。
- **#4765 / #4764 冒烟：** 同一个布局，各 4 到 6 步，看 rc 和每个 rank 的峰值：#4765 `cpu_offload=all`，#4764 `planned`，#4764 只开 balance（`nvlink_intra`，池在目的 GPU 上），#4764 planned 加 balance。这个布局 rank 间预计差 16.5 GiB（45.2 对 28.7），balance 要做的就是把它压平，所以不再单独用关 AC 的 b1 布局。再跑 `kit_h100_2026-09-27/scripts/nvlink_intra_test.py` 的两卡往返。

## 3. DEP

- **格子：** 已提交的 `kimi_k3_debugmodel_pp4_vp2_vit_dep`（pp4 × vp2，M8，SelectiveAC，DistMuon，seq 2048，bubble 开），只把模型换成第 1 节的 dim 6144（本地 recipe `widened_debug/dep_widened.py`）。推算每个 rank 40.9 / 41.7 / 35.7 / 27.7 GiB allocated。
- **四种配置：** 关 DEP、开 DEP 全部 inline、开 DEP 加 prefetch 1、开 DEP 加 bubble。同一份预热 cache，第 12 到 30 步每步耗时，再各抓一步 trace，量 rank 0 的空闲和一次编码的耗时（09-27 G1 的协议）。
- **计算量比例：** 放宽度不改变视觉塔和文本 stage 的比例。只算矩阵乘，一次编码约为一个文本 stage（3 层）前向的 4.3 f 倍（f 是图像 token 在序列里的占比；cc12m-test 以图为主），发布模型是 0.54 f（`kit_h100_sizing_2026-09-27/dep_ratio.out.txt`）。所以这里测的是一条视觉塔偏重的流水线，结果写 body 时照实说明。09-27 在 H100 上量到的 0.2 是 launch bound 下的时间比，不是计算量比。

## 4. 其余实验：按同一规则，还没定

- **#4656 / #4780 单卡：** 同样从 debug model 放宽度。单卡时 dim 4096 光参数和优化器状态就约 44 GiB（8 B/参数），宽度要另外实测再定。PR A、DEP 确认之后再做。
- **#4780 算子级：** 不变（09-18 的形状，没有层数；其中 dim 7168、stack 8 就是发布模型的宽度和 block 数）。脚本要按 09-18 的计时协议和列表接口重写。
- **MoonEP：** 提交里的 h100 格 `kimi_k3_moonep_fsdp4_ep4` 加 MoonEP 自带的 benchmark，不变。先 rebase（5 个文件冲突），再由你定选后端的 flavor 怎么处理。

## 5. 四卡跑不了的

- B200 组合格 `kimi_k3_fsdp2_tp2_ep2_pp2_vpp4`（#4656、#4780、PR A 的 body 里写着 pending (H100)）要 8 卡。5060 八卡冒烟两格 rc=0（logbook）。要么等 8 卡的 H100，要么从 body 里拿掉。
- DEP body 的"The same cell at dp_shard 2"是 dp2 × pp4 = 8 卡；09-27 在 H100 上跑的是 dp2 × pp2 × vp2（4 卡），不是同一个格子。要么改成实际跑的格子，要么等 8 卡。
