## 1. 改动检查（`pp_review_optimize` = `345e9e00a`，CPU 那边会话 09-30 的最小版本）

- 分支：main `97e673b77` → `07abef619`、`e66a9442b`（#4656 rebase 副本）→ `36cfddf87`（v3）→ `345e9e00a`（v4 最小版本，加在 v3 上面，fast-forward，没有 force）。PR A 自己相对 #4656 副本（`e66a9442b..345e9e00a`）：7 个文件 +160/−140，主要是 `stage.py`。
- 逐行读了 `stage.py`、`__init__.py`、`model.py` 的 diff，逻辑上没有发现问题：
  - `_assemble_stack`：store 里的块变成共享存储的新叶子（`.detach().requires_grad_(True)`），收到的块直接当 stage 输入，不再 `torch.stack` 拷一份；`_pack_outgoing_delta` 直接返回模型自己的张量；`_split_stack_grad` 对 `None` 梯度补零、按线上顺序返回。
  - `get_fwd_send_ops` 覆盖：SEND_F 时用 `_batch_p2p` 发出并记下 work，本 stage 这个 micro-batch 反向时再等；下游此时一定已经收完（本 stage 要拿到它回传的梯度），不会死锁。只在 action-list runtime（`_PipelineScheduleRuntime`）下开，那里 send 不和 receive 合批。
  - `backward_maybe_with_nosync` 覆盖：拿到 store 里那些块的输入梯度（core 只留收到的输入的梯度，现在每块是独立叶子）。依赖 torch 的私有方法签名，偏脆，和 4312 覆盖 `_compute_input_grads` 同一类。
  - 反向：先等本 micro-batch 的前向 send，再按块拆梯度、存 deposit；发给上游的 `bwd_cache` 是隐状态加每个收到的块，按接收元数据逐项核对。
  - `model.py`：`forward` 直接收发块列表，去掉 `stack` / `unbind`。
- 测试和显存要在 GPU 上补：body v4 的 Test plan 五个文件（本机缺 CuTeDSL），Results 是 Pending (H100)。

- **为什么 CPU 上等于紧界、GPU 上贴着论文界（对账）：** pp4 × vpp2 峰值时 PR A 超出紧界的量是 0.24 / 0.18 / 0.14 / 0.10 GiB，同一时刻还没等的前向 send 是 0.23 / 0.19 / 0.14 / 0.09 GiB，两者一致。`cpu_bound.py` 用 gloo，send 发出就完成，不会挂着占内存，所以 CPU 上看到的是紧界；NCCL 的 send 是异步的，PR A 等到发送方 stage 自己反向这个 micro-batch 时才等，块就一直留到那时。要到紧界，得在接收方用完时就等（比如 #4765 那边的做法，或者 torch 的 issue），不是这个 PR 的范围。
