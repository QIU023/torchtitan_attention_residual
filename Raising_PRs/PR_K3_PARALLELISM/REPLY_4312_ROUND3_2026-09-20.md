## Thread 3, `torchtitan/models/kimi_k3/__init__.py:554` (discussion_r4056273914)

--- PASTE BEGIN ---

Done in <C3>: vocabulary 2048 (`tests/assets/tokenizer` has 2020 tokens plus Kimi K3's four special tokens; llama3's and qwen3's debug models use the same arrangement), 8 layers in two blocks of 4, full attention at layers 3 and 7. The embedding and head go from 335.5 M parameters to 4.2 M and the model from 1.1 B to 283 M. The widths stay: shrinking `dim` changes the shared flavor for the TP, EP and multimodal cells as well, so I left that as a separate decision; say the word and I will halve it.

Eight is the minimum that tests VPP > 1 with every path of the block transport, since the paths need two blocks and a block opening inside a stage. Under pp2 x vp2 core's split is [emb, 0, 1] [2, 3, 4] [5, 6] [7, head]: the second block opens at layer 4, inside stage 1; stage 2 (rank 0) receives it on the hop and reads the first block from rank 0's store, where stage 0 committed it; stage 3 (rank 1) receives an empty payload and reads both from rank 1's store; the backward runs the matching deposits and collections. Four layers in one block would run a looped schedule but no block would cross a stage, so nothing would be routed. It is also the 2 blocks x 4 layers shape of your lifecycle question, so both threads now describe the same model. The 33 layer flavor and the pp8 x vp4 cell are gone; the CPU exact test keeps 8 and 16 stages on four ranks, blocks opening inside stages, at no GPU cost.

Q1. The same global batch on both sides of every row: 1024 tokens per step as four micro batches of 256 in the first table, 2048 as two ranks times four micro batches of 256 in the second, and the reference runs those four micro batches as gradient accumulation. The reference also accumulates the way the pipeline does. torch pipelining sets `set_is_last_backward(False)`, `set_reshard_after_backward(False)` and `set_requires_gradient_sync(False)` on the FSDP module for every backward but the last (`stage.py`, `backward_maybe_with_nosync`), so the four micro batch gradients are summed in the reduce dtype and rounded once; the reference sets the same three switches on its accumulation steps (the `NOSYNC_GA` patch linked under the table). With that, every cache off pipeline cell is identical to the reference on all 100 steps, loss and grad norm, in both tables. The stock trainer syncs after every micro batch instead: reduce scatter in fp32, cast to bf16, add in bf16, four roundings where the pipeline has one, so a stock reference differs from every pipeline cell at the bf16 rounding of that sum, cache or no cache. `reshard_after_forward` decides whether the parameters are gathered again before backward and does not enter the accumulation; those runs used its defaults (`False` under PP, `True` without). I can add a stock accumulation row to the fp32 rerun below, so the size of that one rounding is on the record next to the cache's.

## Top level comment, after claude[bot]'s review (issue comment 5748181520)

--- PASTE BEGIN ---

On the bot's two asks. (1) Done in <C5>: `backward_one_chunk` checks that the receive metadata describes (hidden, delta) with a [T, N, D] delta before reading the delta's `requires_grad`, and the comment says why the answer comes from the metadata rather than from autograd (the stack the module saw is a detached leaf, so in the metadata pass the output does not depend on the delta). (2) No schedule guard, on purpose: the store relies on two orderings that every pipeline schedule provides by data dependency alone, a rank's stages run forward for a micro batch in increasing stage order and backward in decreasing order, with the loss between; `_is_first_on_rank` and `_is_last_on_rank` take the min and max stage index on the rank, so V shaped placements (DualPipeV, ZBV) fit as well as looped ones, and the deposit count check already fails loudly if a deposit is missing or extra. The comment at the store release now says this.
