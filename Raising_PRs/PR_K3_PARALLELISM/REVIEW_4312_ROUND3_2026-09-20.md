## 2. Item 2, the assert on `pipeline_parallel_layers_per_stage`

## 5. Item 5, the numerics questions

Q1. Both tables already compare gradient accumulation against the pipeline at the same micro batch count: 1024 tokens per step as four micro batches of 256 (dp1), and 2048 as two ranks x four x 256 (dp2). The reference accumulates its four micro batches with the three FSDP switches torch pipelining sets on every backward but the last (`stage.py` `backward_maybe_with_nosync`: `set_is_last_backward(False)`, `set_reshard_after_backward(False)`, `set_requires_gradient_sync(False)`), so the unsharded gradient is summed in the reduce dtype and rounded once, as the pipeline's is. With that reference every cache off pipeline cell (pp2, pp2 x vp2 naive, pp4 x vp4 naive, dp2 x pp2, dp2 x pp2 x vp2 naive) is identical on every step of 100. The stock trainer instead syncs after every micro batch: reduce scatter in fp32, cast back to bf16, add in bf16, four roundings instead of one. Measured on the same seed (PP_NUMERICS_MATERIAL_2026-09-12.md, section 91): stock dp1 against matched dp1 is 2 of 750 gradient tensors bitwise, one bf16 ulp on about 31 percent of every tensor's elements, relative L2 2.8e-3, flat across depth. `reshard_after_forward` decides whether parameters are re gathered before backward and does not enter the accumulation; the pipeline default is `False` under PP and `True` otherwise, and the identical rows above were taken with those defaults.

Q2. The tables are bf16 parameters and compute with fp32 reduction (`training.dtype = "bfloat16"`, the flavor's default). fp32 evidence so far is from the local 8 x 5060 Ti box only, which cannot go in the reply: at step 1, cache on in fp32 differs from cache off in the same 334 tensors as in bf16 with the largest relative gap down from 7.4e-2 to 9.1e-6; over 100 steps at pp8 x vp2 the cache on run first departs from cache off at step 3 by 1e-7 (fp32) and step 4 by 1e-15 (fp64), against step 2 by 5e-3 in bf16, and all three saturate at the same 0.4 percent band. What tianyu asks for is the C4 100 step table with fp32 parameters, compute and reduction, cache on, on H100: `--training.dtype float32 --training.mixed_precision_param float32 --training.mixed_precision_reduce float32` (the dtype alone leaves bf16 compute under FSDP; see memory `fp32-probe-needs-mixed-precision-flags`), plus the KDA reference path since Attention Gym's kernels are bf16. Four cells (reference, pp2 x vp2 cached, pp4 x vp4 cached, pp2 x vp2 naive), 4 x H100, about an hour with the seed and warm up. The reply can be posted with the bf16 answer and the fp32 table follows once the box exists.

## 6. Item 6, the no PP lifecycle

Tianyu's question, restated: no pipeline, 2 blocks x 4 layers, what does each layer save in forward and when is it released. The bot's answer is right on the stack (each `torch.cat` at a block opening makes a new storage; layers 1 to 3 hold a reference to the `[T, 1, D]` stack, layers 4 to 7 and the output aggregation to the `[T, 2, D]` one; three columns of `[T, D]` in total, N(N + 1) / 2 for N blocks), on the per layer partial sum (one `[T, D]` per layer, a plain residual's cost), and on the fp32 internals of `_apply_attention_residual` being the dominant saved term without recomputation. What to add: the exact release points (a layer's saved set is freed when its backward finishes, the `[T, 1, D]` column when layer 1's backward finishes, the `[T, 2, D]` column when layer 4's does), what `SelectiveAC` (the flavor's default, per op) saves versus recomputes in that function, and a measured table: run the new 8 layer debug model without PP under `torch.autograd.graph.saved_tensors_hooks`, record shapes and dtypes per layer, and print the count. That is a mechanism table, device independent, fine to take from the local box.

Measured 2026-09-20 (`logs_pp_round3_2026-09-20/saved_probe_{none,selective,full}.txt`, one 5060 Ti, T = 256): without AC the bf16 stack is saved by no op (only the fp32 upcasts inside the residual read are: two [T, N + 1, D] per call, 8 to 12 MiB per layer out of 94 to 113); under `SelectiveAC` and full AC each layer's region saves h and the stack only, so the three columns (one storage each, layers 2 to 4 sharing layer 1's, 6 and 7 sharing layer 5's) are the whole AttnRes overhead, 1.5 MiB. Memory left after the forward above the parameters: 383 / 63 / 15.5 MiB for none / selective / full. The reply is written from this.
