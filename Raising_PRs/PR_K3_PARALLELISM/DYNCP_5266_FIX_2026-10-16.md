## 10-18：方案 B 是什么，和 A 比（用户："4380 方案B是什么来着？我觉得回滚她的代码不太好"）

- **方案 B：** 保留 #5266 的机制（tower 标 `I@CP`，FSDP 只在 dp_shard 上切，输出梯度在 CP 上 all-reduce），在 dynamic CP 内部补偿：
  1. bank gather 的反向只取自己那份，不求和；
  2. 整图那部分的梯度在每个 rank 上乘 1/C；
  3. 反向结束后、梯度裁剪之前，对 tower 的参数梯度在 CP 上做一次显式 all-reduce。
- **为什么两个方案都绕不开 CP 上的参数梯度归约：**
  - 参数梯度是所有 token 贡献的和。切开的 band 只在属主 rank 上算，各 rank 的参数梯度必然不同。
  - #5266 之后 tower 在各 CP rank 上是完整副本，副本要保持一致，就必须在 CP 上做一次参数大小的归约，或者每个 rank 都把所有 band 重算一遍（等于不切）。
  - 区别只在归约放在哪：A 让 FSDP 在 dp_shard x cp 上做 reduce-scatter（#5266 之前 main 就是这样）；B 自己做 all-reduce。
- **B 的代价：**
  - "反向之后、裁剪之前"这个位置，titan 没有现成的接缝，只能加一个 hook，违反 "titan's seams first"。
  - 通信更多：all-reduce 约等于 reduce-scatter 加 all-gather，而且 tower 的梯度在 CP 上不分片，显存更高。#5266 正文里显存已经从 3.93 涨到 5.18 / 8.36 GiB。
  - 类型不再如实：仍然标 `I@CP`，但反向途中各 rank 的梯度不同，类型检查验证不了。
- **A 并没有回滚 #5266 的默认行为：**
  - 别的 encoder，以及 K3 不开 dynamic CP 时，走的都是 #5266 原来的路径；
