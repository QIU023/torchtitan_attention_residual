`get_total_norm` accumulates in the input tensors' dtype. With bf16 gradients split across ranks, each rank's partial norm is rounded before the partials are combined, so under pipeline parallelism the reported total depends on how many stages the model was cut into rather than only on the gradients. This PR adds a `dtype` argument that accumulates the per-tensor norms and the norm of norms in that dtype. Moved here from [torchtitan PR](https://github.com/pytorch/torchtitan/pull/4135).

### Commit 1: DTensor `_foreach_norm.Scalar` does not read `dtype` as `dim`

`_foreach_norm.Scalar` shares `vector_norm`'s DTensor sharding strategy, which reads `args_schema[2]` as `dim`, while `_foreach_norm`'s schema is `(self, ord, *, dtype)`: position 2 is `dtype`, so `torch._foreach_norm(tensors, ord, dtype=...)` on DTensors raises today. Setting `dim=None` for that overload fixes every `_foreach_norm(dtype=)` DTensor caller, the FSDP gradients `get_total_norm` sees included, and keeps `get_total_norm` a plain passthrough with no DTensor special-casing.

### Commit 2: `get_total_norm(..., dtype=)`

`dtype` is passed through to the three norm calls the function already makes (`torch._foreach_norm`, the per-tensor `torch.linalg.vector_norm` and the norm of norms); both ops already accept `dtype`. `dtype=None` keeps today's behavior.

### Commit 3: tests

- `test_nn.py::test_get_total_norm_dtype`: bfloat16 `[255, 32, 1]`, whole and split into `[g[:2], g[2:]]`, foreach on and off, p in {1, 2}. With `dtype=torch.float32` both give the exactly rounded norm (`atol=0, rtol=0`); without it the result is bfloat16 and, for p=2, depends on the split (258 whole, 256 split).
- `test/distributed/tensor/test_math_ops.py::test_foreach_norm`: the existing DTensor test also runs bfloat16 input with `dtype=torch.float32` and checks the output dtype; without commit 1 it raises.

### The two splits

512 bf16 gradients, byte-identical at every world size; the only thing that changes is how they are divided across ranks. Both divisions come from real training:

- **FSDP.** Every gradient is a DTensor `Shard(0)` over the mesh. `get_total_norm` returns a DTensor carrying `_NormPartial`, and `full_tensor()` performs the cross-rank combine.
- **Pipeline.** Rank `r` owns `grads[r::world]` as plain tensors, which is what a stage holds. Each rank norms its own, then the partials are all-reduced.

The reference is float64 over the whole set, computed identically on every rank, so it does not depend on the world size. Neither should the reported norm.

### Result

```
                world=1    world=2    world=4    world=8    spread(rel)
dtensor today   256.000    256.000    256.000    256.000    0.00e+00
dtensor fp32    255.682    255.682    255.682    255.682    0.00e+00
pp today        256.000    255.973    255.505    255.631    1.93e-03
pp fp32         255.682    255.682    255.682    255.682    5.97e-08
float64 truth   255.682226
```

The pipeline row is the defect: the same gradients report a different norm depending only on how many stages the model was cut into, so clipping takes a different-sized step for a reason that has nothing to do with the gradients. The DTensor row does not vary with the world size but sits 0.12% off the truth, bf16 having snapped the total to 256. Passing `dtype=torch.float32` puts both on the truth.
