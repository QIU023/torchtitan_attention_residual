Rebased onto current main. The two red jobs were the `inductor_aoti_fallback` CPU shards, which Dr. CI lists as unstable and unrelated (`test_aot_inductor_arrayref.py`, an AOTI debug printer test); the rebased head reruns them.

On point 3: agreed that the test asserted CPU/CUDA rounding on every device type. The literals 258 and 256 are what the CPU and CUDA kernels give, since both accumulate bfloat16 in float32 and round to nearest even. The structural form `whole != split` does not travel any better: a backend that accumulates in bfloat16 gives 256 for both the whole tensor and the split, so the inequality would fail there too. The test is therefore restricted to cpu and cuda with `@onlyOn(["cpu", "cuda"])`, and keeps the exact values, which document the rounding chain the argument removes. `onlyNativeDeviceTypes` would not do, as `NATIVE_DEVICES` now includes `mps` and `mtia`. The `dtype=torch.float32` comparisons stay `atol=0, rtol=0`.

On the docstring: added the constraint. `dtype` must be a floating point type the inputs promote to (`torch.promote_types(input.dtype, dtype) == dtype`), which is the check `linalg.vector_norm` and the foreach CUDA kernel make, and anything else raises.

On point 2, since it is the same defect one function down: `dim` and `keepdim` are now read by their position in the op's schema (`_dim_keepdim_from_schema`), shared by the vector_norm and powsum strategies, so `_foreach_powsum.Scalar` with `dtype=` works as well and the op identity check is gone. `test_foreach_powsum_sharded` gained a bfloat16 input with `dtype=torch.float32`.

Locally, on the nightly with the patch overlaid: the 8 `test_get_total_norm_dtype` cases pass on cpu and cuda, the 8 DTensor `foreach_norm` / `foreach_powsum` tests pass on 4 GPUs, and the new powsum case raises the old `'>=' not supported between instances of 'torch.dtype' and 'int'` with the previous strategy.
