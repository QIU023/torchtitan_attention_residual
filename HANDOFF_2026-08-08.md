## Two real defects fixed, both found by a check the matrix could not make

### LoRA: a Rowwise base with a plain input lost its all-reduce

`KimiLoRALinear.forward` had a branch for "plain input but a DTensor base weight",
written for NoParallel descents where the weight is Replicate and `to_local()` is
exact. It bypasses `self.base`, so the registered TP style's collective never runs.
With a **Rowwise** base the weight is `Shard(1)` -- the contracted axis -- so the
local product is only this rank's PARTIAL contribution, and `to_local()` drops the
DTensor that would have summed it. The partial escapes as a plain tensor, which
everything downstream reads as replicated.

MLA's `o_proj` is the only site: it is the one Rowwise LoRA target reached with a
plain input, because the attention output is built in plain-tensor land. The dense
FFN's `down_proj` is also Rowwise and also wrapped, but receives a DTensor from the
Colwise gate/up pair, so it took the correct path all along.

Verified three ways: cross-rank values bit-identical; 26 of 26 replicated gradients
at `max_delta` exactly 0.0 over 3 steps with non-zero magnitudes; and from a shared
seed checkpoint against tp1 (7.65207 / 3.6093), tp2 goes from 2.9e-02 loss and
5.7e-02 grad_norm error to 4e-05 and 0, tp4 from 3.1e-02 and 4.97e-01 (14% off) to
0 and 4e-04. Error growing with TP degree is the shape a missing all-reduce has:
the surviving fraction is 1/tp.

### MLA's CP path dropped the TP all-reduce for k_rot's gradient

The CP branch leaves DTensor land so the CP collectives run on plain tensors, with a
bare `to_local()`. That defaults the incoming gradient's placement to the forward
placement, which for a Replicate value is correct only when every rank does the SAME
work with it -- KDA's redundant kernels, which is why `_to_local_if_dtensor` keeps
the default and is unchanged.

`k_rot` is not that case. It comes from `kv_a_proj_with_mqa` (NoParallel ->
Replicate) and is expanded onto THIS rank's head subset, so each rank holds one
partial contribution and the true gradient is their sum: Partial, not Replicate.

Measured: at tp2 x cp2 all four MLA layers' `kv_a_proj_with_mqa` gradients differed
across the tp pair by 1-6% relative on every step, while tp2, fsdp2 x tp2 and
fsdp4 x tp2 were bit-identical. **CP is the axis that matters, not FSDP.** After
the fix, 0 disagreements over 3786 comparisons.

## The matrix cannot see either of these, and why more steps do not help

The matrix judges by **loss agreement**, whose band is 0.009 full-parameter and
0.0146 under LoRA. The `o_proj` defect was 2.9e-02 in step-1 loss -- inside the
band. The MLA CP defect was 1-6% on one parameter's gradient and moved the loss far
less. More steps widen the band rather than narrowing it.

Worse, a BACKWARD-only defect is invisible in step-1 loss **by construction**. The
`k_rot` ablation on today's head shows it: step-1 loss is identical to five decimals
in all three TP+CP cells, and the fix shows up only in the trajectory (step-100
0.0088 / 0.0244 / 0.0093). So it is not "too small to see at step 1" -- it is
exactly zero there.

### The check that can see them: `matrix_scripts/replicate_axis_check.py`

A gradient `Replicate` on some mesh axis must be bit-identical across that axis:
exactly 0.0 or a bug, no tolerance to interpret, and no reference run needed. Every
property it has was paid for:

* **Per-axis subgroups, not the world group** -- a gradient can be Replicate on tp
  and Shard on fsdp; gathering over the world compares different shards.
* **The verdict is world-REDUCED before printing.** At fsdp2 x tp2 x cp2 ranks 6 and
  7 each held 12 disagreements while ranks 0-5 held none, and a rank-0-only verdict
  printed PASS.
* **The reduction happens inside the step**, because torchtitan destroys the process
  group before `main()` returns, so a collective afterwards is a silent no-op -- it
  printed PASS on that same run.
* **An explicit verdict line the collector must REQUIRE.** Import errors, OOMs and
  port collisions all exit 1; a missing PYTHONPATH once read as "four cells found
  problems".
* **`NOASSERT` distinct from `FAIL`**, and `comparisons == 0` is not a pass.
* **Agreements recorded with magnitude**, so zero-agrees-with-zero is not counted.

Coverage, stated rather than implied: **TP-bearing cells only.** CP-only and
FSDP-only cells have no Replicate axis, because the `"fsdp"` mesh here is
`dp_shard x cp` so parameters are sharded on the cp axis too. That contradicted the
general CP invariant I had written into the script and surfaced only because it
records `no_replicate_axis` instead of skipping silently -- had it read "nothing to
compare" as a pass, cp2 would have shown green.

For the uncovered cells the verdict must be "within the measured floor", not "zero".
The floor: changing ONLY the gradient-accumulation order on one GPU with no
parallelism gives a norm-weighted max of 0.0975.

## Dynamic CP: both halves of report 5.2.3, verified

Patch-dimension partition with gather-KV, plus sub-CP groups with LPT balance.
Sub-groups are pre-created at setup for every divisor of `cp_size`, because
`new_group` must be called by every process with the same rank list in the same
order -- a per-batch call would have each rank passing its own CP group and hang.

**Verified:** the whole tower reproduces the unpartitioned features to
`max|delta| = 0.000e+00` in fp32 at two ranks, on (1,8,4), (1,6,4), the report-arch
config's own (1,16,16), and the frame-spanning (2,8,4).

Four defects on the way, each found by measuring:

1. **Positions.** MoonViT carries position twice -- the divided_fixed absolute
   embedding and 2-D RoPE -- and both start at row 0, so a shard described as a
   standalone image got rank 0's positions. Both tables are now built for the whole
   image and sliced.
2. **A tolerance that passes either way is not a measurement.** `rtol=2e-3` in fp32
   passed with defect 1 present; the legitimate difference there is 1e-6.
3. **`--training.dtype float32` does not reach the tower.** Tensors arriving at
   `MoonViT.forward` are bf16 even in an fp32 run: the `"fsdp"` mesh is
   `dp_shard x cp`, so CP alone puts FSDP in the path and FSDP all-gathers the fp32
   master into a bf16 compute copy. Reading `patch_embed.proj.weight` before the
   forward hook shows fp32 and misleads. **Every tower A/B therefore has a bf16
   floor**; the residual 1.93e-03 training delta is 3.6e-03 relative per feature,
   exactly `2**-8`. An earlier round read "the gap grows in fp32, so it is not
   rounding" as evidence -- that run was never fp32 where it mattered.
4. **The projector collapses time.** `tpool_patch_merger` is `sd2_tpool`:
   `mean(dim=0)` over ALL frames. Splitting a video by FRAMES therefore gives each
   rank the mean of its own frames, so the concatenation is `t` times too many
   tokens rather than the mean -- 100% mismatch at t=2. The partition is a band of
   spatial ROWS with every frame on every rank, which also makes t=1 a contiguous
   slice. Corollary: a partitioned image emits `(h/kh)*(w/kw)` tokens with no `t`,
   so `counts // merge` is right only for stills.

## ViT DEP: the decoupling works; the bubble hiding is proven NOT to work this way

**Read `phase13_k3like_48b_posttrain/VIT_DEP_DESIGN_2026-08-07.md` from the bottom
up** -- its later sections correct its earlier ones, and the corrections are the
content.

Implemented and exact: **ViT and text as separate PP stages** (`KIMI_VIT_DEP=1`, off
by default because it changes the stage count). From a shared seed checkpoint --
required, because different stage splits consume RNG differently and cold start gave
a misleading 0.05 -- step-1 loss matches non-DEP at pp2/1F1B, and matches on BOTH
loss and grad_norm at pp4/1F1B and pp2/Interleaved1F1B. So the tower's placement is
now configuration rather than a hard attachment to the embed stage.

**Not implemented, and now known to be unreachable by this route:** the bubble
hiding. Three measurements, none of them wall clock:

1. pp8 x Interleaved1F1B, 16 virtual stages: **2019 bubbles with DEP, 2019 without**.
   Identical. A stage's actions are on the critical path, and since the vision stage
   is taken out of the text budget, DEP swaps a text stage for a vision stage -- same
   dependency graph, same stalls, vision work in a COMPUTE slot rather than a bubble.
2. **All 24 IR reorder candidates were rejected by the lowering** ("Malformed compute
   schedule, can't schedule sends/recvs"), with the action multiset verified preserved
   each time. Deferring a vision forward on one rank leaves the consumer's forward
   earlier in ITS list, so no send/recv pairing exists. Fixing that cascades through
   every downstream stage, which is a different schedule rather than a reorder.
3. The reason both hold: at `n_vit = 1` the vision stage IS the pipeline head, so the
   bubbles are downstream of the work that would fill them.

**This closes a loop I opened myself.** `VIT_DEP_DESIGN_2026-08-06.md` argued exactly
(3) -- "the idle that looks free is upstream of the work that would fill it" -- and I
superseded it for being "derived from my own timing analysis rather than the report".
It was right. The lesson is about the supersede: "this came from my own reasoning
rather than the source" is a reason to CHECK a claim, not to discard it.

What is left is a concurrent design: micro-batch m's encode overlapping m-k's text
compute on a side stream, the pipeline never waiting because the encode ran k ahead.
That is outside the PP schedule, so two things must be decided deliberately -- the
AttnRes adapter's "PP owns all NCCL" property would be given up, and the lookahead k
is bounded by the memory for k micro-batches of live vision features, which is what
decides whether "most" of the ViT can be hidden or only some.

**Cost weights, if anyone quantifies this:** they are not derivable from a model
config. Computed from the configs, one ViT forward on a 1024-patch image is **25.2
text layers** at `report_arch_pp8vp4` but **0.057 of one layer** at the real
`2p8t_vl` -- ~440x apart, because the debug flavor's text side is tiny. A share of
step time needs the visual token budget per micro-batch, which is a data parameter,
and attention is quadratic in patches so large images cannot be extrapolated linearly.

Beyond the earlier verification, the multi-sub-group path has now actually run rather

sub-group count is the largest divisor of `cp_size` not exceeding the large-image
count. The report gives no rule for either.

## ViT DEP: the exchange contract (earlier note, still accurate)

Design: `phase13_k3like_48b_posttrain/VIT_DEP_DESIGN_2026-08-07.md`. The
2026-08-06 design is superseded.

**The API fact that settles the shape.** `register_custom_function` validates
`computation_type` against a CLOSED set (`FORWARD`, `FULL_BACKWARD`,
`BACKWARD_INPUT`, `BACKWARD_WEIGHT`, `OVERLAP_F_B`, `UNSHARD`, `RESHARD`,
`REDUCE_GRAD`), so a new `VIT_FORWARD` action cannot be added and "inject work into
the bubble" is not expressible. That is the better outcome: **if the ViT is a
STAGE, its forward and backward are already in the action list** and the interleaved
schedule places them where bubbles would be. So the deadlock risk I had recorded --
sends outside the action list, giving up "PP owns all NCCL" -- does not arise, and
the pipeline stays linear.

**The blocker, verified against current core rather than trusted from a comment.**
`_split_module` iterates only `named_children()` and never recurses: a non-container
child is kept if its bare name is in `modules_to_keep`, otherwise set to None. On
the multimodal wrapper the children are `vision_tower` and `language_model`, so you
can isolate the tower OR split the text layers, not both. The options are to hoist
the text stack's children up to the wrapper (which changes the parameter namespace,
though `_register_mm_prefix_hooks` already exists to reconcile the two) or to build
the ViT stage manually instead of through `pipeline_llm`.

**Landed now:** the stage exchange contract in `vit_cp_plan.py` --
`stage_exchange_lengths`, `stage_exchange_capacity`, `pack_stage_features`,
`unpack_stage_features`. The load-bearing property is that **the exchange shape must
be a CONFIG-level upper bound, never batch-derived**: PP sizes its P2P buffers once,
so a batch-derived shape works until a later batch carries more image tokens, and
then it fails inside the P2P far from the cause. Sizing needs no communication --
`grid_thw` is replicated, so both stages compute the same layout. Overflow raises
rather than truncating, because a truncated vision feature is a silently wrong model
the receiver cannot detect.

## Disk, which took bash down mid-matrix

At 100% full the agent harness could not write a command's output file either, so
bash stopped working entirely. `/tmp` held 227 GB of checkpoints from matrices whose
evidence is the ~200 KB log beside them.

`matrix_scripts/prune_run_artifacts.sh` deletes `checkpoint/` and JIT caches and
**keeps `tb/`** -- measured on one 13-cell matrix, `checkpoint/` is 9.0 GB,
`structured_logs/` 159 MB, `tb/` 1.3 MB, and tb is the one thing that must survive
because stdout prints five significant digits and a real loss comparison has to come
from the TensorBoard record. The first version deleted whole dump folders, which
would have destroyed the only full-precision copy of every published matrix.
Reclaimed **242 GB**, 84% -> 20%. `disk_watchdog.sh` runs it as a supervisor service
every 60s below 40 GB free (not the requested 10 GB: one 8-GPU 100-step cell writes
~700 MB and eighteen write ~12 GB, so at 10 GB the writer outruns the sweep). Both
matrix runners now drop each cell's checkpoint as that cell finishes. **`/tmp` and
`/workspace` are the same overlay here**, so cleaning `/workspace` alone does
nothing for a full `/tmp`.
