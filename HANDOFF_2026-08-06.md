## ViT DEP -- design only, and the RECOMMENDATION below is superseded

Not implemented. **Read `phase13_k3like_48b_posttrain/REPORT_ALIGNMENT_DEP_CP_MTP_2026-08-06.md`
first.** Report sec 5.2.3 prescribes the hybrid -- the first PP micro-batches' ViT
forwards synchronously upfront, the REMAINING forwards scheduled into pipeline
bubbles, backward analogously, with ViT and text as separate stages. That strictly
dominates Design A below, which leaves every bubble empty. The dependency inversion
Design A was built around is real and the report works around it the same way; the
conclusion drawn from it ("so put all of it in a parallel prologue") is what is
wrong. What follows is kept because the constraints it establishes still hold.

**The task was posed as "put the ViT compute into the PP bubbles", and that is the
wrong thing to optimise.** Bubbles are a fixed O(P) cost -- warmup plus cooldown,
independent of the microbatch count. The vision encode is proportional to M, since
every microbatch carries images. So as M grows the bubble fraction shrinks while
the tower's share does not. The real win is that today the whole tower runs on the
stage owning `embed_tokens` while P-1 stages wait, and at real scale MoonViT-V2 is
447.4M against k3mini's 80.9M text side. The bubble is just where the spare
capacity happens to sit.

**Why the naive version cannot work.** Stage 0 needs microbatch 0's features at the
START of its first forward; stages 1..P-1 are idle at that moment precisely because
they are waiting for stage 0. Formally stage k is idle for t in [0,k) and stage 0
needs microbatch j at t~=j, so stage k can only serve j >= k and must finish inside
k slots. For small j that is one or two slots and the tower's forward does not fit.

**Design A -- parallel prologue (SUPERSEDED; see above).** Before the action list starts,
every PP stage encodes a disjoint slice of the batch's images; one collective on
its own communicator; schedule untouched. Tower time `T_vit -> T_vit/P + gather`.
It does not overlap the bubble -- it shortens the prologue, which is the deliberate
trade for keeping the property the AttnRes adapter is built around, that PP owns
all NCCL.

**Design A is the ViT CP mechanism with the group swapped**, and that code is
landed and verified (below). The real prerequisite is tower weights on every PP
stage -- today only stage 0 has them, and `pipeline_adapter` states "nothing
vision-side crosses a stage". Replicating 447.4M across 8 stages does not scale;
FSDP-sharding the tower along the PP axis does, and is a new mesh interaction.

**Design B -- true interleaving.** Three reasons not to reach for it first: benefit
bounded by (M-J0)/M and vanishing for short pipelines; delivery runs AGAINST the
pipeline direction (stage k -> stage 0) and no such channel exists; and it requires
sends interleaved with the schedule's action list, which is exactly how PP
deadlocks and gives up the adapter's deadlock-free property.

**Not in the way:** the AttnRes cross-stage adapter is orthogonal. Verified
bit-identical on and off, multimodal PP8xVP4, seq 1024 through 8192.

**Sequence to implement A:** (1) shard the tower across the PP axis; (2) make the
CP image-sharding helper take a group argument so one implementation serves both
axes; (3) A/B as CP was verified -- exact equality is the expected result, since
distributing images changes no arithmetic.

`language_model.model.*`. That the failures were ALL and ONLY expert keys is what
pointed there rather than at the prefix logic, which was choosing correctly.

## ViT CP -- landed and verified (`57c6728ed`)

Under CP the vision tower was **replicated**: text tokens were sharded but
`pixel_values` was not, so every CP rank encoded the whole batch's images and
discarded what its sequence shard did not need. Now each rank encodes a disjoint
round-robin slice and the features are shared.

**No new mesh needed**, which our notes had recorded as the blocker: the unit of
work is the IMAGE, so the assignment is per-batch while the group stays the static
`_cp_group`. Sizing needs no extra communication either -- `grid_thw` is
replicated, so every rank knows every output length up front and the exchange is a
fixed-shape `funcol.all_gather_tensor`, whose transpose is the reduce-scatter that
returns each rank the gradient for the images it encoded.

**Verified:** step-1 loss AND grad_norm bit-identical, in bf16 AND fp32, on the MoE
flavor AND the dense control. Published matrix legs are unaffected -- they run
`local_batch_size 1`, so the path never triggers.

**Two traps this hit, both worth carrying forward:**

1. The first run looked perfect and proved nothing -- the path never engaged, because
   `local_batch_size 1` means one image per microbatch and `len(counts) < cp_size`.
   Engagement is now asserted by log, not inferred.
2. **"step 1 matches, step 2 does not" is not evidence of a backward bug.** It looked
   like under-reduction. It is not: the `"fsdp"` mesh IS `dp_shard x cp` and
   `disable_fsdp_gradient_division` is applied, so tower gradients are summed across
   CP. A missing reduction would show as a factor-of-cp error; fp32 showed ~1e-5. And
   the dense control, with no routing to flip, shows the same pattern -- so it is
   reduction order amplified by Adam's first updates, where the update magnitude is
   ~lr almost independently of gradient scale. **Distinguishing a real reduction bug
   from that needs a dtype sweep and an architecture control, not more staring at the
   same two numbers.**

Related and also landed: ViT MLP TP (`54810694d`) and ViT attention head TP
(`e37faff3c`, with `kimi_k3_debugmodel_report_arch_vit4h` because the shipped debug
tower has 3 heads, which no TP degree divides).

## LoRA TP -- FIXED (2026-08-07)

Root-caused and fixed. Full trace, numbers and the reasoning that misdirected the
search first: `phase13_k3like_48b_posttrain/LORA_TP_2026-08-05.md`, section
"RESOLVED (2026-08-07)".

**The defect.** `KimiLoRALinear.forward` had a branch for "plain input but a
DTensor base weight", written for NoParallel descents (MoE shared experts, weight
Replicate, where `to_local()` is exact). It bypasses `self.base` entirely, so the
registered style's collective never runs. With a **Rowwise** base the weight is
`Shard(1)` -- the CONTRACTED axis -- so the local product is only this rank's
PARTIAL contribution, and `to_local()` drops the DTensor that would have summed
it. The partial value escapes as a plain tensor, which everything downstream reads
as replicated.

**Why `o_proj` alone.** It is the only Rowwise LoRA target reached with a plain
input, because MLA builds the attention output in plain-tensor land. The dense
FFN's `down_proj` is also Rowwise and also LoRA-wrapped, but receives a DTensor
from the Colwise gate/up pair, so it takes the `self.base(x)` path and was clean.

**Scope is LoRA + TP, not TP.** The same trace with LoRA off is bit-identical at
`o_proj` and everywhere after it, so the published matrices' non-LoRA TP legs are
unaffected. The worry that every TP leg might be running a rank-divergent residual
stream does not hold.

**What found it.** Recording the whole residual stream of layers 0-1 in EXECUTION
ORDER with placements and cross-rank deltas, and reporting the FIRST unexpected
divergence -- `phase13_k3like_48b_posttrain/tp_residual_stream_probe.py`. One run
located it; four rounds of hypothesise-and-refute had not. Both refuted hypotheses
were about the adapter arithmetic and the defect was in the base. The trace also
named it directly: no `o_proj.base` row appears at all, while every other target
has one, because its forward is bypassed.

**Verification.** Replicate-gradient probe at tp2 over 3 steps: 26 of 26 agree,
`max_delta` exactly 0.0, with non-zero `ref_absmax` at steps 2-3 so they are
genuinely testable (before: 22 of 24 testable disagreed). Seeded protocol against
tp1 = 7.65207 / 3.6093: tp2 goes from 2.9e-02 loss / 5.7e-02 grad_norm error to
4e-05 / 0, tp4 from 3.1e-02 / 4.97e-01 (14% off) to 0 / 4e-04. The error growing
with TP degree is the shape a missing all-reduce should have -- the surviving
fraction is 1/tp. Regression test `tests/test_lora_rowwise_plain_input.py`, which
**needs two ranks**: on a world_size=1 mesh the missing all-reduce is a no-op and
the test passes either way, which is how this survived a single-process suite.
Suite 268 passed.
