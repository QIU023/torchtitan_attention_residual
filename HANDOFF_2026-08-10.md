## The two results that matter most

### PP produces bit-identical gradients. The band was the instrument.

Open since 2026-08-02 under three explanations -- LoRA, then AttnRes, then KDA (mine,
today) -- all wrong. The runner compared a reference at `local_batch_size 2` (one forward
at batch 2) against a pp2 leg running microbatches of 1: different tensor shapes into
every kernel. `chunk_kda` is a chunked scan whose blocking depends on shape, which is why
only KDA responded and why the response compounded with KDA layer count.

Matched shapes: `max>1%` goes 0.16749 -> **0.000000 across all 592 parameters** on the
21-layer KDA+MoE+AttnRes flavor. Full write-up in
`phase13_k3like_48b_posttrain/GRAD_BAND_RESOLVED_2026-08-10.md`.

This is a stronger statement about PP than the loss matrix makes: the matrix compares a
cell against itself across code changes and never compares one parallelism against
another. **CP and TP are NOT covered** -- sharding the sequence or the heads is what they
do, so the scan blocks differently by construction and their 0.16 needs a different
control. That is the open half.

### A core defect: grad norm was computed in the gradients' dtype

`torch.nn.utils.get_total_norm` returns the norm in the input dtype, so with
`training.dtype=bfloat16` the reported and APPLIED norm was accurate to 3-4 digits and its
error depended on how parameters were grouped. Clipping fires every step here, so the
error went straight into the update. Two PP layouts with identical gradients reported
10.008054 and 9.951641 against a float32 truth of 9.989287.

Fixed in `torchtitan/distributed/utils.py` (`ee114861f`). Upstream kit ready at
`Raising_PRs/PR26_torchtitan_grad_norm_low_precision/`, verified on a CLEAN upstream
worktree (`681fd4b50`) with unmodified `llama3_debugmodel`: float32 rows unchanged, bf16
step-1 norm moves 1.4453 -> 1.4485, which is what the float32 configuration reports.

## veRL

The titan engine exists upstream (`verl/workers/engine/torchtitan`), which settles the
"unverified conflict" CLAUDE.md flagged.

**LoRA weight sync now transports what LoRA learns, checked end to end.** Three defects on
the way:

* the sync shipped `module.state_dict()`, so the adapter tensors (which have no HF
  mapping) were dropped and the frozen base went out -- identical weights every step,
  the same shape as the deliberately broken FREEZE_SYNC control;
* `merge_lora_state_dict` keyed on `named_modules()` while `state_dict()` strips wrapper
  segments, so under activation checkpointing it wrote an unrecognisable key AND left the
  adapter triple behind (surfaced as `Unmapped tt key:
  'layers.0._checkpoint_wrapped_module.ffn.gate_proj.weight'`);
* the checksum probe read `embed_tokens.weight`, frozen under LoRA, so its digest was
  constant regardless -- the same "reads the same either way" failure the probe existed to
  replace.

Evidence, `kimi_k3_debugmodel_report_arch_lora`, 3 GRPO steps, 4 syncs:

    live    5025434ac0b1cc95 -> 3fac48a58dbf4316 -> d6da94cc8680b412 -> 8bf479e0d7c98f6e
    frozen  5025434ac0b1cc95 x4

The frozen arm's first digest equals live's, so both provably start from the same state.

**Limitation, worth knowing before planning around LoRA RL:** this engine returns
`peft_config=None`, and `engine_workers` gates its base-then-adapter sequence on that being
present, so adapter-only sync is unreachable and a run with `model.lora.merge=False` still
gets merged full weights. LoRA buys optimizer and gradient memory here, not sync bandwidth.

## Method lessons that cost real time

* **A single variable moving the number is not causation.** Three wrong attributions of the
  same band -- LoRA, AttnRes, KDA -- all failed identically: an arm was run, the number
  moved, the variable was named, and nobody checked the two arms were otherwise equivalent.
  The shape difference was in the runner's arguments the whole time.
* **The "worst parameter" column names where a problem SHOWS, not where it starts.**
  `attn_res_proj` led three documents to AttnRes; it is an amplifier, mixing every block.
* **Validate an instrument against a known output before using it.** The compare script
  reproduced the LoRA arm's recorded numbers exactly and NOT the full-parameter arm's --
  which is how the 2.37 discrepancy surfaced.
* **Read a probe's own selection rule.** The sync checksum picked the first floating-point
  key in sorted order, which is frozen under LoRA. Constant digests read as "sync broken"
  and proved nothing.
* **Assert engagement from a log, not from a downstream symptom.** My merge log shipped at
  `info`, never appeared, and "the merge ran" was inferred from an error message.
* **A negative control that fails for the wrong reason is not a control.** Reverting a
  rename made tests fail with `AttributeError` rather than on behaviour; the body had to be
  reverted separately.
* **Read `p.grad` BEFORE `clip_grad_norm_`** -- it rescales in place, and the first version
  of the multiset probe measured post-clip values.
* `n_microbatches == local_batch_size`, and EP is not a multiplicative factor in world size.
  Both cost failed runs today.
* The matrix runner assigns fixed per-cell ports and lost one cell to `EADDRINUSE` on three
  consecutive runs before retry-on-busy-port was added.
